=== FILE frontend/src/App.tsx
>>> SUMMARY
The **map of the whole frontend**: which address shows which page, and which roles may open it.

**Routing** means choosing what to show based on the address in the browser's address bar. React Router watches the address. When it changes (a menu link is clicked, or the user presses Back), it shows the matching page **without asking the server for a new HTML page**.

**The layers, from outside to inside:**
1. `BrowserRouter`: routing, using the real address bar;
2. `ToastProvider`: any page can pop up a short message;
3. `ConfirmProvider`: any page can ask "Are you sure?";
4. `AuthProvider`: who is logged in, and the login/logout functions;
5. `Routes`: the address → page table.

Each "provider" makes something available to **every** component inside it, without passing it through each level by hand. This is React's *context* feature.

**Two guards:**
- every page except `/login` is inside `<RequireAuth>`: not logged in → sent to the login page;
- `only([...roles], page)` additionally checks the role: logged in but the wrong role → a "not allowed" message.

**Important:** these guards only decide what the **screen** shows. The real protection is the backend's RoleMatrix, which checks every request. Someone who changes the frontend's code in their own browser still gets 403 from the server. The frontend guard exists for **convenience**: people are not shown pages they cannot use.

**To add a page:** create the page file, add a `<Route>` here, and add a menu line in `navigation.ts`.

=== FILE frontend/src/config.ts
>>> SUMMARY
Frontend **settings that are neither text nor colours**. (Text lives in `i18n/messages.ts`, colours in `styles/theme.css`.)

Some values here must **match the backend**. They are repeated so the browser can warn **before** sending anything (for example "this file is larger than 5 MB") instead of after a slow upload. If you change one side, change the other too. Even if they disagree, the backend's value always wins, because the server checks again.
>>> 6
`API_BASE = ''`: every backend address starts from the page's own origin, so requests go to `/api/...` on the same host and port. In development Vite forwards them to port 8080; in Docker nginx does. The frontend code is the same in both cases.
>>> 9
The attendance threshold shown on screen (75%). It must match the backend's `edumate.academic.attendance-threshold-percent`.
>>> 12
The largest upload: 5 × 1024 × 1024 = 5,242,880 bytes. It must match `spring.servlet.multipart.max-file-size: 5MB`.
>>> 15
The demo password shown on the login page.
>>> 18-35
The demo usernames listed on the login page, in display order. `as const` makes TypeScript treat the list as fixed, so `messages.ts` can be checked to have a description for each one.
>>> 38
Show the demo helper only in development. `import.meta.env.DEV` is `true` under `npm run dev` and `false` in `npm run build`, so a production build never advertises the demo accounts.
>>> 41
How long a toast stays on screen: 5,000 ms = 5 seconds.
>>> 44-45
The timetable grid's days (1–5 = Monday–Friday) and periods (1–6), the same as the backend's `TimetableSolver.DAYS` and `PERIODS`.

=== FILE frontend/src/navigation.ts
>>> SUMMARY
The **left-hand menu** for each role: which links appear, and in which order. The link texts come from `messages.ts` (`t.nav.…`), so renaming a menu item means changing only that text.

A menu link without a matching route in `App.tsx` would lead to "page not found", and a route without a menu link is reachable only by typing its address. So always add both.

Students and guardians share one menu (a guardian sees their child's pages).
