=== FILE backend/src/main/java/com/edumate/exam/ResultStatus.java
>>> SUMMARY
The five **stages** a result set passes through, in order:

<pre class="block">DRAFT ──compute──► COMPUTED ──approve (person A)──► AWAITING_SECOND_APPROVAL
      ──approve (person B, not A)──► APPROVED ──publish──► PUBLISHED</pre>

The SQA Plan adds **Safety** as a quality objective (new in ISO/IEC 25010:2023): "incorrect results cannot reach students irreversibly". Its measure is "two-person approval enforced before any result set is published". These stages are how that is enforced: results can only be published from APPROVED, and APPROVED can only be reached through two approvals by two different people.

If a mark changes after computing, the set goes back to DRAFT (see `ResultSet.invalidate`).

=== FILE backend/src/main/java/com/edumate/exam/ResultSetRepository.java
>>> SUMMARY
Reads result sets and, most importantly, **publishes them safely**. This is the fix for test defect **DEF-027**: "Concurrent publication publishes the same result set twice. Root cause: published flag read and written without a lock."

**The old mistake ("check, then act"):**
<pre class="block">Superintendent A: read status → APPROVED ✓            … write PUBLISHED, send 11,400 messages
Superintendent B:        read status → APPROVED ✓ (A has not written yet) … write PUBLISHED, send them again</pre>
Both checks passed because both read before either wrote.

**The fix: check and act in one step.** `publishIfApproved` is a single SQL statement:
<pre class="block">UPDATE result_set SET status = 'PUBLISHED', … WHERE id = ? AND status = 'APPROVED'</pre>
The database runs an UPDATE on a row one transaction at a time. The first one finds status APPROVED, changes it, and reports "1 row changed". The second one, a moment later, finds PUBLISHED; its `WHERE` no longer matches, and it reports "0 rows changed". The service turns 0 into the message "These results were already published". The automated test `ResultPublicationIntegrationTest` runs two publishes at the same instant and checks that exactly one succeeds.

The report's recommendation says DR-01, DR-02 and DEF-027 are "one underlying pattern: a check-then-act sequence without a lock". This is the third instance, fixed.
>>> 25
`@Modifying`: this query changes data. `flushAutomatically` writes any pending changes before it runs; `clearAutomatically` forgets cached copies afterwards, so the service's next read sees the database's real state.
>>> 26-31
The atomic UPDATE described in the summary, written in JPQL. It also increases the `version` counter itself, because a bulk update bypasses Hibernate's automatic version handling.
>>> 32-33
The method. It returns the number of rows changed: 1 = this call published it, 0 = it was not approved or someone else already published. The two status values are passed as parameters so the query compares enum values safely.

=== FILE backend/src/main/java/com/edumate/exam/ResultComputationService.java
>>> SUMMARY
Computes **SGPA, CGPA and PASS/FAIL for a whole cohort** at once (FR-19; the report calls this design element ResultComputationService). It is started by an examination superintendent clicking "Compute" on the Results workflow page.

The steps:
1. **Checks.** The exam session and programme exist; the programme is on the caller's campus; the results are not already published.
2. **Load everything in two queries** (the fix for DR-03): all marks of the cohort with their course credits, and all earlier published semesters of the cohort.
3. **Refuse incomplete data.** If any mark is missing, stop with "N mark entries are still empty". Computing with gaps would produce wrong SGPAs.
4. **Throw away the old computed rows** of this result set.
5. **For each student:** grade every course, work out SGPA and CGPA, decide PASS (all credits earned) or FAIL, and save the result and course grades.
6. **Mark the set COMPUTED** (clearing any old approvals), write an audit line, and report a summary: how many students, how many passed, the average SGPA.

It deliberately does **not** send any messages. The report found (DR-08) that the old design both computed results and sent notifications, so a slow SMS provider could slow or break the computation. Messages are sent only after publication, through the outbox.

Everything runs in one transaction: if anything fails half-way (for example the database refuses a row), the whole computation is undone and the previous state remains.
