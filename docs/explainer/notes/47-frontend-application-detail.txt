>>> SUMMARY
**One application as the admissions officer (or admin) sees it**, at `/admissions/<id>`:
- **"Where this application is"**: a step tracker along the normal road, Draft → Submitted → Under review → Shortlisted → Offered → Enrolled. An application that left the road (rejected, withdrawn, enrolment reversed) shows a red box with that status instead. The reason for the last decision, if any, is shown under it;
- three **info cards**: personal details (with a "Minor (17)" badge when relevant), programme and scores, and guardian with consent status (a green shield when consent is granted, amber otherwise);
- **all five document boxes**, read-only. Staff can press **View** to open a scan. Each view is written to the audit log as DOCUMENT_VIEWED, because these can be a minor's personal documents;
- the **consent history** (requested / granted / revoked, with the masked guardian contact);
- the **decision** card: a reason box and **one button per action the state machine allows for this role** (for example Shortlist and Reject on an UNDER_REVIEW application). Actions that end or undo something (Reject, Reverse enrolment, Withdraw) are **red**, and their confirmation dialog has a red button too.

The buttons come from the backend's `allowedActions`, built from the same table that enforces the rules, so the page can never offer a button the backend would refuse (except when the rules need a reason and none was typed: then the backend answers "Please give a reason for this decision.").
