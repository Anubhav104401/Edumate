=== FILE backend/src/main/java/com/edumate/fees/PaymentOrchestrator.java
>>> SUMMARY
Handles **fee payments through the payment gateway** (FR-08; the report names this design element PaymentOrchestrator). A payment happens in two steps:

1. **initiate**: the student clicks "Pay now". EduMate creates a payment *order* for the amount still due and sends the browser to the gateway's page (in this project, the demo gateway page `/pay/ORD-…`).
2. **handleCallback**: after the bank has taken (or declined) the money, the gateway calls EduMate's callback address with the result, signed with a shared secret. EduMate records the payment, credits the student's fee ledger, and issues a receipt number.

**The defect this fixes.** Design review found **DR-02** and system testing confirmed it as **DEF-014**: "Replayed payment gateway callback credits the fee ledger twice". Gateways sometimes deliver the same callback more than once (a network retry, for example). The old handler credited ₹62,500 again each time, so the ledger showed ₹1,25,000 paid. The handler must be **idempotent**: receiving the same callback twice must have the same effect as receiving it once.

Four guards now make sure a payment is credited exactly once:
- **Signature check**: a callback whose HMAC signature does not match is refused, so nobody can fake a "payment successful" message.
- **Row lock**: the payment row is locked while a callback is processed, so two copies arriving together are handled one after the other, never interleaved.
- **Duplicate recognition**: a callback carrying the bank reference that is already recorded is answered "DUPLICATE_IGNORED" and changes nothing.
- **Database uniqueness**: the payment's bank reference and the ledger credit's reference are UNIQUE columns, so even a mistake in the code could not store a second credit.

The whole callback runs in **one transaction**, so the payment status, the ledger credit and the receipt are saved together or not at all.

=== FILE backend/src/main/java/com/edumate/fees/GatewaySignature.java
>>> SUMMARY
Proves that a payment callback **really came from the payment gateway** and was not changed on the way.

EduMate and the gateway share a secret text (`edumate.payment.gateway-secret`). For every callback the gateway computes

<pre class="block">signature = HMAC-SHA256(secret, "orderId|txnRef|status|amount")
e.g. with the development secret "dev-gateway-secret-change-me":
            HMAC-SHA256(secret, "ORD-81D4440CAE9D45BA|TXN000123456789|SUCCESS|62500.00")
         →  "a7554c0ad616b24f68cda993fd88209343bc813a41fc8a951f355e697c9dd56f"</pre>

and sends it along. EduMate computes the same thing with its copy of the secret. If anyone changed even one character (say, the amount), the two results are completely different. Without the secret it is practically impossible to produce a matching signature.

HMAC is like a wax seal that only the two parties can make. It is the same method the gateways used in India (Razorpay, PayU and others) use for their callbacks.
>>> 26
The algorithm's standard Java name.
>>> 31
Turns the secret text into bytes once, when the component is created.
>>> 34
`sign`: compute the signature for these four fields.
>>> 35-42
- Line 36: get an HMAC-SHA256 calculator.
- Line 37: give it the secret key.
- Line 38: feed it the joined fields as bytes; `doFinal` returns the 32-byte result.
- Line 39: write those bytes as 64 hexadecimal characters (0-9, a-f).
- Lines 40-41: Java requires handling the (practically impossible) case that the algorithm is missing.
>>> 46-53
`verify`: a missing signature is simply wrong (lines 47-49). Otherwise compute the expected signature and compare it with the given one using `MessageDigest.isEqual`, which always takes the same time. An ordinary comparison stops at the first different character, and an attacker could measure those tiny time differences to guess a signature one character at a time.
>>> 55-56
The text that is signed: the four fields joined with `|`.

=== FILE backend/src/main/java/com/edumate/fees/FeeLedger.java
>>> SUMMARY
The **fee account book** of each student (the report's design element FeeLedger). It works like a bank passbook:
- a **DEBIT** line is money the student owes (a bill, e.g. "Semester 5 tuition fee ₹62,500");
- a **CREDIT** line is money the student paid (with the bank reference);
- the **balance owed** = all debits − all credits.

Lines are only ever **added**, never edited or deleted, so the full history can always be checked. A mistake would be corrected by adding another line, as accountants do.

"Fee fully paid" (one of the four inputs of the hall-ticket decision table) means the balance is zero or less.

Adds a DEBIT line (money owed).
>>> 33-35
Adds a CREDIT line (money received).
>>> 40-41
The balance owed, calculated by the database in one query.
>>> 45-46
True when nothing is owed. `signum()` gives −1, 0 or +1 for negative, zero or positive.
>>> 50-51
All lines of one student, oldest first, for the account statement.

=== FILE backend/src/main/java/com/edumate/fees/GatewayCallback.java
>>> SUMMARY
The exact **JSON the payment gateway sends** to `POST /api/payments/gateway/callback`, with a rule on every field. Example:

<pre class="block">{ "orderId": "ORD-81D4440CAE9D45BA", "txnRef": "TXN000123456789", "status": "SUCCESS",
  "amount": "62500.00", "signature": "a7554c0ad616…", "failureReason": null }</pre>

The six fields and their rules: order number, bank reference and signature are required; `status` must be exactly SUCCESS or FAILURE; `amount` must look like digits, a dot and exactly two digits (for example 62500.00); `failureReason` is optional.

=== FILE backend/src/main/java/com/edumate/fees/Payment.java
>>> SUMMARY
One **attempt to pay** a bill through the gateway. It starts as INITIATED when the student clicks "Pay now", and becomes SUCCESS or FAILED when the gateway's callback arrives.

Two ids matter:
- `gatewayOrderId`: **our** number for the attempt (ORD-…), created by EduMate before the student goes to the bank;
- `gatewayTxnRef`: the **bank's** reference for the money movement, arriving with the callback.
Both are UNIQUE in the database. The uniqueness of `gateway_txn_ref` is the database-level half of the fix for DR-02 / DEF-014: the same bank transaction can never be stored against two payments.

`@Version` protects the row against two simultaneous changes.

Creates a new INITIATED payment for a student, bill, amount and order number, stamping the creation and update times.
>>> 77-83
Marks the payment successful: stores the bank reference and receipt number, clears any earlier failure reason, and updates the time.
>>> 85-90
Marks the payment failed: stores the bank reference and the reason given by the bank.
>>> 92-93
True if the payment succeeded. Writing `SUCCESS.equals(status)` (constant first) is a small safe habit: it gives false instead of crashing if `status` were ever null.
