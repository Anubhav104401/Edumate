=== FILE backend/src/main/java/com/edumate/admissions/AdmissionStateMachine.java
>>> SUMMARY
The admission lifecycle written as a **table of allowed arrows** (Fig. 3.2 of the report). A "state machine" is a very simple idea: a thing is always in exactly one state, and it can only move along the arrows drawn for it.

<pre class="block">DRAFT ──SUBMIT──► SUBMITTED ──START_REVIEW──► UNDER_REVIEW ──SHORTLIST──► SHORTLISTED
SHORTLISTED ──OFFER──► OFFERED ──ENROL──► ENROLLED ──REVERSE_ENROLMENT (admin, reason)──► ENROLMENT_REVERSED
WITHDRAW (applicant): from DRAFT, SUBMITTED, OFFERED
REJECT (officer, reason): from UNDER_REVIEW, SHORTLISTED</pre>

**DR-07 fix.** The design review found "no transition out of ENROLLED; enrolment cannot be reversed when made in error". The last row of the table adds that arrow, only for an ADMIN and only with a reason, and every use is audited.

**Why a table?** The alternative is a pile of `if` statements spread over the code ("if status is X and action is Y and role is Z…"). With a table, every rule is visible in one place, a test can check every row (`AdmissionStateMachineTest`), and the screen can ask "which buttons should this person see?" (`allowedActions`) from the very same table. The buttons and the rules can therefore never disagree.

=== FILE backend/src/main/java/com/edumate/admissions/MeritListGenerator.java
>>> SUMMARY
**Ranks the applicants of a programme and allocates seats** (FR-05; the report calls this design element MeritListGenerator).

**Step 1: merit score.** `0.60 × entrance score + 0.40 × qualifying %`, rounded to 2 decimals. The weights come from `application.yml` (`edumate.admissions.entrance-weight` and `qualifying-weight`), so the university can change them without touching code.

**Step 2: ranking.** Highest merit score first. When two scores are equal, the tie is broken by, in order:
1. the higher entrance score;
2. the higher qualifying %;
3. the **older** applicant (earlier date of birth);
4. the earlier submission;
5. the application number.

Application numbers are unique, so no two applicants can ever tie completely. Running the list twice on the same data therefore **always** gives exactly the same order. This matters: a list whose order changes between runs cannot be defended when a family challenges it.

**Step 3: seats.** For the demo's 60 seats and the shares in `application.yml`:

| Category | Share | Seats |
|---|---|---|
| OBC | 27% | floor(16.2) = 16 |
| SC | 15% | floor(9.0) = 9 |
| ST | 7.5% | floor(4.5) = 4 |
| OPEN | the rest | 60 − 29 = 31 |

"Floor" means rounding **down**, so reserved seats never exceed their percentage. OPEN seats go strictly by rank to everyone, whatever their category. Then each reserved category's seats go, by rank, to candidates of that category who did not already get an OPEN seat. A high-ranking OBC candidate therefore takes an OPEN seat and leaves the OBC seat for the next OBC candidate. Everyone left is wait-listed in rank order (W1, W2, …).

**Speed.** Everything is **one** database query and one sort in memory (O(n log n)). The report measured the old N+1 version at 14.2 minutes and the corrected one at 6.1 minutes (DR-03).

**Other ways it could have been done.** Ranking inside SQL (`ORDER BY … LIMIT`) would work for step 2 but not for step 3, which needs the two passes. A "best of both" algorithm that moves candidates between OPEN and reserved seats is used by some national counselling bodies. It is more complex, and the report does not ask for it.

=== FILE backend/src/main/java/com/edumate/consent/ConsentRegistry.java
>>> SUMMARY
**Verifiable guardian consent** for applicants under 18 (NFR-07; the report calls this design element ConsentRegistry). Requirement review RR-02 (severity S1) found it missing from SRS v2.0.

**How "verifiable" works:**
1. The minor applicant fills in the guardian's name and e-mail (or phone) and presses "Send code to guardian".
2. EduMate creates a random 6-digit code, stores only its bcrypt hash, and sends the code to the **guardian's** inbox or phone through the outbox.
3. The guardian reads the message and, if they agree, tells the applicant the code.
4. The applicant types it in. If it matches, consent is GRANTED.

Only someone with access to the guardian's inbox or phone can complete step 4. That is the "verifiable" part.

**Limits:**
- the code expires after **10 minutes** (410 "This code has expired");
- after **5 wrong codes**, that code is locked (409 "Too many wrong codes");
- consent can be **revoked** at any time by the applicant or an admin, as the Act requires. After that, the application can be withdrawn or rejected but not moved forward.

**Demo mode.** With `edumate.demo.expose-otp: true` (the dev profile), the code is also returned to the browser and shown on screen, so the demo works without a real e-mail inbox. In production this setting is false, and the code is only ever in the guardian's message.

**Why 6 digits and SecureRandom?** One million possible codes and at most 5 tries gives an attacker a 5-in-a-million chance. `SecureRandom` is Java's cryptographically strong random generator. The ordinary `Random` is predictable, so someone who saw a few codes could work out the next ones.
