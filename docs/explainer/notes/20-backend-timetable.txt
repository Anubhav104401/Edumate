=== FILE backend/src/main/java/com/edumate/timetable/TimetableSolver.java
>>> SUMMARY
The **timetable algorithm** (FR-14; the report calls this design element TimetableSolver). It does two jobs: **generate** a clash-free week, and **find clashes** in any timetable. It is plain Java with no database, so the tests (`TimetableSolverTest`) can check it directly.

**Generating is like solving a Sudoku.**
- The **blanks**: every lecture that must happen this week. A 4-hour course becomes 4 lectures, so a semester of 6 courses might need about 20 lectures.
- The **values** a blank can take: the 30 weekly slots (5 days × 6 periods).
- The **rules** (constraints):
  1. a section can attend only one lecture per slot;
  2. a teacher can give only one lecture per slot, **including** lectures they already teach in other sections' published timetables;
  3. a course meets at most **once a day**, so its hours are spread over the week.

**How it searches (backtracking with "most constrained first").**
1. Look at every lecture without a slot and count its **legal** slots (slots that break no rule right now).
2. Pick the lecture with the **fewest** legal slots. This is the *minimum remaining values* (MRV) heuristic, the same idea as the DSATUR method for graph colouring: deal with the hardest blank first, while there is still room to manoeuvre.
3. Try its first legal slot, then repeat from step 1 for the remaining lectures.
4. If some lecture ends up with **no** legal slot, a choice made earlier was wrong. **Undo** the last choice and try that lecture's next slot. Undoing and retrying is called *backtracking*.
5. When every lecture has a slot, the timetable is done. If every possibility has been tried, no clash-free timetable exists. After 200,000 steps the search also gives up, so a bad input can never hang the server.

**Why not simpler methods?**
- *Greedy* (place each lecture in the first free slot, never undo): fast, but it can paint itself into a corner and fail even when a solution exists.
- *Trying every combination*: 30 choices for each of about 20 lectures is 30²⁰, far more than any computer could ever check.
- *Integer programming or special solvers* (such as OR-Tools or OptaPlanner): powerful, but a large extra dependency for a problem this small. Backtracking with MRV solves a section's week in milliseconds.

**Finding clashes** is simpler. Put every lecture into three sets of "boxes": one box per (teacher, slot), one per (section, slot), one per (room, slot). Any box holding two or more lectures is a clash. This is a single pass over the lectures (O(n)).

=== FILE backend/src/main/java/com/edumate/timetable/TimetableService.java
>>> SUMMARY
The **timetable workflow** used by the timetable coordinator:

1. **Generate** a DRAFT for a section (programme + semester + section) with the solver.
2. **Adjust** it by hand if needed: move a lecture to another day, period or room.
3. **Check clashes**, both inside the draft and against other sections' **published** timetables (the same teacher or room booked twice).
4. **Publish.** This is **refused while any clash exists**, which is the expected result of test case TC-011. Publishing replaces the section's previous published timetable.

It also answers "My timetable" (a student's section, or a teacher's own lectures) and the **workload report** (lecture hours per week for each teacher).

**Why may a hand move create a clash?** Coordinators sometimes need to try an arrangement that is temporarily invalid on the way to a valid one (like moving furniture). The move is allowed, the clash is shown in red at once, and publishing stays blocked until it is fixed. Refusing every intermediate state would make hand editing painful.
