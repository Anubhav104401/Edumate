=== FILE backend/src/main/java/com/edumate/library/Book.java
>>> SUMMARY
A **title in the library catalogue**: ISBN (the book's worldwide unique number), title, author, how many copies the library owns, how many are on the shelf right now, and which campus it belongs to.

It has a `@Version` counter. Two librarians at two desks might both try to issue the **last** copy at the same moment. Both read "1 available", both subtract one… The second save then finds that the version has changed and is refused (409), so the book can never be issued twice or reach −1 copies. This is the same *optimistic locking* used for marks and attendance (DR-01).

>>> 64-68
`returnCopy`: one copy comes back, but never more than the library owns.

=== FILE backend/src/main/java/com/edumate/notifications/NotificationMessage.java
>>> SUMMARY
**One e-mail or SMS in the outbox.** An *outbox* works like the tray on an office desk: whoever wants a letter sent puts it in the tray, and a messenger comes by regularly to take the letters to the post office. Here the "tray" is the database table `notification_outbox`, and the messenger is `NotificationDispatcher`.

Each row records the channel (EMAIL or SMS), recipient, subject, text, status (PENDING → SENT, or FAILED after 3 failed tries), how many tries so far, and a **deduplication key** that is UNIQUE in the database.

**Why an outbox instead of sending at once?**
1. **Speed and safety (DR-08).** Writing a row takes microseconds, while talking to an SMS provider can take seconds or fail. Business work (for example publishing results) is never slowed down or broken by a slow provider.
2. **All or nothing.** The row is written in the *same transaction* as the business change. If the change is undone, the message disappears with it. If it succeeds, the message is guaranteed to be sent eventually. Sending directly could send "Your results are published" even though publishing failed a moment later.
3. **Retries** happen by themselves.
>>> 59-67
A new PENDING message.
>>> 69-73
Sent successfully: status SENT, the time, and one more try counted.
>>> 75-80
A try failed: count it. After the maximum number of tries, give up (FAILED) so the message is not retried forever.

=== FILE backend/src/main/java/com/edumate/notifications/NotificationService.java
>>> SUMMARY
**The only way business code queues a message.** Every module (results, attendance shortfall, admissions, consent, payments) calls `enqueue`.

The **deduplication key** makes sure the same message is never queued twice, however many times the caller asks. Examples:
- `admission:7:SHORTLISTED:3`: application 7 reached SHORTLISTED (version 3);
- `consent-otp:12`: the code for consent record 12.

If the key already exists, `enqueue` does nothing and returns false. The database's UNIQUE rule on `dedup_key` is a second safety net.

=== FILE backend/src/main/java/com/edumate/notifications/NotificationDispatcher.java
>>> SUMMARY
**The messenger that empties the outbox** (the report's design element NotificationDispatcher). Every 5 seconds it takes up to 50 PENDING messages, oldest first, and hands each one to the gateway:
- delivered → SENT;
- refused → one more try is counted, and after 3 tries the message becomes FAILED.

The admin's **Outbox** page shows all of these with their status and tries.

**Why every 5 seconds and 50 at a time?** Messages are not urgent to the second, and a small batch keeps each run short. If 11,400 result messages are queued at once, they drain steadily over a few minutes without overloading the provider. A real provider's rate limit would set these numbers.
>>> 26
At most 3 tries per message.
>>> 32-36
Constructor: the outbox repository, the gateway and the clock.
>>> 38
`@Scheduled`: Spring runs this method automatically, first 10 seconds after start-up (`PT10S`), then 5 seconds (`PT5S`) after each run finishes. `PT5S` is the ISO-8601 way to write "a period of 5 seconds". `@EnableScheduling` in `EduMateApplication` switches scheduling on.
>>> 39
All changes of one run are saved together.
>>> 40-42
Fetches the 50 oldest PENDING messages.
>>> 43-46
For each one: try to send; if it works, mark it SENT with the time.
>>> 47-50
If sending threw an error: log a warning and count the failed try. One bad message does not stop the rest of the batch.

=== FILE backend/src/main/java/com/edumate/admin/AdminController.java
>>> SUMMARY
`GET /api/admin/role-matrix`: shows administrators **exactly who may call which URL**. The Role matrix page draws this as a table. The data comes from the very same `RoleMatrix` that Spring Security enforces, so the page can never show a rule different from the real one.

**A bug found while building this page.** In Spring Framework 7, `HttpMethod` (GET, POST…) is a class rather than an enum. Jackson turned it into an empty object `{}`, so the page received no method names and crashed. The fix is the small `RuleView` record, which sends the method as plain text such as `"GET"`. The frontend also got an ErrorBoundary, so a page that crashes shows a friendly message instead of a blank screen.
