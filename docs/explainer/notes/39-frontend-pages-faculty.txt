=== FILE frontend/src/pages/faculty/TakeAttendancePage.tsx
>>> SUMMARY
**A teacher marks attendance for one class meeting.**

1. The teacher picks the **course**, **section**, **date** (today or earlier, never in the future) and **period**, and presses **"Open register"** → `GET /api/attendance/sessions?courseId=…&section=A&date=2026-09-28&period=2`. The backend answers with the class list. If the register was already taken, it comes with the saved marks and a **version number**; if not, everyone starts as present.
2. Every student is a **large tile** with an avatar, name and USN. **Tap a tile to mark the student absent** (it turns red and the tick flips to a cross); tap again for present. "Mark all present" / "Mark all absent" set every tile at once. Big tiles are easier to hit than tiny checkboxes, especially on a phone in a classroom.
3. A bar **stuck to the bottom of the screen** (`position: sticky`) always shows a small ring with the share present, "27 of 30 present", and the **Save** button, so a teacher with a long list never has to scroll back to save.
4. **"Save attendance"** → `PUT /api/attendance/sessions` with every mark **and the version number that was loaded**.

**The two-teachers problem (defect DR-01 of the report).** Suppose two teachers open the same register at the same time. Teacher A saves first. Teacher B, still looking at the old version, saves second. Without protection, B's save would silently wipe out A's work. EduMate uses **optimistic locking**: the database row has a version number; a save only succeeds if the version sent is still the current one. B's save is refused with **409 STALE_UPDATE**, and this page shows a red box: "Someone else saved this register while you were editing. Your changes were not saved, so nothing was overwritten…", with a "Reload register" button. `AttendanceConcurrencyIntegrationTest` proves this on the backend.

=== FILE frontend/src/pages/faculty/MarksEntryPage.tsx
>>> SUMMARY
**Internal-assessment marks entry** for a teacher's course (requirement FR-17), and the place where test case **TC-012** (amending a mark from 18 to 22 with an audit trail) is demonstrated. Data: `GET /api/exams/marks?courseId&examSessionId`.

The teacher picks a course and an exam session; a table lists every student with the internal mark (out of 40, editable), the external mark (out of 60), the total, a coloured grade chip, and who changed the row last and when.

**Changing a mark:**
1. The teacher types a new mark. The row turns **amber** (`row-changed`), so an unsaved change is never forgotten, and a **reason box** and a **Save** button slide in on that row.
2. The page checks the mark (a number from 0 to 40) and that a reason was given.
3. `PUT /api/exams/marks/{id}` with `{ internalMarks, version, reason }`. The backend checks the teacher teaches this course, refuses changes once the results are approved or published, uses the **version** for optimistic locking (the same idea as attendance: a stale save is refused), and writes an **audit** entry with the old value, the new value and the reason.
4. The saved row replaces the old one in the table (with its new version, total, grade and "last change").

Each row saves on its own, so one mistake never blocks the others, and every change carries its own reason in the audit log.

**Locked sheets.** Once results for the course are approved or published, the backend marks the sheet `locked`: a lock icon appears in the title, an amber box explains why, and the inputs are disabled.
