=== FILE frontend/src/motion/presets.ts
>>> SUMMARY
**The shared "vocabulary of movement".** Every animation in EduMate takes its timing from these few recipes, so the whole product moves with one personality: quick to respond, soft to settle, a little springy. A designer would call this the product's **motion language**.

Two ideas from the `motion` library appear here:
- a **transition** says *how* something moves: how long, and along which curve (or as a spring with a stiffness and a damping, like a real spring);
- a **variant** is a named pose, for example `hidden = { opacity: 0, y: 18 }` (invisible and 18 pixels lower) and `show = { opacity: 1, y: 0 }`. An element given these variants animates from one pose to the other when told to.
>>> 12
`EASE_OUT`: a **cubic Bézier curve**, the four numbers that describe how speed changes over time. This one starts fast and glides to a gentle stop, which feels responsive and calm. It is the same curve as `--ease-out` in `theme.css`, so CSS and JavaScript animations match.
>>> 15
`SPRING`: a spring instead of a fixed duration. `stiffness` is how strongly it pulls towards the target (higher = snappier), `damping` how quickly the bouncing dies down, `mass` how heavy the moving thing feels. Springs are used for small things that should feel physical: the sliding menu highlight, dialogs popping in, the segmented switch.
>>> 18-20
`fadeUp`: start invisible and 18 px lower, end visible in place, over 0.6 s with `EASE_OUT`. Used by every list that appears item by item.
>>> 25-27
`staggerChildren(gap, delay)`: a parent that has no pose of its own but tells its children to start their `show` animation one after another, `gap` seconds apart, after an initial `delay`. This cascade is what makes the dashboard tiles appear left to right instead of all at once.
>>> 35-36
`pageVariants`: how a whole page arrives and leaves. It starts slightly lower, transparent and blurred…
>>> 37-41
…and **enters** by rising 14 px, fading in and sharpening, in 0.45 s.
>>> 43
Afterwards the blur filter is removed completely. A leftover `filter` (even `blur(0px)`) would quietly break any `position: fixed` element inside the page, such as the confetti canvas.
>>> 45
It **exits** in only 0.14 s (up a little, fading, blurring), so a click on the menu feels instant.

=== FILE frontend/src/motion/SmoothScroll.tsx
>>> SUMMARY
**Smooth scrolling**, using the Lenis library.

Normally one click of a mouse wheel moves the page about 100 pixels in a single jump. Lenis catches each wheel movement and **glides** the page to the same place over a few frames. That feels calmer, and it lets scroll-linked effects (the reading-progress line, the tilting preview on the welcome page, the pinned sections) move fluidly instead of in steps.

Lenis still uses the browser's **real** scrolling underneath: the scrollbar, the keyboard (Page Down, Space), "find in page" and screen readers keep working. It switches itself off for people who ask their computer for reduced motion, and it leaves touch screens with their native feel.

This file also gives two small helpers: `useScrollLock` (freeze the page while a dialog is open) and `useScrollToTop` (jump to the top when a new page opens).
>>> 16-18
`<ReactLenis root>`: one Lenis engine for the whole window (`root`), wrapped around the entire app.
>>> 19-20
Its settings. `lerp` (from `config.ts`): each frame the page moves 10% of the remaining distance, so it slows down smoothly as it arrives.
>>> 21
Lenis runs its own animation loop (`requestAnimationFrame`, the browser's once-per-screen-refresh timer).
>>> 22
Clicking a link to `#modules` on the welcome page glides there too.
>>> 23
Boxes that scroll by themselves (a wide table, the command menu's list) keep scrolling normally instead of moving the page.
>>> 24
Clicking a link stops any glide still in progress, so the new page never inherits leftover movement.
>>> 27

>>> 34

>>> 35-39

>>> 44
The Lenis engine, again.
>>> 45-47
The function given back: jump to the top at once (`immediate`, and `force` even if Lenis is stopped), or use the browser's own `scrollTo` when there is no Lenis.

=== FILE frontend/src/motion/PageTransition.tsx
>>> SUMMARY
**The animated page area.** It does the job of React Router's `<Outlet />` (draw the current page inside the layout), but animates every change of page: the old page fades out quickly, the window jumps to the top, and the new page rises into place (the recipes are `pageVariants` in `presets.ts`).

**The tricky part.** `AnimatePresence` keeps the *old* page on screen for its short exit animation after the address has already changed. During those 140 milliseconds React Router already thinks the *new* page is current, so if the old page asked "what should I draw?" it would draw the new page twice. The `Frozen` helper solves this: each page remembers the element it was first given and keeps drawing exactly that.

The page is also wrapped in the `ErrorBoundary` (a crash shows a friendly message, not a blank screen) and a `Suspense` boundary (while a lazily loaded page's code is still downloading, a skeleton shows instead).
>>> 19
`useOutlet()`: the element of the current child page, as a value we can keep.
>>> 20
The "jump to the top" function from `SmoothScroll.tsx`.
>>> 22-23
`AnimatePresence mode="wait"`: when the page changes, finish the old page's exit animation **before** starting the new one's entrance. `onExitComplete` runs in between, so the new page starts at the top of the window, while the old one leaves from wherever the person had scrolled to.
>>> 24
The animated box. `key={location.pathname}` is the important part: a different address means a different key, and React treats a different key as a different element, which is what triggers the exit of the old box and the entrance of the new one. `variants`, `initial`, `animate` and `exit` name the poses from `pageVariants`.
>>> 25
The safety net, reset for every address.
>>> 27
The skeleton while a page's code downloads.
>>> 38-39
`Frozen`: `useState(children)` stores the first `children` it receives and ignores later ones (the setter is not even taken), so this page keeps drawing its own content until it has left.

=== FILE frontend/src/motion/CountUp.tsx
>>> SUMMARY
Shows a value such as `75.00%` or `Rs 62500.00` by **counting the number up from zero**, keeping the words around it. It is used on the dashboard tiles, the current CGPA and the numbers on the welcome page. Text without exactly one number (`Not yet`, `Eligible`) is shown as it is.

**Accessibility.** Screen readers are given the final value straight away in a visually hidden copy (`sr-only`); the moving copy is hidden from them (`aria-hidden`), so nobody hears "0, 1.5, 3.2, …".

**Performance.** The changing number is written directly into the page (`node.textContent = …`) about 60 times a second, **without** going through React. Asking React to redraw 60 times a second would work, but it is far more work for the same result.

=== FILE frontend/src/motion/Parallax.tsx
>>> SUMMARY
**Pointer parallax**: layers that drift with the mouse by different amounts. Near things move more than far things (like looking out of a train window), so the eye reads the difference as **depth**. The floating glass cards on the welcome and sign-in pages use it.

How it works: `usePointer()` tracks where the mouse is inside an area, as two numbers from −0.5 (left/top edge) to +0.5 (right/bottom edge). Each `<Float depth={30}>` multiplies those numbers by its depth and moves by that many pixels. A **spring** sits between the mouse and the layers, so the layers glide after the mouse with a little lag instead of jerking with every pixel.

All of this uses **motion values**: numbers that change many times a second **without** making React redraw. Only the few moving elements are updated, directly.
>>> 17-22
What `usePointer()` gives back: the smoothed `x` and `y`, and the two event handlers to put on the area that should report the mouse.
>>> 26-27
The raw pointer position, updated on every mouse movement.
>>> 28-29
The smoothed versions: springs that follow the raw values. A low `stiffness` (70) makes them lazy and floaty.
>>> 30
Whether the person asked for reduced motion.
>>> 32-34
Give back the smoothed values…
>>> 35-36
…and the mouse-move handler, which does nothing when motion is reduced.
>>> 37-39
Where is the mouse inside the area? `getBoundingClientRect()` gives the area's position and size. (mouse x − area's left edge) ÷ area's width is 0 at the left edge and 1 at the right; subtracting 0.5 makes the middle 0.
>>> 41-43

>>> 49-60
