=== FILE backend/src/main/java/com/edumate/attendance/AttendanceMath.java
>>> SUMMARY
**Pure arithmetic for attendance**: no database, no Spring, just numbers in and numbers out. Keeping it separate makes it trivial to test (`AttendanceMathTest`) and impossible to get wrong by accident somewhere else.

**The key idea: decide with whole numbers, round only for display.** "Is 18 out of 24 at least 75 %?" is answered as `18 × 100 >= 75 × 24`, i.e. `1800 >= 1800`: true, with no division and no rounding. If the code first computed 74.996 % and rounded it to 75.00 %, a student just under the line would be let through; with whole numbers that cannot happen.

**Worked example** (a course with 3 lectures a week × 16 weeks = 48 planned classes, 24 held so far, 18 attended, threshold 75 %):
- `percent(18, 24)` = 75.00;
- `meetsThreshold(18, 24, 75)` = true (exactly 75 % is enough, the fix for **DEF-019**);
- `classesCanMiss(18, 24, 48, 75)`: 24 classes remain; 75 % of 48 = 36 must be attended; 18 + 24 − 36 = **6** more classes may be missed;
- `maxAchievablePercent(18, 24, 48)` = (18 + 24) ÷ 48 = 87.50 %.
>>> 21-23
`percent`: with no class held yet there is no percentage at all, so it answers `null` (shown as "—"), not 0 % and not 100 %.
>>> 25-26
attended × 100 ÷ held, divided to exactly 2 decimals with the school rounding rule (HALF_UP: 0.005 rounds up). `BigDecimal` is Java's exact decimal number type; `double` could show 74.99999999 for 75.
>>> 30-32
`meetsThreshold`: with no class held, nobody can be short yet, so the answer is "meets".
>>> 34
The exact, inclusive comparison, in whole numbers: attended × 100 ≥ threshold × held. `(long)` makes the multiplication use 64-bit numbers so it can never overflow.
>>> 41-42
`classesCanMiss`: the classes still to come (never negative, even if more were held than planned).
>>> 43
The classes that must be attended over the whole semester: threshold % of the planned total, rounded **up** (74.4 classes means 75 must be attended).
>>> 44
What the student will have if they attend everything from now on, minus what they need. The difference is how many they can still skip; a negative answer means even perfect attendance is no longer enough.
>>> 48-51
`maxAchievablePercent`: the best percentage still possible if every remaining class is attended.
>>> 54-55
`ceilDiv(a, b)`: whole-number division that rounds **up** (7 ÷ 2 = 4). Adding `b − 1` before the normal (rounding-down) division does the trick.

=== FILE backend/src/main/java/com/edumate/attendance/AttendanceSession.java
>>> SUMMARY
**One class meeting whose attendance was taken**: course + section + date + period (e.g. CS301, section A, 28 Sep 2026, period 2), who took it and when. The present/absent marks themselves are `AttendanceRecord` rows pointing at this session.

The table also has a UNIQUE constraint on (course, section, date, period), so even two **first** saves at the same instant cannot create two sessions for one class: the second insert is refused by the database.

The `@Version` field is the fix for design defect **DR-01**: every save adds 1 to it, and Hibernate adds `WHERE version = <the number read>` to its UPDATE. === FILE backend/src/main/java/com/edumate/attendance/AttendanceCaptureService.java
>>> SUMMARY
**Teachers take and correct attendance here** (design element "AttendanceCaptureService", FR-11). Two operations:
- `loadSheet`: the register for one class meeting, with the saved marks if it was already taken, otherwise everyone present;
- `saveSheet`: store the marks, write the audit log, and queue guardian e-mails for anyone who has fallen below the minimum.

**Concurrency protection** (the fix for **DR-01**) works in two layers:
1. The browser sends back the **version number it loaded**. If the sheet has been saved by someone else since, the save is refused with **409 STALE_UPDATE** before anything is written.
2. **The audit line** records only what changed, e.g. `before: 23BTRCS007=P` → `after: 23BTRCS007=A`; for a first save it records "58/60 present".

=== FILE backend/src/main/java/com/edumate/attendance/EligibilityEvaluator.java
>>> SUMMARY
**Decides whether a student may be issued a hall ticket** for a course (design element "EligibilityEvaluator", FR-12). It encodes the **decision table** of the SQA report (Table 3.9):

| Condition / Action | R1 | R2 | R3 | R4 | R5 |
|---|---|---|---|---|---|
| Attendance ≥ 75 % | Y | N | Y | N | Y |
| Fee fully paid | Y | Y | N | N | Y |
| Internal assessment complete | Y | Y | Y | Y | N |
| Medical exemption approved | N | Y | N | N | N |
| **Issue hall ticket** | **Yes** | **Yes** | No | No | No |

**The table lists 5 of the 16 possible combinations** of four yes/no conditions. The code does not only look the case up in the table (that would leave 11 cases undecided); it applies **three independent checks** that cover all 16, and then also reports which table rule the case matched ("derived" if none). So every decision is complete **and** traceable to the report.

The three checks, each adding a reason when it fails:
1. fee not paid → "Fee dues";
2. attendance short **and** no medical exemption → "Attendance shortfall";
3. assessment not complete → "Assessment pending".

Eligible means no reasons. `EligibilityEvaluatorTest` runs the report's test cases TC-008 to TC-010 against it, including the 75.00 % boundary (DEF-019).
