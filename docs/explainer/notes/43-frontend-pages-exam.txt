=== FILE frontend/src/pages/faculty/MarksEntryPage.tsx
>>> SUMMARY
**Internal-assessment marks entry** for a teacher's course (FR-17), and the place where **TC-012** (amending 18 to 22 with an audit trail) is demonstrated.

The teacher chooses a course and an exam session. The sheet lists every student with the internal mark (editable, 0–40), the external mark (read-only; "revalued" is shown if a revaluation replaced it, RR-08), the total, the grade, who changed the mark last and when, and a "change" column.

**Changing a mark:**
1. Type the new value. A **reason** box and a Save button appear on that row only.
2. Type a reason (required; the audit log records it).
3. Save sends `PUT /api/exams/marks/<id>` with `{"internalMarks": 22, "version": 3, "reason": "IA-2 re-evaluated"}`.
4. The backend checks the **version**. If someone else saved this mark since the sheet was loaded, the answer is 409, and the teacher is asked to reload rather than silently overwriting (optimistic locking).
5. The audit log stores the old and new value (DR-04 / DEF-022).

**Locked sheets.** Once a result set is approved or published, marks can no longer change (the backend answers RESULTS_LOCKED). The page then shows an amber notice and disables the inputs.

**Why one Save per row, not one for the whole sheet?** Each change needs its own reason and its own version check, and one student's problem (for example a conflict) must not block saving the others.

=== FILE frontend/src/pages/exam/ResultsManagePage.tsx
>>> SUMMARY
**The examination superintendent's results workflow**, where the **Safety** objective (two-person approval) and **TC-015 / DEF-027** (publish exactly once) can be seen:

<pre class="block">Compute ──► Approve (person 1) ──► Approve (person 2, must be different) ──► Publish</pre>

- **Compute** (top card): choose exam session, programme and semester. If marks are missing, the backend refuses with "1 mark entries are still empty…". Otherwise it shows a toast such as "Computed 60 results: 57 passed, average SGPA 7.68."
- **Result sets** (table): each set's status, who approved it, and who published it and when. Only the **right** button is shown for each status: Approve for COMPUTED / AWAITING_SECOND_APPROVAL, Publish for APPROVED.
- If the **same** person approves twice, the backend refuses: "You gave the first approval. A second, different exam superintendent must approve."
- **Publish** asks "Are you sure?" first, because publishing is final.
- "Consolidated marks" shows the cohort's marks sheet under the table.

The page **only shows buttons**; every rule is enforced by the backend. Even if two superintendents click Publish at the same moment, only one succeeds (the atomic UPDATE).
