Viva questions and answers

Short, honest answers to questions an examiner is likely to ask. Each points to the chapter or file with the details.

About the whole system

Q. What is EduMate in one sentence?
A multi-campus web application that automates admissions, attendance, examinations and results, fees, timetables and the library for a university, built from the SQA report's design, with every defect the report found fixed and covered by an automated test.
Q. What is the architecture?
A React + TypeScript single-page application talking JSON over HTTP to a Spring Boot backend (a modular monolith), which uses PostgreSQL (H2 in development), Redis for caching, a file-system object store for scans, and an outbox for e-mail/SMS (chapter 4).
Q. Which ports are used and why only one reaches the browser?
5173 (Vite, dev), 8080 (backend), 3000 (nginx, Docker), 5432 (PostgreSQL) and 6379 (Redis), the last two only inside Docker. The browser only talks to 5173 or 3000, which forward /api to 8080, so there is one origin and no CORS configuration.
Q. Why a monolith and not microservices?
One university's system, one team: a monolith keeps "pay, credit the ledger, queue the receipt" in one database transaction. Microservices would add network failures and distributed transactions without a matching benefit at this scale.

JSON, requests and the frontend

Q. How is a JSON request created and sent?
A page calls a typed function in endpoints.ts; request() in http.ts turns the object into text with JSON.stringify, adds Content-Type, Accept and Authorization: Bearer …, and sends it with fetch. On the server, Jackson turns the text into a Java record, Bean Validation checks it, and the controller's return value is turned back into JSON by Jackson (chapter 5).
Q. How are errors shown to users?
Every backend error has one JSON shape (ApiError: status, code, message, fieldErrors). The frontend turns it into an ApiError and shows its message in a toast or a red box; field errors go under the right inputs.
Q. Where would I change the text of a button or an error?
On-screen text: frontend/src/i18n/messages.ts. Business-rule errors: the Java service that raises them. Colours: theme.css. The cookbook lists every text with its location (chapter 11).
Q. Why is the token in sessionStorage?
It survives a page refresh but disappears when the tab closes, so a forgotten login on a shared computer does not stay active. localStorage would persist; an HttpOnly cookie would bring back CSRF.

Uploads

Q. How does the file upload work?
The browser checks size, extension and the first 8 bytes, then sends a multipart/form-data body (type + file) with XMLHttpRequest for a progress bar. The server rejects anything over 5 MB before the controller, then re-checks ownership, draft status, size, the real kind by magic bytes, and whether that kind is allowed for the document. It computes SHA-256, stores the bytes under a random key with an atomic rename, saves an index record, audits the upload, and cleans up files if the transaction fails (chapter 8).
Q. Why not trust the file extension?
The name and the browser's Content-Type are chosen by the sender. A program renamed marks.pdf still starts with MZ; the magic-byte check refuses it (tested).
Q. Why not store files in the database?
It would bloat the database and slow backups. The report's architecture names an object store; the ObjectStore interface allows S3 or similar with a one-class change.
Q. What if the database fails after the file was written?
A transaction callback deletes the new file when the transaction does not commit, and old files are deleted only after a successful commit, so the disk and the database never disagree.

Correctness and concurrency

Q. How is the double-credit defect (DEF-014) prevented?
An HMAC signature on the callback, an amount check, a row lock (SELECT … FOR UPDATE), a duplicate check on the bank reference, and UNIQUE constraints on the bank reference and the ledger reference. The test delivers the callback twice and asserts one credit.
Q. How is double publication (DEF-027) prevented?
Publishing is a single conditional UPDATE (WHERE status = 'APPROVED'); the database lets exactly one succeed. The test runs two threads released by a latch at the same instant.
Q. Optimistic or pessimistic locking?
Optimistic (@Version) for human editing (marks, attendance, applications, books): no one waits, conflicts are reported. Pessimistic (row lock) for payment callbacks, which must be serialised.
Q. Why BigDecimal?
Money and GPAs need exact decimals; double cannot represent 0.1 exactly.
Q. What does two-person approval guarantee?
No single person can publish results: two different superintendents must approve, recomputing clears approvals, and marks lock after the first approval (the Safety objective).

Algorithms

Q. How are SGPA and CGPA computed?
SGPA = Σ(credits × grade point) ÷ Σ credits; CGPA adds earlier semesters as SGPA × credits; exact decimals, rounded half-up to 2 places once, at the end. TC-013 gives 138 ÷ 16 = 8.63.
Q. How does the merit list allocate seats?
Merit = 0.6 × entrance + 0.4 × qualifying; ranked with deterministic tie-breaks. Reserved seats = floor(total × share); OPEN seats go strictly by rank to everyone first, then reserved seats go by rank to remaining candidates of each category; the rest are wait-listed.
Q. How is the timetable generated?
A backtracking constraint-satisfaction search that always places the lecture with the fewest legal slots first (minimum remaining values), with a 200,000-step cap. Clashes are found by grouping lectures by teacher, section and room per slot.
Q. Complexity of the main algorithms?
Result computation: linear in the number of mark rows, with 2 queries. Merit list: O(n log n) for the sort. Clash detection: O(n). Timetable search: exponential in the worst case, but the heuristic and the small size (about 16 lectures in 30 slots) make it milliseconds in practice.

Security

Q. How are passwords stored?
bcrypt with cost 12 and a random salt; never the password itself. Unknown usernames still run a bcrypt check, so response times do not reveal which usernames exist.
Q. What is in the JWT and how is it protected?
Username, user id, name, role, campus, student id (if any), issue and expiry times, signed with HMAC-SHA256 using a server secret of at least 32 bytes. Changing any character invalidates the signature. It is readable, so it contains no secrets.
Q. Why is CSRF protection disabled?
The token travels in an Authorization header that JavaScript adds explicitly; browsers never attach it automatically, so a forged cross-site request carries no credentials.
Q. How was DEF-031 fixed so that it cannot return?
A single deny-by-default RoleMatrix (anyRequest().denyAll()) plus RoleMatrixCoverageTest, which fails the build if any controller address is missing from the matrix.
Q. How is a minor's consent verified?
A 6-digit SecureRandom code goes to the guardian's own e-mail/phone, is stored only as a bcrypt hash, expires in 10 minutes, allows 5 attempts, and can be revoked; submission requires GRANTED consent.

Quality assurance

Q. How do you know the fixes work?
64 backend tests (unit, integration through real HTTP, PostgreSQL compatibility) and 15 frontend tests, each mapped to a test case or defect in the report (chapter 12).
Q. Did you find anything wrong in the report itself?
Yes: TC-013's expected SGPA, the review-effort percentage, and the count of security findings are inconsistent (chapter 15).
Q. What are the limitations?
Smaller than the report's production system; ERP and DigiLocker not integrated; payment and SMS gateways simulated; audit log and outbox shared across campuses; tokens cannot be revoked before expiry.
