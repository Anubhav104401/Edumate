The algorithms, worked through by hand

An algorithm is a precise recipe for solving a problem. This chapter works through each of EduMate's algorithms with real numbers, so you can check every step with a pencil.

1. Grades, SGPA and CGPA (regulation R-2023)

Where: GradeScale, SgpaCalculator, used by ResultComputationService.

Step A: the grade of one course

Total = internal (out of 40) + external (out of 60). Revalued external marks replace the original ones (RR-08).

Total (out of 100)GradeGrade point
90 – 100S10

below 40, or external below 21 of 60F0

The external check comes first: 40 internal + 20.99 external = 60.99 would be a C by total, but it is an F because the external is below 21 (tested in externalMinimum).

Step B: SGPA, the semester average weighted by credits

        Σ (credits × grade point)
SGPA = ───────────────────────────
             Σ credits

Worked example (TC-013). Aarav's five courses:

CourseCreditsMarks (in + ex)GradePointCredits × point
Design and Analysis of Algorithms436 + 56 = 92S1040

SGPA = 138 ÷ 16 = 8.625 → 8.63 (rounded half-up to 2 decimals). The SQA report states 8.25 for this case; see chapter 15.

Step C: CGPA, the average over all semesters so far

        Σ over earlier semesters (SGPA × credits)  +  Σ this semester (credits × grade point)
CGPA = ───────────────────────────────────────────────────────────────────────────────────
                          all credits (earlier + this semester)

Worked example. Aarav's published history is SGPA 8.40, 8.75, 8.52, 8.90 over 20, 20, 22, 22 credits:

earlier points = 8.40×20 + 8.75×20 + 8.52×22 + 8.90×22 = 168 + 175 + 187.44 + 195.80 = 726.24
this semester  = 138 points over 16 credits
CGPA = (726.24 + 138) ÷ (84 + 16) = 864.24 ÷ 100 = 8.6424 → 8.64

Design choices

  • Exact decimals (BigDecimal): no floating-point dust such as 8.624999999.
  • Round once, at the end, half-up. Rounding each semester's contribution first could move a CGPA by 0.01, enough to cross a scholarship cut-off.
  • CGPA uses earlier SGPA × credits (the published figures), so a past semester is never silently recalculated.
  • Small methods. The report measured the original SGPA routine at cyclomatic complexity 19 (Recommendation 1). Here it is split into methods of complexity ≤ 3, each tested separately.
  • Whole cohort in two queries (DR-03): all marks of the cohort and all earlier published semesters are loaded at once, instead of one query per student. The report measured 14.2 minutes before the fix and 6.1 after.

2. Two-person approval and publishing exactly once

DRAFT ─compute─► COMPUTED ─approve(A)─► AWAITING_SECOND_APPROVAL ─approve(B ≠ A)─► APPROVED ─publish─► PUBLISHED
  • A second approval by the same person is refused (SAME_APPROVER).
  • Re-computing clears both approvals, so nobody can approve one set of numbers and publish another.
  • Changing a mark after computing sends the set back to DRAFT; after the first approval, marks are locked.
  • Publishing is one SQL statement: UPDATE result_set SET status='PUBLISHED' … WHERE id=? AND status='APPROVED'. It returns how many rows changed. When two people click at the same moment, the database runs the two UPDATEs one after the other: the first changes 1 row (and wins), and the second finds the status already PUBLISHED and changes 0 rows → "These results were already published by examsup." (DEF-027, TC-015).

3. The merit list and seat allocation

Where: MeritListGenerator.

Score

merit score = 0.60 × entrance score + 0.40 × qualifying %
example: 0.60 × 82.50 + 0.40 × 91.20 = 49.50 + 36.48 = 85.98

Ranking with deterministic tie-breaks

Sort by: merit score ↓, then entrance ↓, then qualifying % ↓, then date of birth ↑ (older first), then submission time ↑, then application number. The last key is unique, so no two applicants ever tie completely, and the list is identical every time it is generated. Complexity: one sort, O(n log n).

Seat matrix

reserved seats per category = floor(total seats × share)        (floor = round down)
OPEN seats = total − all reserved

60 seats:  OBC floor(16.2)=16   SC floor(9.0)=9   ST floor(4.5)=4   OPEN 60−29 = 31
10 seats:  OBC floor(2.7)=2     SC floor(1.5)=1   ST floor(0.75)=0  OPEN 10−3  = 7

High-ranked OBC and SC candidates (ranks 2, 4, 6) take OPEN seats on merit, which leaves the reserved seats for the next candidates of their categories. That is the standard principle: a reserved seat is never wasted on someone who already earned an open seat.

4. The timetable: a small constraint-satisfaction search

Where: TimetableSolver.

The problem. Place every lecture of a section's week in one of 30 slots (5 days × 6 periods) so that: (1) the section has one lecture per slot, (2) a teacher has one lecture per slot, including other sections' published lectures, and (3) a course meets at most once a day.

The method. Backtracking search with the "most constrained first" rule (minimum remaining values, the same idea as the DSATUR graph-colouring heuristic):

  1. For every unplaced lecture, list its currently legal slots (earliest periods first, days spread out).
  2. Choose the lecture with the fewest legal slots.
  3. Try its first legal slot; repeat from 1.
  4. If some lecture has no legal slot, undo the last choice and try that lecture's next slot.
  5. Stop when all are placed, when all options are exhausted (no timetable exists), or after 200,000 steps.

Worked example on a tiny week: 2 days × 2 periods

Course A (2 lectures, teacher T1), course B (2 lectures, teacher T2). T1 already teaches another section on Day 1, Period 1.

Start. Legal slots:  A-lecture: D2P1, D1P2, D2P2  (3; D1P1 is T1's busy slot)
                     B-lecture: D1P1, D2P1, D1P2, D2P2  (4)
Pick the fewest → an A lecture → first legal slot D2P1.
Now:  A-lecture #2: D1P2 only  (not D2: A already meets on day 2; not D1P1: T1 busy)   → 1 option
      B-lectures:   D1P1, D1P2, D2P2                                                    → 3 options
Pick the fewest → A #2 → D1P2.
Now:  B-lectures: D1P1, D2P2 (2 options each). Pick B #1 → D1P1.
Now:  B #2: D2P2 only (B already meets on day 1). Place it. Done, with no backtracking needed.

          P1      P2
Day 1     B       A
Day 2     A       B

Had we placed B first, B could have taken D1P2, leaving A no legal slot on day 1; the search would then have had to backtrack. Choosing the most constrained lecture first avoids most such dead ends.

Why not simpler or bigger methods?

  • Greedy (first free slot, never undo): fast, but can fail when a solution exists.
  • Try everything: about 3016 combinations for 16 lectures, which is impossible.
  • Integer programming or specialised solvers (OR-Tools, OptaPlanner): powerful for whole-university timetables with room capacities and preferences, but a large dependency for one section's week, which backtracking solves in milliseconds.

Clash detection: boxes

Put every lecture (the draft plus other sections' published lectures that share a teacher or room) into three kinds of box: teacher@day-period, section@day-period, room@day-period. Any box holding two or more lectures is a clash. One pass, O(n). Publishing is refused while any clash involves the draft (TC-011).

6. Payment callbacks: exactly once

Where: PaymentOrchestrator. The defect (DR-02 / DEF-014): the gateway delivered a success callback twice, and the fee was credited twice (₹62,500 paid, ₹1,25,000 credited). Four guards now stop it:

  1. Signature: HMAC-SHA256 over orderId|txnRef|status|amount with the shared secret. With the development secret, the payload ORD-81D4440CAE9D45BA|TXN000123456789|SUCCESS|62500.00 signs to a7554c0ad616b24f68cda993fd88209343bc813a41fc8a951f355e697c9dd56f. Change any character and the signature no longer matches → 400 BAD_SIGNATURE.
  2. Row lock: SELECT … FOR UPDATE on the payment, so two copies of the callback are processed one after the other, never interleaved. The amount in the callback must also equal the order's amount (otherwise 400 AMOUNT_MISMATCH).
  3. Already done? If this bank reference is already recorded on the payment → DUPLICATE_IGNORED, nothing credited. If the payment already succeeded under a different bank reference → 409 ALREADY_PAID, and the case is flagged for reconciliation in the audit log.
  4. Database uniqueness: gateway_txn_ref is UNIQUE, and the ledger's (entry_type, reference) is UNIQUE, so even a bug in steps 1–3 could not create a second credit.
delivery 1: verify ✓ → lock row → status INITIATED → mark SUCCESS, receipt RCPT-…, credit ledger, queue e-mail → PROCESSED
delivery 2: verify ✓ → lock row (waits for delivery 1 to finish) → status SUCCESS, same txnRef → DUPLICATE_IGNORED

7. Optimistic locking: the version number

09:00  Teacher X opens the marks sheet: mark #412 = 18, version 3
09:01  Teacher Y opens it too:          mark #412 = 18, version 3
09:02  Y saves 22, sending version 3 → stored version is 3 ✓ → UPDATE … SET internal=22, version=4 WHERE id=412 AND version=3
09:03  X saves 20, sending version 3 → stored version is now 4 ✗
       → 409 "This mark was changed by someone else after you opened the sheet. Reload and try again."

Two guards work together. The service first compares the version the browser sent with the stored one (the explicit check in MarksEntryService). Hibernate's @Version then adds AND version = 3 to the UPDATE itself, which catches the rare case of two saves passing the first check at the same instant. Without the version, X's save would silently overwrite Y's (the "lost update" of DR-01).

8. The admission state machine: a table lookup

Allowed moves are rows (from, action, to, role, reason required?) in AdmissionStateMachine. To move, find the row whose from and action match: none → 409; wrong role → 403; reason needed but missing → 400. The same table answers "which buttons should this person see?", so the screen and the rules can never disagree. The row ENROLLED → REVERSE_ENROLMENT → ENROLMENT_REVERSED (ADMIN, reason) is the DR-07 fix.

9. Guardian consent code

code   = SecureRandom number 0 … 999,999, written with 6 digits (42 → "000042")
stored = bcrypt(code)          (never the code itself)
check  = within 10 minutes? fewer than 5 wrong attempts? bcrypt.matches(typed, stored)?

1,000,000 possible codes and at most 5 tries give a guesser a 5-in-a-million chance.

10. The outbox

business action (same transaction) ──► INSERT notification_outbox (PENDING, dedup_key UNIQUE)
every 5 s: dispatcher takes ≤ 50 oldest PENDING ──► gateway.send ──► SENT
                                               └─ failure ──► attempts+1 ──► after 3 ──► FAILED

The deduplication key (e.g. admission:7:SHORTLISTED:3) makes queuing the same message twice impossible. Computing results never waits for an SMS provider (DR-08).
