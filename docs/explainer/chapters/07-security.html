Security: who you are, what you may do, and what can never be tampered with

Like a school exam hall At the gate, a guard checks your ID card (authentication: who are you?). Inside, a list on the wall says which room each class may enter (authorisation: what may you do?). The answer sheets are sealed so nobody can change them afterwards (integrity). A register records who entered and when (audit).

1. Passwords: stored so that even the database cannot reveal them

EduMate never stores a password. It stores a bcrypt hash:

Edumate@2026  ──bcrypt, cost 12, random salt──►  $2a$12$Q9mK…(53 more characters)
  • A hash is a one-way scramble: easy to compute from the password, practically impossible to reverse.
  • A random salt is mixed in, so two people with the same password get different hashes, and pre-computed tables of common passwords are useless.
  • Cost 12 makes each check deliberately slow (about a quarter of a second). A real user never notices; an attacker who stole the table and tries a billion guesses would need decades. (SecurityConfig line 97)

Alternatives and what they would change: plain SHA-256 or MD5 is fast, which is exactly wrong here (billions of guesses per second on a graphics card); storing passwords encrypted means whoever holds the key can read them all. Argon2 is a newer, even stronger choice, and bcrypt remains OWASP-accepted. The report's security testing (Table 3.13, category A02) inspected exactly this, and recorded no finding: bcrypt with cost 12.

Timing trick. When the username does not exist, EduMate still runs one bcrypt check against a dummy hash (line 59). Otherwise "unknown user" would answer instantly and "wrong password" slowly, and an attacker could tell which usernames exist. Both answers also have the same wording: "Invalid username or password."

2. Account lockout

After 5 wrong passwords in a row, the account is locked for 15 minutes: even the correct password gets 423 "Too many failed attempts. Your account is locked until 10:45 AM." This stops online guessing (the report's A07 finding). The counter is saved even though the login fails: @Transactional(noRollbackFor = ApiException.class). Both numbers are settings (max-failed-logins, lockout-minutes).

3. The login token (JWT)

After a successful login the backend hands out a JSON Web Token, a signed "wristband":

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJzdHVkZW50Iiwicm9sZSI6IlNUVURFTlQiLCJ1aWQiOjEyLCJjYW1wdXMiOiJKR0MiLC4uLn0 . 7mV9…
      header                                    payload (who, role, campus, expiry)                                  signature
  • The header and payload are only encoded (Base64URL), not secret: anyone can read them. Never put secrets in a token.
  • The signature is HMAC-SHA256 of header + payload with the server's secret key (at least 32 bytes, checked at start-up: line 79). Change one letter of the payload and the signature no longer matches; the test aTamperedTokenIsRejected proves it.
  • It expires after 8 hours (token-validity-hours).
  • The browser sends it on every request as Authorization: Bearer <token>.

Why a token and not a server session? With sessions, the server remembers each logged-in user in memory and gives the browser a cookie. That is simple, and allows instant logout-everywhere, but it needs shared session storage when there are several backend copies, and cookies bring CSRF risk (below). With a token, the server remembers nothing: any backend copy can check any request.

The trade-off, stated honestly: a token cannot be "taken back" before it expires. If one is stolen, it works until its expiry. Real systems reduce this with short expiry plus refresh tokens, or a revocation list. EduMate keeps 8 hours (one working day) and keeps the token only for the life of the browser tab (sessionStorage).

Other alternative: log in through the university's existing identity provider (OAuth 2 / OpenID Connect, for example Azure AD or Google Workspace). Then EduMate would not store passwords at all. That is recommended for production, but it needs the university's identity system, so it is outside this project.

4. CSRF: why it is switched off

Cross-site request forgery tricks a logged-in browser into sending a request to another site, relying on the browser automatically attaching that site's cookies. EduMate's login travels in a header that JavaScript adds explicitly; browsers never attach it automatically. So there is nothing for CSRF to ride on, and CSRF protection is disabled (line 46). If EduMate switched to cookies, CSRF protection would have to be switched back on.

5. Authorisation: the RoleMatrix, deny by default

RoleMatrix is the single, complete list of "which role may call which address", for example:

allow(GET,  "/api/fees/me",                STUDENT, GUARDIAN);
allow(POST, "/api/exams/result-sets/*/publish", EXAM_SUPERINTENDENT);
open (POST, "/api/auth/login");                                  // no login needed
…
anyRequest().denyAll();                                          // everything else: refused, for everyone

The defect it fixes (DR-06 / DEF-031). In the original design, two report addresses were missing from the matrix and quietly fell back to "any logged-in user". So a student could download the whole class's marks (TC-017). Now anything missing is refused, even for an administrator. The test RoleMatrixCoverageTest fails the build if any controller address is missing from the matrix. The administrator can see the whole matrix on the Role matrix page.

Denials are recorded. A refused request writes ACCESS_DENIED with the user and address to the audit log.

6. Object-level checks: "is this record yours?"

The RoleMatrix says a student may call /api/fees/me. It cannot say whose fees. That second check is done in the services:

  • The student's identity comes from the signed token (CurrentUser), never from a number in the URL, so it cannot be changed.
  • For records addressed by id (/api/admissions/applications/7), the service checks ownership (applicant) or campus (staff). Someone else's application answers 404, not 403, so nobody can even find out that it exists.
  • Every staff query is limited to the user's campus (multi-tenancy).

7. Input: never trusted

  • Validation: every JSON body is checked with Bean Validation rules (@NotBlank, @Email, @Size, @DecimalMax…) before any code uses it.
  • SQL injection (A03) is impossible by construction: every query uses parameters (?, :name), so typed text is always treated as data, never as SQL.
  • Uploads: real file type by magic bytes, size limits at three layers, safe names, random storage keys (chapter 8).
  • Payment callbacks come from outside without a login, so they must carry an HMAC-SHA256 signature over orderId|txnRef|status|amount made with the shared gateway secret. The comparison uses MessageDigest.isEqual, which takes the same time however many characters match, so an attacker cannot guess the signature character by character from response times.

8. Output: nothing runs that should not

  • XSS (DEF-036, reflected cross-site scripting): React always writes values as text. A name like <script>alert(1)</script> is shown as those characters and never run. EduMate never uses dangerouslySetInnerHTML.
  • Content-Security-Policy (nginx): scripts may only come from EduMate itself, so even an injected <script src="https://evil…"> is refused by the browser. frame-ancestors 'none' and X-Frame-Options: DENY stop click-jacking.
  • Downloads of uploaded documents carry Content-Security-Policy: sandbox and X-Content-Type-Options: nosniff, so a crafted PDF cannot run scripts as EduMate.
  • CSV exports: a cell starting with =, +, - or @ gets a leading ', so a spreadsheet will not run it as a formula (CSV injection).
  • Errors (A05): never a stack trace or SQL in an answer (include-stacktrace: never). Unexpected errors show only a reference number; details go to the server log. The test errorsDoNotLeakInternals checks this.

9. Children's data: guardian consent (DPDP)

The Digital Personal Data Protection Rules, 2025 require verifiable parental consent before a child's personal data is processed. The report's requirement review found this missing (RR-02). EduMate sends a 6-digit one-time code to the guardian's e-mail or phone:

  • it is generated with SecureRandom (unpredictable) and stored only as a bcrypt hash;
  • it is valid for 10 minutes, with at most 5 attempts;
  • the guardian's contact is masked everywhere (an****om);
  • consent can be revoked, after which the application can be stopped but not moved forward;
  • staff views of a minor's documents are audited.

The "demo code on screen" feature exists only because no real inbox is available in a demo; it is controlled by edumate.demo.expose-otp and must be false in production.

10. Secrets and the server itself

  • Secrets (JWT key, gateway secret, database password) come from environment variables, in Docker from a .env file that is never committed (.gitignore). docker-compose.yml refuses to start without them (${JWT_SECRET:?…}).
  • The development defaults in application.yml are marked change-me.
  • The backend container runs as an ordinary user (USER edumate), never as root.
  • Only /actuator/health and /actuator/info are exposed, and health shows no details.
