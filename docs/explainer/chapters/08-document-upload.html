The document upload system, in minute detail

An applicant must upload scanned documents: a photograph, an identity proof, marks cards, and a category certificate. This chapter follows one file from the applicant's computer to the server's disk and back to an officer's screen, naming every check, every limit, every byte format and every file involved. It then lists what can go wrong at each step, and the other designs that were possible.

Like handing a document to the admission office You pick the paper (choose a file). The clerk at the window glances at it: is it blank, too thick, the wrong kind of paper? (browser checks). You put it in an envelope with a label saying what it is (FormData). The postman carries it, and you can watch how far he has walked (progress bar). At the office, a second, stricter clerk opens it and checks everything again, fingerprints it, gives it a random locker number, locks it in the cupboard, and writes an index card (server checks, SHA-256, storage key, disk, database). Later, an officer asks for it by the index card, and the visit is written in the register (audit).

Maximum size: 5 MB (5,242,880 bytes) per file. One file per document type; uploading again replaces the previous one. Uploads are possible only while the application is a DRAFT.

Step 1: choosing the file (browser)

The box is a <div role="button"> with a hidden <input type="file"> inside. There are three ways in:

  • Click (or Enter / Space for keyboard users) calls inputRef.current.click(), which opens the operating system's file chooser. The chooser is pre-filtered by accept=".pdf,.jpg,.jpeg,.png" (or ".jpg,.jpeg,.png" for the photo). That is only a convenience filter: the person can switch it to "All files".
  • Drag over: onDragOver calls preventDefault() (without it the browser would refuse the drop) and highlights the box.
  • Drop: onDrop calls preventDefault() (otherwise the browser would leave EduMate and open the file itself) and takes event.dataTransfer.files[0].

Either way, the page now holds a File object. It knows the file's name (aadhaar.pdf), size (in bytes), type (the browser's guess from the extension) and lastModified. The bytes have not been read yet: a File is a handle to the file on disk.

Step 2: the browser's quick checks

checkFile(file, acceptedKinds) runs four checks, cheapest first, and stops at the first problem:

#CheckHowMessage (from messages.ts → upload)
1empty?file.size === 0“aadhaar.pdf” is empty.
2too big?file.size > 5 × 1024 × 1024“aadhaar.pdf” is larger than 5 MB. Please scan it at a lower resolution.
3allowed extension?lower-cased name ends with .pdf / .jpg / .jpeg / .png (only those this document accepts)“aadhaar.docx” is not an accepted file. Use PDF, JPEG or PNG.
4really that kind?reads only the first 8 bytes: file.slice(0, 8).arrayBuffer(), then compares with the magic numbers“aadhaar.pdf” does not look like a real PDF, JPEG or PNG file.

If anything is wrong, a red toast appears and nothing is sent. The whole check takes a few milliseconds, even for a 5 MB file, because only 8 bytes are read.

Step 3: packing the file into a multipart form

api.admissions.uploadDocument builds a FormData:

const form = new FormData();
form.append('type', 'ID_PROOF');     // a text part
form.append('file', file);           // a file part: the browser will stream the bytes from disk

When sent, the browser turns this into a multipart/form-data body: several parts separated by a random boundary line the browser chooses:

  • The part names type and file must match @RequestParam("type") and @RequestParam("file") in DocumentController.
  • The page does not set Content-Type itself: only the browser knows the boundary it chose. Setting the header by hand would leave the boundary out, and the server could not find the parts.
  • The Content-Type: application/pdf inside the file part is the browser's guess from the extension. The server ignores it for all decisions.

Why multipart and not JSON? JSON can only carry text, so the file would have to be converted to Base64 text, which is 33% larger (4 characters for every 3 bytes) and must be held entirely in memory on both sides. Multipart carries the raw bytes as they are, and every web server understands it.

Step 4: sending, with a progress bar

uploadWithProgress uses XMLHttpRequest rather than fetch, because fetch cannot report upload progress. While the bytes leave the computer, the browser fires xhr.upload.onprogress with loaded and total:

loaded 120,000 of 348,217  → onProgress(34) → "Uploading… 34%" and the bar at 34% width
loaded 348,217 of 348,217  → onProgress(100)

The request goes to port 5173 (or 3000), and Vite (or nginx) forwards it to the backend on port 8080. nginx allows bodies up to 6 MB (client_max_body_size 6m). Its default of 1 MB would block most scans with error 413.

Step 5: the server receives the multipart body

Tomcat, inside Spring Boot, reads the body, using the limits in application.yml:

spring.servlet.multipart.max-file-size:    5MB     ← any single file part
spring.servlet.multipart.max-request-size: 6MB     ← the whole body (file + text parts + boundaries)

Too large → Spring raises MaxUploadSizeExceededException → GlobalExceptionHandler answers 413 FILE_TOO_LARGE "The file is larger than the 5 MB limit." The controller never runs, so an oversized upload wastes as little server work as possible.

Step 6: the security guard

The JWT is checked (signature, expiry), then the RoleMatrix: allow(POST, "/api/admissions/applications/*/documents", APPLICANT). An officer, a student or an anonymous caller cannot upload at all.

Step 7: the controller

DocumentController.upload accepts only multipart/form-data (consumes = …). Spring fills its parameters:

  • CurrentUser me from the token;
  • applicationId = 7 from the address;
  • DocumentType type from the text part. "ID_PROOF" becomes the enum value; an unknown value such as "SELFIE" gives 400 BAD_PARAMETER;
  • MultipartFile file from the file part (a missing part also gives 400 BAD_PARAMETER).

The fingerprint: SHA-256

SHA-256 turns any amount of data into a 256-bit number, written as 64 hexadecimal characters. The same bytes always give the same fingerprint; changing even one byte gives a completely different one. EduMate stores the fingerprint of every upload, so anyone can later prove that the stored file is exactly the one that was uploaded, by computing its SHA-256 again. The test fingerprintIsTheStandardSha256 checks the official test value: SHA-256("abc") = ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad.

The storage key: never the person's file name

applications/7/3f2c9a1b-4d5e-4f60-a5b1-7c8d9e0f1a2b.pdf
└─ folder per application ─┘└──────── random UUID ─────────┘└ extension of the REAL kind

Why not store the file under its own name? Two people upload scan.pdf (a collision); a name like ..\..\config.yml tries to climb out of the folder (path traversal); names can reveal personal details; and a predictable name can be guessed. A random UUID has none of these problems. The extension always matches the real content: a PDF renamed .png is stored as .pdf.

The displayed name is cleaned separately by safeFilename: folders are removed, only letters, digits, spaces and ._()- are kept, it is cut to 90 characters, and the real extension is added. ..\..\evil<script>.exe becomes evilscript.pdf.

Writing to disk safely: LocalFileObjectStore

  1. Resolve the key under the storage root (./storage, or /app/storage in Docker, a named volume), clean it (normalize), and refuse it unless it is still inside the root. This is a second defence against path traversal.
  2. Create the folder storage/applications/7/ if needed.
  3. Write the bytes to a temporary upload-….part file in that folder.
  4. Rename it to the final name in one step (ATOMIC_MOVE). Anyone looking sees either no file or the complete file, never half a file, even if the server stops mid-write.

Keeping the disk and the database in step

The file is written before the transaction commits. Two things could go wrong, and both are handled with Spring's TransactionSynchronization ("call me when this transaction ends"):

SituationWithout careWhat EduMate does
The new file is written, then the transaction fails (database down, constraint violated)an orphan file on disk that nothing points todeleteObjectIfRolledBack: after the transaction, if it did not commit, the new file is deleted
Replacing a document: the old file is deleted, then the transaction failsthe old record comes back, but its file is gonedeleteObjectAfterCommit: the old file is deleted only after a successful commit
Deleting the old file after commit fails (for example, a locked file on Windows)the user sees an error although their upload workedquietlyDelete only logs a warning

Step 9: the answer, and the screen updates

The service returns a DocumentView, and Jackson writes it as JSON:

{"id":41,"type":"ID_PROOF","label":"Identity proof (Aadhaar card or passport)",
 "originalFilename":"aadhaar.pdf","contentType":"application/pdf","sizeBytes":347812,
 "sha256":"9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
 "uploadedAt":"2026-09-28T05:31:07.412Z"}

In the browser, xhr.onload sees status 200, parses the JSON, and resolves the promise. DocumentUpload shows the green toast "Identity proof (Aadhaar card or passport) uploaded.", hides the bar, clears the file input, and calls onChanged(). ApplyPage reloads the application, so the box now shows "Uploaded", the name, "339.7 KB", the time and the first 16 characters of the fingerprint. The "Still missing" list shrinks.

Viewing a document

  1. The View button calls api.admissions.downloadDocument(41) → download('/api/admissions/documents/41/content'). This must be a fetch with the token: a plain link would not send the Authorization header and would get 401.
  2. RoleMatrix: applicant, admissions officer or admin. The service then checks that the applicant owns it, or that the staff member's campus matches.
  3. If the viewer is staff, DOCUMENT_VIEWED is written to the audit log: who looked at which document of which application. These may be a minor's personal documents.
  4. The controller streams the file from disk with these headers: 
    Content-Type: application/pdf                              ← the REAL kind, found at upload time
Content-Disposition: inline; filename="aadhaar.pdf"        ← show it; use this name if saved
Content-Security-Policy: sandbox                           ← treat as untrusted content
X-Content-Type-Options: nosniff                            ← (added by Spring Security) never guess the type
  5. The browser receives the bytes as a Blob, makes a temporary blob: address for them, and opens it in a new tab with noopener. The temporary address is released after 60 seconds.

The file can only ever be PDF, JPEG or PNG, because that was decided from its bytes at upload, so the browser always opens it with its built-in PDF or image viewer, never as a web page. When the content address is opened directly, the sandbox policy adds a second wall.

Removing a document

Remove asks "Remove the uploaded identity proof (aadhaar card or passport)?", then sends DELETE /api/admissions/documents/41. The service checks that it is the applicant's own DRAFT, deletes the record, deletes the file after commit, writes DOCUMENT_DELETED, and answers 204 No Content.

After submission

Submitting requires the three required documents (AdmissionService.checkReadyToSubmit: "Upload these documents first: …"). Once the application is SUBMITTED, uploads and deletions are refused (409 NOT_DRAFT). The page shows the boxes without the drop area or Remove button. Officers see all five boxes read-only, with View only.

Tests that prove it

  • UploadSafetyTest (server): magic bytes, disguised programs, file-name cleaning, which kinds each document accepts, the SHA-256 test value.
  • AdmissionConsentIntegrationTest (server, through real HTTP): a program renamed id.pdf is refused with UNSUPPORTED_FILE; a real PNG and PDFs are accepted; submission then succeeds (with consent).
  • fileChecks.test.ts (browser): empty file, wrong extension, disguised program, PDF renamed as a photo.

Designs that were possible, and what they would change

AlternativeWhat would changeWhy not here
Keep the bytes inside the database (bytea / BLOB)One place to back up; transactions cover files too.The database grows by gigabytes; backups and queries slow down. The report's architecture names a separate object store.
Cloud object store (Amazon S3, Azure Blob, MinIO) with the same ObjectStore interfaceUnlimited, replicated storage; nothing else in EduMate changes.Needs a cloud account. The interface was designed so this is a one-class change.
Direct-to-cloud upload with pre-signed URLsLarge files bypass the backend entirely.The backend would no longer see the bytes before storage, so the magic-byte and size checks would move to a later step.
Base64 inside JSONOne uniform JSON API.33% larger, held fully in memory, no native progress.
Resumable / chunked uploads (e.g. the tus protocol)Survives a dropped mobile connection half-way.Unnecessary for files of at most 5 MB.
Trust the browser's Content-Type or the extensionSimpler code.Both are chosen by the sender: a renamed program would be accepted.
Virus scanning (e.g. ClamAV) and image re-encoding (to strip hidden data)Extra protection against malicious PDFs and images.Not part of this project; the ObjectStore step is where such a scan would be added.

The demo's placeholder documents

The 30 seeded M.Tech applications need documents without anyone uploading real scans. The seeder builds a real, valid one-page PDF by hand (header %PDF-1.4, five objects, a cross-reference table with exact byte positions) and a real PNG (a 120 × 150 blue rectangle with the person's initials), and stores them exactly as an upload would be: random key, SHA-256, index card. They pass the same magic-byte checks and open in any viewer.
