Testing and the SQA report: how we know it works

The SQA report is about quality assurance: planning, reviewing and testing so that defects are found and fixed before users see them. EduMate turns the report's findings into code and into automatic tests that prove each fix, and keep proving it every time the tests run.

Running the tests

cd backend
./mvnw test          (Windows: mvnw.cmd test)      → 64 tests, about a minute

cd frontend
npm test                                           → 15 tests, a few seconds

Maven prints Tests run: 64, Failures: 0, Errors: 0 when everything passes. A failing test prints what it expected and what it got.

What a test looks like

From SgpaCalculatorTest:

@Test
@DisplayName("TC-013: grades S, A, B, B, C over credits 4, 4, 3, 3, 2")
void tc013() {
    List<GradedCourse> courses = List.of(
            new GradedCourse(4, GradeScale.S.gradePoint()),  …  );
    assertThat(SgpaCalculator.sgpa(courses)).isEqualByComparingTo("8.63");
}

Every test has the same three parts: arrange (prepare the inputs), act (call the code), assert (check the result). If the result differs, the test fails and says so.

Why automatic tests matter for quality assurance

  • A fix without a test can quietly break again. RoleMatrixCoverageTest exists so that DEF-031 can never come back unnoticed.
  • Tests are executable specifications. The concurrency test is the definition of "publish exactly once".
  • The integration tests run through the same security filters, JSON conversion and database as real users do, so they catch mistakes in the connections between parts, not only in single parts.
