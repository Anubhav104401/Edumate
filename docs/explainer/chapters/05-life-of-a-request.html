The life of one request: from a click to the database and back

This chapter follows two real journeys through the real code, step by step. The first is logging in. The second is opening "My fees". Every step links to the line that does it.

Journey 1: logging in

Step 1: the person types and presses "Sign in" (browser)

LoginPage.handleSubmit runs. It stops the browser's old-fashioned page reload, checks that both boxes are filled, and calls login(username, password) from AuthContext, which calls api.auth.login:

request<LoginResponse>('POST', '/api/auth/login', { username, password })

Step 2: the JavaScript object becomes JSON text (browser)

In request(), the body is an ordinary JavaScript object:

{ username: "student", password: "Edumate@2026" }        ← a JavaScript object in memory

JSON.stringify(body) turns it into text that can travel over the network:

{"username":"student","password":"Edumate@2026"}         ← a string of 49 characters

and the headers are set: Content-Type: application/json ("the body is JSON") and Accept: application/json ("please answer in JSON"). There is no token yet, so no Authorization header.

Step 3: fetch sends it (browser → port 5173)

fetch('/api/auth/login', { method: 'POST', headers, body }). The address has no host, so it goes to the page's own origin: http://localhost:5173. On the wire:

POST /api/auth/login HTTP/1.1
Host: localhost:5173
Accept: application/json
Content-Type: application/json
Content-Length: 49

{"username":"student","password":"Edumate@2026"}
About passwords on the wire On localhost the request never leaves your computer. In a real deployment the site must use https, so this body is encrypted between the browser and the server.

Step 4: Vite forwards it (port 5173 → port 8080)

Vite sees the path starts with /api (vite.config.ts line 19) and sends the same request to http://localhost:8080/api/auth/login. (In Docker, nginx does the same: nginx.conf line 21.)

Step 5: Tomcat receives it (backend)

Spring Boot contains a web server, Tomcat, listening on port 8080. Tomcat reads the bytes, understands the HTTP, and hands the request to Spring.

Step 6: the security guard (Spring Security filter chain)

Before any EduMate code runs, the request passes through Spring Security, configured in SecurityConfig. The RoleMatrix says POST /api/auth/login is public (you cannot have a token before logging in), so it is let through.

Step 7: the right method is found, and JSON becomes a Java object (Jackson)

Spring's DispatcherServlet looks for a method whose mapping matches POST /api/auth/login and finds AuthController.login. Its parameter is @Valid @RequestBody LoginRequest request, so:

  1. Jackson reads the JSON text and builds a Java record: new LoginRequest("student", "Edumate@2026"). It matches JSON field names to the record's component names.
  2. Bean Validation checks the rules written on the record (@NotBlank, @Size(max = 60)). If one fails, the method never runs; instead GlobalExceptionHandler answers 400 with {"code":"VALIDATION_FAILED","fieldErrors":{"username":"Username is required."}}.
  3. If the body is not JSON at all, the answer is 400 MALFORMED_JSON, never a Java stack trace.

Step 8: the password check (service + database)

LoginAttemptService.authenticate:

  1. Finds the user by username. The repository method findByUsername becomes SQL like SELECT * FROM app_user WHERE username = ?. The ? is filled in safely, so a username like ' OR 1=1 -- is just a strange name, not an attack (no SQL injection).
  2. If the account is locked (5 failures in the last 15 minutes): 423.
  3. Compares the typed password with the stored bcrypt hash (chapter 7). Wrong → count the failure, answer 401 "Invalid username or password."
  4. Right → reset the failure counter and write LOGIN_SUCCESS to the audit log.

Step 9: the token is made

JwtTokenService.issue writes a JWT: three parts joined by dots, header.payload.signature. The payload (decoded) is:

{
  "iss": "edumate-backend",
  "sub": "student",                 ← username
  "iat": 1790575200,                ← issued at (seconds since 1 Jan 1970)
  "exp": 1790604000,                ← expires 8 hours later
  "uid": 12, "name": "Aarav Sharma", "role": "STUDENT", "campus": "JGC", "sid": 7
}

The signature is HMAC-SHA256 of the first two parts, computed with the server's secret key. Changing even one character of the payload (say "role":"ADMIN") makes the signature wrong, so the server refuses it.

Step 10: the Java answer becomes JSON (Jackson again)

The method returns new LoginResponse(token, expiresAt, me). Spring sees the method belongs to a @RestController, so Jackson writes the record as JSON: each record component becomes a field, an Instant becomes an ISO date-time text, an enum becomes its name:

HTTP/1.1 200
Content-Type: application/json

{"token":"eyJhbGciOiJIUzI1NiJ9.eyJpc3MiOi…","expiresAt":"2026-09-28T14:00:00Z",
 "user":{"id":12,"username":"student","fullName":"Aarav Sharma","role":"STUDENT","campusCode":"JGC","studentId":7}}

Step 11: back in the browser

The response travels back through Vite. In handleResponse, the status is 200 and the type is JSON, so response.json() turns the text back into a JavaScript object. AuthContext saves the token in sessionStorage and remembers the user. React notices that the state changed and redraws. The login page sees a user and navigates to the dashboard.

Journey 2: opening "My fees"

#WhereWhat happens
1browserThe student clicks "Fees" in the menu. React Router changes the address to /fees without asking the server for a page, and shows MyFeesPage.
2browserThe page's useLoad(() => api.fees.mine(), []) starts; the screen shows "Loading…".
3browserapi.fees.mine() calls request('GET', '/api/fees/me'). A GET has no body; the token is added: Authorization: Bearer eyJ….
4Vite → TomcatForwarded to port 8080, as before.
5securityThe resource-server filter reads the Bearer token, checks its signature and expiry with the secret key, and turns the claim role: STUDENT into the authority ROLE_STUDENT.
6RoleMatrixallow(GET, "/api/fees/me", STUDENT, GUARDIAN): allowed. (An accounts officer would get 403; no token at all, 401.)
7controllerFeeController.mine(CurrentUser me). The CurrentUser parameter is filled by CurrentUserArgumentResolver from the token's claims: id 12, role STUDENT, campus JGC, student id 7. The student id comes from the signed token, never from the URL, so nobody can ask for another student's fees by changing a number.
8serviceFeeAccountService.accountOf(7) loads the student, their bills, payments and ledger through repositories.
9Hibernate → databaseEach repository method becomes SQL, for example SELECT … FROM fee_demand WHERE student_id = ? ORDER BY due_date. The database returns rows, and Hibernate turns each row into a Java object (an entity).
10serviceFor each bill: paid = sum of successful payments; balance = amount − paid; status PAID / OVERDUE / DUE. All money is BigDecimal, exact to the paisa.
11JacksonThe FeeAccount record becomes JSON: {"studentId":7,"usn":"23BTRCS007","fullName":"Aarav Sharma","outstanding":62500.00,"demands":[…],"payments":[],"ledger":[…]}
12browserresponse.json() → object → useLoad stores it in data → React redraws: the amber "Amount outstanding ₹62,500.00" card, the bills table with "Pay now", the statement.

The error JSON, always the same shape

{
  "timestamp": "2026-09-28T05:12:44.120Z",
  "status": 409,
  "code": "SAME_APPROVER",
  "message": "You gave the first approval. A second, different exam superintendent must approve.",
  "path": "/api/exams/result-sets/5/approve",
  "traceId": null,
  "fieldErrors": null
}

Defined by ApiError, produced by GlobalExceptionHandler, read by toApiError. Because every error has a machine-readable code and a human message, the screens can show the message directly, and tests can check the code.

A file upload is different in one way

An upload is not JSON: the body is multipart/form-data, a format that can carry both text fields and raw file bytes. Chapter 8 follows one upload byte by byte.
