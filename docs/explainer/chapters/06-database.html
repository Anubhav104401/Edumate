The database: tables, keys, rules and transactions

All of EduMate's lasting information lives in one relational database: PostgreSQL in production, H2 (in PostgreSQL mode, in memory) on a laptop. The structure is created by one SQL file, V1__create_schema.sql, run by Flyway.

Keys: how rows point at each other

  • Almost every table has an id (its primary key): a number the database gives each new row (BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY), unique in that table. The campus table instead uses its short code (JGC) as its key, because other tables refer to campuses by code.
  • A foreign key such as mark.student_id REFERENCES student (id) says "this must be the id of an existing student". The database refuses a mark for a student who does not exist.
  • ON DELETE CASCADE (for example course_grade → student_result): deleting a student result automatically deletes its course grades. Used where the children mean nothing without their parent.

Rules the database itself enforces (and the defects they fix)

Many of the report's defects are fixed in the database, not only in Java, because the database is the last line of defence: it holds even if a future bug slips past the Java checks.

UNIQUE (student_id, course_id, exam_session_id) on marktwo mark rows for the same student, course and sessionDR-05

version BIGINT on marks, attendance, payments, applications, result sets, bookssilent overwrites by concurrent editors (optimistic locking)DR-01
dedup_key … UNIQUE on notification_outboxthe same message being queued twiceDR-08
CHECK (copies_available >= 0 AND copies_available <= copies_total) on booknegative copies or more copies than owned(library integrity)
storage_key … UNIQUE on application_documenttwo records pointing at the same stored file(upload integrity)

When one of these rules stops a write, Java receives a DataIntegrityViolationException, and GlobalExceptionHandler answers 409 "This change conflicts with data that already exists."

Data types chosen with care

  • Money: NUMERIC(12,2) in SQL, BigDecimal in Java: exact to the paisa. The alternative, floating-point (double), cannot store 0.1 exactly: 0.1 + 0.2 = 0.30000000000000004. Adding thousands of fees that way produces errors of paise.
  • Marks, SGPA, CGPA: NUMERIC(5,2) and NUMERIC(4,2), also exact.
  • Moments in time: TIMESTAMP WITH TIME ZONE, sent to browsers in UTC and shown in local time.
  • Plain dates (birth date, due date): DATE, with no time zone to shift them.
  • Statuses: short texts ('DRAFT', 'PUBLISHED') rather than numbers, so a person reading the table understands it.

Transactions: all or nothing

Like a shop counter You pay and receive the goods in one exchange. If the shopkeeper runs out of the item, you get your money back: there is never a moment where you paid but got nothing.

A transaction groups several database changes so that either all of them happen, or none do. In EduMate, every service method marked @Transactional is one transaction. For example, processing a payment callback marks the payment successful, generates the receipt, credits the ledger and queues the e-mail. If any step fails, none of them stay.

A transaction also protects files: see deleteObjectIfRolledBack in chapter 8.

The report's conclusion notes that DR-01, DR-02 and DEF-027 are "one underlying pattern: a check-then-act sequence without a lock". These three techniques are the three fixes.

Flyway: the database's own version history

On start-up, Flyway looks at flyway_schema_history. V1__create_schema.sql has not been applied yet, so it runs it and records it. On the next start it skips it. A future change would be a new file, V2__add_hostel_module.sql, which Flyway applies exactly once on every database. Existing migration files are never edited once they have run.

Looking inside the database yourself

While the backend runs in development, open http://localhost:8080/h2-console, use the JDBC URL jdbc:h2:mem:edumate, user sa, empty password, and try:

SELECT usn, full_name, section FROM student ORDER BY usn;
SELECT * FROM audit_log ORDER BY id DESC;
SELECT status, COUNT(*) FROM notification_outbox GROUP BY status;

The in-memory database is recreated, with fresh demo data, every time the backend starts.
