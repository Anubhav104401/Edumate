The new look (Release 3.0): design system, motion and scrolling

Release 3.0 redesigned every screen of EduMate. Nothing about the rules changed: the backend, the database, every check and every test are the same. What changed is how the product looks, moves and feels. This chapter explains that layer from zero: what a design system is, how colours are chosen, how animations and smooth scrolling work, how the pieces stay fast, accessible and secure, and where each thing lives in the code.

Like redecorating a school The classrooms, timetables and rules stay exactly as they were. The school gets one paint chart that every room must use (the design tokens), doors that open smoothly instead of banging (animations), signposts in every corridor (the menu, breadcrumb and command palette), ramps next to every staircase (accessibility), and a rule that nothing may be bought from an unapproved shop (the security policy).

Part 1: the design system

Design tokens: one paint chart for everything

A design token is a named value that every screen must use instead of a raw number: not #3b5bea but var(--color-primary); not 16px but var(--space-4). All tokens live in theme.css. Because every button, card, badge and chart refers to the tokens, re-branding EduMate or tuning the dark mode means editing one file. The cookbook lists every token.

Colours that know about light and dark

--color-primary: light-dark(oklch(0.52 0.2 264), oklch(0.74 0.14 262));
  • light-dark(a, b) is a CSS function: the browser uses a in light mode and b in dark mode. Both versions sit on one line, so they can never be forgotten or drift apart.
  • oklch(L C H) is a modern way to write a colour: Lightness (0–1), Chroma or colourfulness (0–0.37), Hue (an angle: 25 red, 155 green, 264 blue). It is perceptual: two colours with the same L really look equally light, whatever their hue. With hex codes or HSL that is not true (HSL's "50 % yellow" is far brighter than its "50 % blue"), so tints and text contrast become guesswork.
  • Soft backgrounds are mixed, not hand-picked: --color-good-soft: color-mix(in oklab, var(--color-good) 12%, transparent). The mix is done in the OKLab space; mixing in OKLCH was tried first and gave greyish colours a pink tint (the hue of white is undefined, and OKLCH interpolates hue), a real bug found and fixed during the redesign.
  • Which theme? color-scheme: light dark on the page lets the browser choose from the computer's setting. The theme switch overrides it by setting data-theme="light" or "dark" on <html>, which theme.css turns into color-scheme: light or dark.

The font files are installed from npm (the Fontsource packages) and bundled with the app by main.tsx. No request goes to Google Fonts. That is faster, keeps visitors' addresses private, and is required by the Content-Security-Policy (Part 5).

Depth, corners and texture

  • Shadows are layered: a tight 1 px shadow plus a wide, soft one (--shadow-card). Real objects cast both, so layered shadows look natural where a single shadow looks like a sticker.
  • Glass: the top bar and the command palette are semi-transparent with backdrop-filter: blur(18px) saturate(170%), so the page scrolling beneath shows through, softened.
  • Aurora: three large, blurred circles of brand colour that drift on slow, different loops (18–26 s) behind the dashboard banner, the login page and the welcome page. Pure CSS, no JavaScript.
  • Noise: a nearly invisible film-grain texture (an SVG feTurbulence noise pattern at 5 % opacity) over big gradients, which stops them from looking flat and prevents visible colour bands.

Colour from a name: hueFor

Avatars, course colours in the timetable, and book covers all get a colour worked out from a text (a name, a course code, a title) by hueFor in utils/visuals.ts. The text is turned into a number (a hash), and that number picks a hue on the colour wheel. The same text always gives the same colour, on every page and for every user, and nobody has to assign colours by hand. The hash is spread with the golden ratio (0.618…) so that similar texts such as CS301 and CS302 land far apart on the wheel instead of getting nearly the same colour (another bug found by looking at the timetable and fixed, with a test).

Part 2: motion

Why animate at all? When a drawer slides out, you see where it came from, so you know where to put it back. Good animation explains changes: what appeared, what went away, what is connected to what. Bad animation just makes you wait. EduMate's animations are short (0.15–0.7 s), start fast and end gently, and can all be switched off.

The motion library in one example

motion (formerly Framer Motion) lets an element describe its animation instead of programming it step by step:

<motion.div
  initial={{ opacity: 0, y: 12 }}        ← start: invisible, 12 px lower
  animate={{ opacity: 1, y: 0 }}         ← end: visible, in place
  exit={{ opacity: 0 }}                  ← when removed: fade out (inside AnimatePresence)
  transition={{ duration: 0.55, ease: EASE_OUT }}
/>

motion works out every frame in between and animates only transform and opacity, the two properties the browser can animate on the graphics card without recalculating the layout, which keeps it smooth.

One vocabulary of movement: presets.ts

All animations pick from a few recipes in motion/presets.ts, so the whole product moves with one personality:

The same curves exist for CSS in theme.css (--ease-out, and --ease-spring, a spring written with the new CSS linear() function), so CSS hovers and JavaScript animations feel alike.

Part 3: scrolling

Smooth scrolling with Lenis

A mouse wheel normally moves the page in jumps of about 100 pixels. Lenis (motion/SmoothScroll.tsx) catches each wheel movement and glides the page there over a few frames. Each frame it moves a fixed share of the remaining distance (lerp: 0.1 = 10 %), which is what makes the movement slow down softly at the end.

Crucially, Lenis still uses the browser's real scrolling underneath. Older "smooth scroll" libraries moved the whole page with a transform instead, which breaks position: sticky, Ctrl+F, anchors and screen readers. With Lenis all of those keep working. It switches itself off for "reduce motion" and leaves touch screens alone (their native scrolling is already smooth). While a dialog or the phone menu is open, the page behind is frozen with useScrollLock, which calls Lenis's stop() and start().

Scroll-driven animations in CSS

@supports (animation-timeline: view()) {                  ← only in browsers that understand it
  @media screen and (prefers-reduced-motion: no-preference) {   ← not for "reduce motion", not when printing
    .content .card, .content .stat, .content .reveal {
      animation: scroll-reveal linear both;
      animation-timeline: view();                          ← progress = where the card is in the window
      animation-range: entry 0% entry 55%;                 ← from "just entering" to "55 % entered"
    }
  }
}

Normally an animation runs over time. With animation-timeline: view() it runs over the element's journey through the window: scroll a little and the card is half-risen; scroll back and it sinks again. It runs on the browser's compositor thread, so it stays smooth even while JavaScript is busy. Browsers that do not know the feature skip the whole block (@supports) and simply show the cards, a safe fallback called progressive enhancement.

Motion values: why scroll effects do not slow React down

Scroll positions change up to 120 times a second. If each change were React state, React would redraw the page 120 times a second. motion's useScroll, useSpring and useTransform return motion values instead: containers that motion writes straight into the element's style, without React redrawing anything. React only hears about a change when a component explicitly asks (useMotionValueEvent, used by useScrolled to flip one true/false value).

Part 5: fast, accessible and secure

Speed

  • Code splitting. Each of the 26 pages is its own file, loaded the first time it is opened (lazyPage in App.tsx, React's lazy and Suspense). The welcome page's heavy scroll effects are never downloaded by a student going straight to their results.
  • Only cheap properties are animated: transform and opacity (and filter briefly on page entry, removed afterwards with transitionEnd, because a leftover filter would break position: fixed inside the page).
  • Skeletons instead of spinners, and the top loader waits 150 ms before appearing, so fast answers cause no flicker.
  • No layout jumps: skeletons have the shape of the real content; table columns and counting numbers use tabular digits (every digit equally wide), so columns line up and a number does not wobble while it counts.

Accessibility

  • Reduced motion everywhere. <MotionConfig reducedMotion="user"> in App.tsx turns every motion movement into a simple fade for people who ask their computer for less motion; CSS animations are wrapped in prefers-reduced-motion queries; Lenis, the confetti and the theme reveal switch themselves off; CountUp shows the final number at once.
  • Keyboard. Everything works without a mouse: a skip link, visible focus rings, arrow keys in menus and the palette, Escape closes dialogs, the trend chart's read-out moves with ← and →, attendance tiles are real buttons.
  • Screen readers. Radix gives dialogs and menus the right roles and moves focus into them; decorative pictures are hidden (aria-hidden); charts have a text description and every number also appears in a table; toasts and the attendance count are announced (aria-live).
  • Never colour alone. Every status has an icon or a word as well (a tick, a triangle, "Overdue"). The chart colours were checked with a colour-blindness validator for both themes.
  • Print. A @media print block hides the menus, toasts and buttons, so the hall ticket prints cleanly.

Security: living with a strict Content-Security-Policy

nginx sends every page with this policy (nginx.conf):

default-src 'self'; img-src 'self' blob: data:; style-src 'self' 'unsafe-inline';
frame-src 'self' blob:; object-src 'none'; base-uri 'self'; frame-ancestors 'none'

In words: scripts, fonts, workers and connections may only come from EduMate's own address. Even if an attacker managed to inject a <script> tag, the browser would refuse to run it. The redesign had to respect this, and three places show how:

NeedThe usual way (blocked)What EduMate does
Set the dark theme before the page is drawn (no white flash)an inline <script> in index.htmla tiny external file, public/theme-init.js, loaded from our own address
Nice fontsa <link> to Google Fontsfonts bundled with Fontsource
Confettithe library's background worker, created from a blob: addressuseWorker: false: drawn on our own canvas on the main thread

The production build was loaded in a real browser with this policy while testing the redesign: no violation was reported, the fonts loaded, the theme persisted across reloads, and the payment confetti appeared.

Part 6: how it was verified

  • npm run build: TypeScript checks every file, then Vite builds the production bundle.
  • npm test: 34 Vitest tests, including the new visuals.test.ts (colours from names, grade colours, time of day, number splitting for CountUp, the current period) and navigation.test.ts (every role's menu has icons, sections are contiguous, the longest matching address wins).
  • Every screen of every role was photographed with a scripted browser (Playwright) in light mode, dark mode and at phone width, and compared by eye.
  • A scripted interaction test clicked through the new behaviour: signed-out visitors land on /welcome, deep links go to login and back, a wrong password shows the error, Ctrl K navigates, the theme switch persists, the sidebar collapses, the account menu opens, Escape closes dialogs, and the phone drawer opens and closes.
