Decisions and alternatives: why it is built this way

Every design is a set of choices. For each important one below: what was chosen, why, what else was possible, and how the outcome would differ. Examiners often ask "why not X?", and this chapter is the answer sheet.

Architecture

DecisionChosenWhyAlternative → consequence
Overall shapeModular monolith: one backend, one database, one package per moduleSimple to run and test; cross-module work (pay → ledger → e-mail) is one transactionMicroservices → independent scaling and deployments, but network failures between services, distributed transactions for payments, and far more to operate
Frontend / backend splitReact SPA + JSON REST APINamed in the report; fast screens; the API can also serve a future mobile appServer-rendered pages → simpler, but full page reloads, and screens tied to Java code
API styleREST: resources + HTTP methods; actions as POST (/transitions, /approve, /publish)Universally understood; easy to secure address by address with the RoleMatrixGraphQL → flexible queries, but one address for everything makes the per-address RoleMatrix impossible; per-field rules would be needed
How the browser reaches the APISame origin via a proxy (Vite in dev, nginx in Docker)No CORS configuration to get wrong; identical frontend code everywhereCORS → needed if frontend and backend live on different domains; a careless wildcard exposes the API
LayersController → Service → RepositoryEach part testable alone; rules in one placeSQL in controllers → less code at first, tangled later

Data and correctness

DecisionChosenWhyAlternative → consequence
Money and GPA numbersBigDecimal / NUMERICExact decimalsdouble → 0.1 + 0.2 = 0.30000000000000004; wrong paise, GPAs off by 0.01
Schema managementFlyway SQL migrations; ddl-auto: noneExact, reviewed, repeatable schema, with CHECK and UNIQUE rulesHibernate auto-DDL → convenient, but it can silently alter production tables and cannot express every rule
Concurrent edits (marks, attendance, applications, books)Optimistic locking (@Version) + explicit version checkNo waiting; conflicts are rare and shown clearlyPessimistic locks → a teacher leaving a sheet open would block others; last-write-wins → silent data loss (DR-01)
Payment callbacksRow lock + duplicate check + UNIQUE constraintsDuplicates arrive milliseconds apart and must be serialisedOnly a Java check → the original DEF-014 double credit
Publishing resultsAtomic UPDATE … WHERE status = 'APPROVED'The database decides the single winnerRead, then write → the original DEF-027 double publication
Result computationTwo cohort-wide queries, then in-memory workRemoves the N+1 pattern (DR-03)One query per student → 14.2 minutes on the report's performance run
MessagesTransactional outbox + scheduled dispatcherBusiness work never waits for, or fails because of, an SMS provider (DR-08); retries for freeSend inside the business method → slow computations, and messages sent for work that later rolled back; a message broker (Kafka, RabbitMQ) → more power, one more system to run
AuditOne audit_log table with old and new valueDR-04: traceable changes; simple queriesDatabase triggers → capture everything, but know nothing about the user or reason; event sourcing → full history, much more complex
Multi-campusShared tables with campus_code, checked in servicesOne database to run; provisioning from settingsDatabase per campus → strongest isolation, many databases to upgrade; PostgreSQL row-level security → isolation enforced by the database, but harder to test on H2
Uploaded filesObject store behind an interface; local folder implementationDatabase stays small; cloud storage is a one-class changeFiles in the database → one backup, but a bloated database (see chapter 8)
Development databaseH2 in PostgreSQL mode + a PostgreSQL compatibility testZero installation for newcomers; real PostgreSQL still testedPostgreSQL everywhere → more realistic, every developer must run a database
CachingSpring Cache on published results; Redis in Docker; evicted on publishResults morning load; cache cannot show stale results after a publishNo cache → every student's refresh hits the database

Token storage in the browsersessionStorageSurvives refresh, gone when the tab closeslocalStorage → stays logged in on shared lab PCs; HttpOnly cookie → unreadable by scripts, but CSRF returns

Access rulesOne deny-by-default RoleMatrix + object-level checks in services + a coverage testFixes DR-06/DEF-031 and keeps it fixed@PreAuthorize on each method → rules scattered over 20 files, easy to forget one (exactly the original defect)

File typeMagic bytes, on both sidesNames and browser types are chosen by the senderExtension / Content-Type → a renamed program would be accepted

The Release 3.0 interface

DecisionChosenWhyAlternative → consequence
Animation enginemotion for anything that enters, leaves, follows the mouse or the scroll; plain CSS for hovers, loops and scroll-revealDeclarative, React-native, exit animations, shared-layout animations, springs; scroll values bypass React re-rendersGSAP → superb timelines, but imperative code beside React and a commercial-style licence history; CSS only → cannot animate an element being removed or slide a highlight between menu items
Page transitionsA "frozen" outlet inside AnimatePresence mode="wait": the old page fades out, then the new one rises inWorks with the declarative BrowserRouter; the leaving page keeps showing its own content while it fadesView Transitions API through React Router → needs React Router's data mode, a rewrite of the routing; no transition → pages jump
ScrollingLenis smooth scrolling on top of native scrollingGliding wheel scrolling while position: sticky, anchors, Ctrl+F and screen readers keep working; switched off for "reduce motion"Transform-based scrollers (Locomotive v4) → break sticky elements and accessibility; native only → steppy wheel scrolling on Windows mice
Scroll-triggered revealsCSS animation-timeline: view() for cards, motion's whileInView for staggered listsThe CSS version runs on the browser's compositor with zero JavaScript; older browsers simply show the contentIntersectionObserver in every component → more code, runs on the main thread
Dialogs, menus, tooltipsRadix UI primitives styled by app.cssFocus management, keyboard support and ARIA done correctly and tested by thousands of appsHand-written → easy to miss focus trapping or Escape; Material UI → someone else's look
Navigation for power usersCommand palette (cmdk, Ctrl K) fed by the same menu listAny page in two key presses; one source of truth for menu, palette, breadcrumb and shortcutsA search page → slower; separate lists → drift apart
ThemeLight, dark or "system", remembered; a circular reveal via the View Transitions API; set by public/theme-init.js before the first paintNo white flash on a dark-mode reload; the switch feels physicalAn inline script in index.html → blocked by the Content-Security-Policy; setting it in React → a visible flash
FontsGeist, Geist Mono and Instrument Serif, bundled with FontsourceDistinctive, very legible, variable (one file for all weights); no third-party request, CSP-friendlyGoogle Fonts link → blocked by default-src 'self', and tells Google about every visitor; system fonts → look different on every computer
Colour spaceOKLCH, mixed with color-mix(in oklab, …)Equal lightness across hues, so tints are predictable and text contrast survives re-brandingHex / HSL → "the same lightness" looks different per hue; mixing in OKLCH → can shift the hue of greys (a bug found and fixed during the redesign)
ChartsHand-made SVG (charts.tsx) following data-visualisation rules: 2 px lines, a legend for two series, a colour-blind-checked pair, a keyboard-operable read-out, and every number repeated in a tableTiny, themed, animated, accessibleRecharts / Chart.js → 100–400 kB more, harder to theme and to make keyboard-accessible
Loading statesSkeleton screens shaped like the content, plus a thin top loading bar that appears only for requests slower than 150 msFeels faster than a spinner; no flicker on fast requestsSpinners → the layout jumps when content arrives
Bundle sizeEvery page loaded on demand (React.lazy), icons imported one by oneThe first visit downloads only the shell and the current pageOne big bundle → every visitor downloads all 26 pages
Public welcome page/welcome for signed-out visitors, with the scroll showcase; deep links still go straight to loginA clear first impression and explanation of the product, without slowing down people who follow a link to a specific pageLogin as the only public page → nothing explains what EduMate is

Scope decisions (what was deliberately left out)

  • The university ERP and DigiLocker integrations named in the report are not implemented; they need external systems and credentials.
  • The payment gateway and the SMS/e-mail provider are simulated (MockPaymentGateway, LoggingNotificationGateway). Their interfaces are the same as a real integration would use, so replacing them does not change the rest of the code.
  • The code base is a working reference implementation of the core modules, much smaller than the 48,600 lines the report describes for the production system.
