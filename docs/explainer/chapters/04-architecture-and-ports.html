Port mapping "3000:80" Inside its container, nginx listens at door 80. Docker opens door 3000 on your computer and connects it to door 80 inside. So you knock on 3000, and nginx answers from 80. The database and Redis have no door opened to your computer at all: only the backend, inside Docker's private network, can reach them. That is safer.

Changing a port

  • Backend: start it with the environment variable PORT=9090; then change the proxy target in vite.config.ts ('/api': 'http://localhost:9090').
  • Frontend (dev): change port: 5173 in vite.config.ts.
  • Docker: change the left number in "3000:80" or "8080:8080" in docker-compose.yml.

Why the browser only ever talks to one port: the proxy

A browser treats http://localhost:5173 and http://localhost:8080 as two different origins (origin = scheme + host + port). For safety, a page may not read answers from another origin unless that server sends special CORS headers allowing it.

EduMate avoids the whole problem. The page calls /api/... on its own origin, and the program that served the page forwards the call to the backend:

development:  browser → http://localhost:5173/api/fees/me → Vite forwards → http://localhost:8080/api/fees/me
Docker:       browser → http://localhost:3000/api/fees/me → nginx forwards → http://backend:8080/api/fees/me

That is why API_BASE is an empty string: the same frontend code works in both set-ups, and no CORS configuration exists that could be set too loosely.

Alternative: serve the frontend and backend from different origins and configure CORS on the backend. That is common when they are hosted separately (for example the frontend on a CDN). It works, but one careless wildcard (*) can let any website call the API with a user's credentials.

Inside the backend: four layers

HTTP request
   │
   ▼
Security filter chain   ── checks the JWT and the RoleMatrix           (security/)
   │
   ▼
Controller              ── reads the URL / JSON, calls one service      (…Controller.java)
   │                        method, returns its answer as JSON
   ▼
Service                 ── the business rules and the transaction       (…Service.java, …Generator, …Registry)
   │
   ▼
Repository              ── reads and writes rows                        (…Repository.java)
   │
   ▼
Database (tables)       ── defined by Flyway (V1__create_schema.sql), mapped by entities (@Entity classes)
Like a bank The guard at the door checks your ID (security). The counter clerk takes your form (controller). The officer behind applies the bank's rules (service). The records room keeps the ledgers (repository and database). The clerk never changes a ledger directly; the officer never talks to customers.

Why layers? Each layer has one job, so it can be tested and changed alone. For example SgpaCalculator is tested without any web server or database. The alternative, putting SQL directly in controllers, is quicker for tiny programs but becomes a tangle where every change risks breaking something unrelated.

This is a modular monolith: one program, one database, but cleanly separated packages. Alternative: microservices (a separate program and database per module). That scales teams and parts independently, but every cross-module action becomes a network call that can fail half-way, and "pay a fee and credit the ledger exactly once" would need distributed transactions. For one university's system, a monolith is the simpler and safer choice.

Every page is its own JavaScript file, downloaded the first time someone opens it (code splitting), so the first visit only loads the shell and the page in front of the person. See the chapter on the new look for what each layer does.

Many campuses in one system (multi-tenancy)

The report asks for the Flexibility objective: new campuses without code changes. Each campus is a tenant with a code (JGC, CCC) listed under edumate.tenants in application.yml; TenantProvisioner creates missing ones at start-up. Programmes, students, books and users carry a campus_code. Every service compares it with the logged-in user's campus (read from the token), so a City Campus administrator (ccc.admin) never sees Jain Global Campus's students.

Alternatives: a separate database per campus (strongest isolation, but many databases to run and upgrade); or PostgreSQL row-level security (the database itself filters rows). The shared-table approach is the simplest to run and is tested in the demo. As the README says, the audit log and outbox are still shared by all campuses.
