None of these jobs is specific to a university. Every server application needs them. Writing them yourself takes months, and each hand-made version has its own bugs, especially the security and transaction parts.

Like building a house You could make your own bricks, pipes and wiring. Or you could buy tested parts that fit together and spend your time on the rooms that make this house special. Spring is the tested parts plus the builder who assembles them; EduMate's code is the rooms.

Spring Framework: the container and the integrations

Spring Framework (first released in 2003) has two big ideas:

  1. A container that builds your objects for you. You write classes that say what they need (AttendanceCaptureService needs repositories, a clock and a notifier). The container creates each object once, hands every object what it asked for, and keeps them all ready. This is called Inversion of Control and Dependency Injection (see Beans and dependency injection).
  2. Integrations that plug into the container. Web (Spring MVC), data access, transactions, security, caching, scheduling, messaging, testing. Because every integration talks to the same container, they combine: a method can be a web endpoint, run in a transaction and be cached, just by adding annotations.

Spring Boot: Spring with the set-up already done

Classic Spring was powerful but needed a lot of configuration (at first in XML) before the first request worked. Spring Boot (2014) removed that step with four ideas:

Self-check

What is the difference between Spring Framework and Spring Boot?
The Framework provides the container (dependency injection) and the integrations (MVC, transactions, data access, security hooks…). Boot sits on top and does the set-up: starters choose compatible libraries, auto-configuration creates the usual beans, an embedded server makes the application a runnable jar, and Actuator adds production features.
Why is "every server needs it" a good reason to use a framework for transactions and security?
Because these are hard to get right and easy to get subtly wrong. A framework's implementation has been tested by millions of applications; a hand-made one is tested only by yours, usually after something has gone wrong.
You find a tutorial with import javax.persistence.Entity;. What does that tell you?
It was written for Spring Boot 2 or older. Since Boot 3 the package is jakarta.persistence.

The build file, pom.xml

Maven reads pom.xml to know which libraries to download and how to build. Four parts matter.

1. The parent: tested versions for everything

Inheriting from spring-boot-starter-parent gives you a bill of materials (BOM): a list of hundreds of libraries with versions that the Spring team has tested together. That is why the dependencies below have no <version>: the parent decides. Upgrading Spring Boot means changing this one number.

2. Starters: one line per capability

A starter is an almost empty library whose only job is to depend on the right set of real libraries. spring-boot-starter-webmvc brings Spring MVC, an embedded Tomcat server and Jackson for JSON; spring-boot-starter-data-jpa brings Hibernate, Spring Data and a connection pool (HikariCP). In Spring Boot 4 the starters were split into smaller, more precise modules; that is why EduMate uses spring-boot-starter-webmvc and spring-boot-starter-flyway where older projects used spring-boot-starter-web and a plain Flyway dependency.

3. Scopes: when a library is needed

ScopeMeaningExample
(none) = compileyour code uses it directlythe starters
runtimeneeded only while running; your code never imports itthe H2 and PostgreSQL JDBC drivers: code talks to JDBC, the driver is found at run time
testonly for src/test; not packagedspring-boot-starter-test (JUnit 5, AssertJ, Mockito, MockMvc)

4. The plugin: one runnable jar

spring-boot-maven-plugin adds mvnw spring-boot:run and repackages the build into a fat jar: your classes and every library inside one file, with a small launcher that knows how to load jars nested in a jar. The result, target/edumate-backend-2.0.0.jar, runs anywhere Java runs.

Where the main class lives matters Component scanning starts at the package of the main class (com.edumate) and goes down. A class in com.edumate.fees is found; a class in com.other is silently ignored, and you get "No qualifying bean" errors. Keep the main class in the top package.

What happens when you press Run

Here is the start-up of EduMate, in order. You can see most steps in the log.

  1. Prepare the environment. Read application.yml, then the file of the active profile (application-dev.yml by default), environment variables and command-line arguments, into one set of settings.
  2. Create the application context, the container that will hold every object. Because Spring MVC is on the classpath, it is a servlet web context.
  3. Scan for your classes. Every class under com.edumate annotated with @Component, @Service, @Repository, @RestController or @Configuration becomes a bean definition: a recipe for an object. Interfaces extending JpaRepository become repository recipes.
  4. Add the auto-configurations whose conditions match: a DataSource because a JDBC driver and a URL are present, an EntityManagerFactory because JPA is present, Flyway because it is on the classpath, a JwtDecoder… unless EduMate already defined one (it did).
  5. Create every singleton bean, each after the beans it needs. The DataSource opens its pool; Flyway runs V1__create_schema.sql on the empty database; Hibernate checks the entity classes; security builds its filter chain from the RoleMatrix.
  6. Start Tomcat on port 8080 and register Spring MVC's DispatcherServlet.
  7. Log "Started EduMateApplication in … seconds". The scheduler was switched on together with the context: the outbox dispatcher runs 10 seconds after start, then every 5 seconds.
  8. Run the start-up tasks: every ApplicationRunner, in order. EduMate's TenantProvisioner creates the campuses, then DemoDataSeeder fills the demo data. Only then is the application announced as ready (an ApplicationReadyEvent).

Reading the start-up log

When start-up fails, the most useful line is usually the last "Caused by:" of the stack trace, and Spring Boot often prints an APPLICATION FAILED TO START box with a plain-English description and an Action suggestion. The troubleshooting appendix lists the common ones.

Everything else in Spring is built on one idea: you do not create your important objects; the container does, and it hands each object the others it needs. Understand this chapter well and the rest of the framework stops feeling like magic.

Inversion of Control and Dependency Injection

Like a film set An actor does not hire the camera crew or build the set. They say what they need for a scene ("a chair, a phone"), and the production team provides it before the camera rolls. In Spring, your class is the actor: its constructor lists what it needs, and the container is the production team.
  • Inversion of Control (IoC): the framework, not your code, controls when objects are created and how they are connected. You describe; it builds.
  • Dependency Injection (DI): the specific technique: an object receives the objects it depends on ("dependencies") from outside, usually through its constructor, instead of creating them itself.
  • A bean is simply an object that the Spring container creates and manages. EduMate has a few hundred: its own services, controllers and repositories, plus the ones Spring Boot creates (the data source, the JSON mapper, the security filters…).
  • The container is the ApplicationContext. SpringApplication.run creates it.

Constructor injection, in a real class

Read it as a sentence: "I am a service. To exist, I need these seven things." That is all. When Spring creates this bean it looks at the constructor, finds a bean for each parameter type (the two repositories, the student repository, CourseAccess, AuditLogger, ShortfallNotifier, Clock), creates those first if necessary, and calls the constructor.

  • No @Autowired is needed: when a class has exactly one constructor, Spring uses it.
  • Fields are final: once built, the service can never lose or swap a collaborator. That also makes it safe to share between threads (see scopes below).
  • The class does not know Spring exists. Nothing in the constructor mentions the container. A test can call new AttendanceCaptureService(...) with test doubles.
Always prefer constructor injection The older styles are field injection (@Autowired private Foo foo;) and setter injection. Field injection hides what a class needs, cannot use final, and forces tests to use reflection or Spring. Use constructor injection in application code. In test classes, field injection is fine and common: EduMate's IntegrationTestBase uses @Autowired protected MockMvc mvc;.

You cannot put @Component on java.time.Clock or on Spring Security's BCryptPasswordEncoder: they are not your classes. Instead, a @Configuration class has a method that makes the object, marked @Bean:

The method's return value becomes a bean named after the method (clock). Every class that asks for a Clock in its constructor, and there are many, receives this same object. Why not just call LocalDate.now() everywhere? Because a test can then replace this one bean with a fixed clock (Clock.fixed(...)) and get the same "today" on every run: "attendance for a future date" and "the loan is 3 days late" become testable.

Notice the check in jwtSigningKey: a secret shorter than 32 bytes stops the application at start-up with a clear message, which is far better than a security weakness discovered in production.

Under the hood: why @Configuration classes are special Spring creates a subclass of every @Configuration class at start-up (with a library called CGLIB). The subclass intercepts @Bean methods, so if one @Bean method called another (return new NimbusJwtEncoder(new ImmutableSecret<>(jwtSigningKey()))), it would still receive the one shared key instead of a new one. Passing beans as parameters, as EduMate does, avoids relying on that trick altogether; such classes can even be marked @Configuration(proxyBeanMethods = false) to skip the subclass. Spring Boot's own auto-configurations do exactly that.

Scopes: how many objects, and for how long

Singletons are shared by all requests at the same time Tomcat serves many requests in parallel, each on its own thread, and they all use the same AttendanceCaptureService object. So a singleton must be stateless: no field may hold data about one request (the current user, a running total…). Keep that data in local variables and parameters. EduMate's services only have final fields holding other beans. RoleMatrix fills its list once, in the constructor, and afterwards only reads it; rules() even hands out a copy.

A few more things you will meet

  • Bean names default to the class name with a small first letter (attendanceCaptureService) or the @Bean method name (clock).
  • ObjectProvider<T>: inject it instead of T to get the bean lazily, or only if it exists (getIfAvailable()).
  • Optional dependencies: a constructor parameter of type Optional<T> receives an empty Optional when no such bean exists.
  • Circular dependencies (A needs B, B needs A) make start-up fail. Spring Boot refuses them by default since version 2.6, because they usually signal a design problem. Break the cycle: extract the shared part into a third bean, or let one side publish an event.
  • Never fetch beans by hand with context.getBean(...) in application code (the "service locator" style). It hides dependencies just like field injection does.

Inversion of Control is the general principle that the framework controls object creation and the flow; Dependency Injection is the concrete technique of handing an object its collaborators from outside (in Spring, usually through the constructor).

When the class is not yours (a JDK or library class such as Clock, PasswordEncoder, JwtDecoder), or when creating the object needs code (reading a setting, checking a secret's length, choosing an implementation).

  4. Profile-specific files: application-docker.yml when the docker profile is active

  6. Defaults written in code

Spring MVC uses Jackson (version 3 in Spring Boot 4) to convert between JSON text and Java objects. Java records are ideal for this: their components become JSON fields, in order.

The request {"username":"student","password":"Edumate@2026"} becomes a LoginRequest; the returned LoginResponse becomes:

Three more details of the class matter:

  • A no-argument constructor, here protected: Hibernate needs it to create objects when it reads rows. protected keeps your own code from using it by accident.
  • A real constructor for the fields a new result set must have.

Entities are not records Java records are immutable and have no no-argument constructor, so they cannot be JPA entities. Use records for requests, responses and query results (EduMate does, everywhere), and ordinary classes for entities.

The persistence context: the key to understanding JPA

Inside a transaction, Hibernate keeps a persistence context: a map of every entity it has loaded or saved, by type and id. It is short-lived (usually one request's transaction) and it changes how your code behaves:

  1. Identity: loading the same row twice in one transaction returns the same object, and the second time without a query (the "first-level cache").
  2. Dirty checking: Hibernate remembers what each entity looked like when it was loaded. At the end of the transaction (or at a flush), it compares, and writes an UPDATE for every entity that changed. You never call save for a loaded entity.
  3. Write-behind: INSERTs and UPDATEs are collected and sent at flush time, not the instant you call save or change a field.

This is why EduMate's attendance correction works like this, with no "save" call for changed marks:

record.setPresent(...) only changes the Java object. Because the record was loaded in this transaction, Hibernate notices the change and writes the UPDATE itself. New records are passed to records.save(...), which makes them managed. The explicit sessions.flush() forces the pending SQL out now, so a version conflict is detected inside the request and answered with 409.

Changes to a detached entity (after its transaction ended) are not saved. That is a frequent surprise: modify objects inside the service method that runs in a transaction, not in the controller.

Relationships, and why EduMate mostly avoids them

JPA can map links between tables to object references:

Convenient (loan.getBook().getTitle()), but with costs: each reference is either loaded eagerly (always, even when not needed) or lazily (on first access, by a hidden query). Lazy loading in a loop causes the N+1 query problem (1 query for 60 students, then 60 more for their marks), and accessing a lazy reference after the transaction has ended throws LazyInitializationException.

EduMate deliberately stores ids instead (private Long bookId;, private Long examSessionId;) and loads what it needs with explicit queries, often one grouped query for a whole class (next chapter). Every database access is visible in the code. Both styles are legitimate; for a report-heavy application, explicit queries keep performance predictable.

Why spring.jpa.open-in-view: false By default Spring Boot keeps the persistence context open until the HTTP response has been written ("Open Session in View"), so lazy references work even while Jackson writes JSON in the controller. It hides N+1 problems and holds a database connection for the whole request. EduMate switches it off: all database work happens inside service methods, and controllers only receive plain records. Boot logs a warning when you leave it on without deciding; that is a hint worth following.

Seeing the SQL

Turn this on while learning. Reading the SQL that Hibernate generates is the fastest way to understand (and to catch) what your code really does to the database.

H2 in development, PostgreSQL in production

EduMate's dev profile uses an in-memory H2 database with MODE=PostgreSQL, so nothing needs to be installed; the docker profile points the same code at PostgreSQL 17. Hibernate creates the object first and then fills its fields from the row; it needs a constructor it can call without knowing the values.

It stores the position of the constant; reordering or inserting constants changes the meaning of existing rows without any error.
What is the N+1 query problem?
One query loads N parents, then accessing a lazy relationship on each parent runs one more query per parent: N+1 queries where one or two would do.

8. Transactions and concurrency: all or nothing, one at a time

Saving attendance writes a session, sixty records, an audit line and a few outbox messages. Either all of that must happen or none of it. And when two teachers save the same register at once, neither may silently destroy the other's work. This chapter covers @Transactional, rollback rules, propagation, and the two kinds of locking, with the real bugs EduMate fixed.

What a transaction guarantees

A database transaction groups statements into one unit with the ACID guarantees:

GuaranteeIn EduMate
Atomicall statements succeed, or none take effecta payment is never marked SUCCESS without its ledger credit and receipt
Consistentconstraints (UNIQUE, foreign keys, CHECK) hold after every transactionno second ledger credit for the same bank reference

@Transactional: one annotation, and the method becomes a transaction

When another bean calls publish(...), Spring:

  1. takes a connection from the pool and starts a transaction;
  2. runs your method; every repository call inside it uses that same connection and transaction;
  3. if the method returns normally: flushes pending changes and commits;
  4. if it throws an unchecked exception: rolls back, as if nothing had happened, and re-throws.

So when publish throws ApiException.conflict("NOT_APPROVED", …), any change made earlier in the method is undone, and GlobalExceptionHandler sends the 409.

Under the hood: a proxy stands in front of your bean Spring does not change your class. At start-up it wraps the bean in a proxy: an object of a generated subclass that intercepts calls to @Transactional methods, starts the transaction, calls your real method, then commits or rolls back. Other beans receive the proxy, not your object. This explains the famous trap below, and Level 4 has a whole chapter on proxies.

Read-only transactions

Many EduMate services are annotated at class level with @Transactional(readOnly = true) (AttendanceSummaryService, ReportService, DashboardService…). A class-level annotation applies to every public method. readOnly tells Hibernate it may skip dirty checking and lets the driver and database optimise; a method that must write overrides it with its own @Transactional.

Rollback rules, and when you do not want to roll back

By default Spring rolls back for unchecked exceptions (RuntimeException, Error) and commits for checked exceptions. You can change that per method. EduMate has a case where a refusal must still save something: a wrong password must increase the failed-attempts counter, even though the method then throws.

noRollbackFor = ApiException.class means: if an ApiException is thrown, commit anyway. The counter update (dirty checking on user) and the audit line are saved, then the 401 is sent. Without it the counter would be rolled back on every failure, and the lockout after five wrong passwords would never happen. ConsentRegistry.verify uses the same technique for the guardian's wrong-code counter.

Also worth noticing in that method: when the username does not exist, it still runs a bcrypt check against a dummy hash, so that "no such user" takes as long as "wrong password" and an attacker cannot discover valid usernames by timing the answers.

Propagation: transactions inside transactions

When a @Transactional method calls another @Transactional method (on another bean), what happens depends on propagation:

PropagationBehaviourUse
REQUIRED (default)join the caller's transaction if there is one, else start onealmost always: EduMate's AuditLogger.record joins the caller's transaction, so the audit line commits or rolls back with the change it describes
REQUIRES_NEWsuspend the caller's transaction and run in a new, independent onesomething that must be saved even if the caller fails, e.g. a security log line that must survive a rollback
MANDATORYmust be called inside a transaction, or failguard methods that are only meaningful as part of a bigger unit

Joined transactions roll back together If an inner REQUIRED method throws and the outer method catches the exception and carries on, the shared transaction has already been marked rollback-only, and the commit at the end fails with UnexpectedRollbackException. Catching an exception does not undo the inner method's vote.

The self-invocation trap

The proxy only sees calls that come from outside the bean. A method calling another method of the same object goes straight to the real object, and no transaction (or cache, or security check) is applied. Fixes: move runOne to another bean (the cleanest), or inject the bean's own proxy, or use TransactionTemplate in code. The same rule applies to @Cacheable, @Async and @PreAuthorize. Also: annotated methods must be public and not final.

Isolation levels, briefly

Databases let transactions see each other's committed changes in different ways (READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE). PostgreSQL's default, READ_COMMITTED, is what EduMate uses: a statement sees data committed before it started. Rather than raising the isolation level globally (slower, and more transactions fail), EduMate protects the few places that need it with the locks and conditional updates above. @Transactional(isolation = …) exists when you need it.

A @Transactional method throws a checked IOException. Is the transaction rolled back?

The failed-attempt counter and audit line are committed even though the method throws the 401 error, so the lockout works.

9. Evolving the schema with Flyway migrations

In this chapter
  1. Why not let Hibernate create the tables?
  2. How Flyway works
  3. EduMate's migration
  4. The rules of migrations

Code changes every week; the database must change with it, on every developer's laptop, in the tests, and in production, in exactly the same way and without losing data. Migrations make database changes versioned, repeatable and automatic.

Why not let Hibernate create the tables?

Hibernate can generate tables from your entities (spring.jpa.hibernate.ddl-auto: create or update). It is handy for a first prototype and dangerous afterwards:

  • update only adds; it never renames, drops, moves data or fixes a wrong type, and it guesses at column types and lengths.
  • It cannot express many database rules you want (CHECK constraints, partial indexes, precise UNIQUE combinations, ON DELETE CASCADE).
  • Nobody reviews the SQL it runs on the production database.

EduMate sets ddl-auto: none: Hibernate never touches the schema. Flyway owns it.

How Flyway works

  1. You write SQL files in src/main/resources/db/migration/, named V<version>__<description>.sql (two underscores): V1__create_schema.sql, V2__add_book_language.sql…
  2. At start-up, before Hibernate and your beans use the database, Spring Boot runs Flyway (thanks to spring-boot-starter-flyway).
  3. Flyway reads its own table, flyway_schema_history, to see which versions this database already has, and runs only the missing files, in version order, each in a transaction where the database allows it.
  4. It records each file's version, description, checksum, time and success in the history table.

The same jar therefore upgrades an empty test database from nothing to the latest version, and a year-old production database from version 7 to version 12, with no manual step.

EduMate's migration

The file creates all 24 tables. Look at how many rules live in the database itself, as a last line of defence even if the Java code had a bug:

  • REFERENCES course (id): a foreign key; a session cannot point at a course that does not exist.
  • version BIGINT NOT NULL DEFAULT 0: the column behind @Version.
  • UNIQUE (course_id, section, session_date, period): one register per class meeting, even if two first saves race.
  • ON DELETE CASCADE: deleting a session deletes its records.

gateway_txn_ref … UNIQUE means a bank reference can be stored only once: the database itself makes a double credit impossible.

Portable SQL EduMate's migration runs unchanged on H2 (development) and PostgreSQL (production): standard types, GENERATED BY DEFAULT AS IDENTITY for ids, TIMESTAMP WITH TIME ZONE for instants, NUMERIC(12,2) for money. When you need database-specific SQL, Flyway can keep separate folders per vendor (spring.flyway.locations=classpath:db/migration/{vendor}).

The rules of migrations

Never edit a migration that has run somewhere Flyway stores each file's checksum. Change V1__create_schema.sql after it has run on any shared database, and the next start-up fails with a checksum mismatch, deliberately: that database was built from the old text. Write a new file instead: V2__add_room_capacity.sql with ALTER TABLE ….
  • One change, one file, small and reviewed like code.
  • Change entities and migrations together, in the same commit. Start-up (and every integration test) runs the migrations first, so a mismatch shows up immediately.
  • Expand, then contract for changes on a live system: add the new column (V5), deploy code that writes both, copy the data (V6), deploy code that reads only the new one, drop the old column (V7). Every step is safe to roll out while the previous version is still running.
  • Data migrations are migrations too: UPDATE statements that fix or move data belong in versioned files, not in someone's SQL console.
  • Repeatable migrations, named R__description.sql, run again whenever their content changes; use them for views and stored procedures.
  • Existing databases: spring.flyway.baseline-on-migrate=true lets Flyway adopt a database that was created before Flyway was introduced.

Liquibase is the other popular tool; it does the same job with changelogs in XML, YAML or SQL and can generate rollbacks. Spring Boot supports both equally.

  2. Now change one character in V1__create_schema.sql and run ./mvnw test. Read the error, then undo the change.

Self-check

How does Flyway know which migrations a database still needs?
It reads flyway_schema_history, which lists every version already applied, and runs the newer files in order.
Why must you not edit an applied migration?
Databases that already ran it would not run it again, so they would differ from new databases. Flyway detects the edit through the checksum and refuses to start.
What does ddl-auto: none protect against?
Hibernate silently altering (or failing to correctly alter) the production schema; the schema changes only through reviewed migration files.

Security answers two questions on every request: who are you? (authentication) and may you do this? (authorisation). Spring Security answers both in a chain of filters before your controller runs. This chapter builds EduMate's security from its parts: password hashing, login, signed tokens, a role matrix that refuses everything it does not know, and checks on individual records.

The big picture

① Login   POST /api/auth/login {"username","password"}

Because the token carries everything the server needs and is verified by its signature, the server stores no session: any copy of the backend can serve any request. That is what stateless means.

From token claim to role

Spring Security represents permissions as authorities (strings). A role is simply an authority starting with ROLE_. The converter reads the token's role claim ("FACULTY") and produces the authority ROLE_FACULTY; rules written as hasRole("FACULTY") or hasAnyRole(...) add the prefix when comparing.

Issuing tokens

A JWT has three parts, each Base64url-encoded and joined by dots: a header ({"alg":"HS256"}), the claims (sub = username, exp = expiry, plus EduMate's uid, role, campus, sid) and a signature: an HMAC-SHA256 of the first two parts with the server's secret key. Anyone can read the claims (never put secrets in them), but changing a single character invalidates the signature, and the JwtDecoder refuses the token with 401.

Symmetric versus asymmetric keys EduMate signs and verifies with one shared secret (HS256), which is right when the same application does both. When a separate identity provider issues tokens (Keycloak, Azure AD, the university's single sign-on), use asymmetric keys (RS256/ES256): configure only spring.security.oauth2.resourceserver.jwt.issuer-uri, and Spring Boot fetches the provider's public keys and builds the decoder for you.

Passwords: bcrypt and lockout

The PasswordEncoder bean is new BCryptPasswordEncoder(12). Bcrypt adds a random salt to every password and is deliberately slow (cost 12 ≈ a quarter of a second): harmless for one login, crippling for an attacker trying millions of guesses from a stolen database. Never store passwords any other way, and never compare hashes with equals; use passwordEncoder.matches(raw, hash).

LoginAttemptService (see the transactions chapter) counts failures and locks the account for 15 minutes after the fifth, answering 423 Locked. Unknown usernames take as long as wrong passwords, and both get the same message, so the login form does not reveal which usernames exist.

11. Caching, background jobs and start-up tasks

In this chapter
  1. Caching with @Cacheable
  2. Scheduled jobs and the outbox pattern
  3. Running work in the background: @Async and virtual threads
  4. Start-up tasks: ApplicationRunner

Three kinds of work do not fit "one request, one answer": answers worth remembering (caching), work that should happen on a timer or later (scheduling, the outbox), and work that must happen once when the application starts (runners). Spring handles each with an annotation and an abstraction you can plug a real technology into.

Caching with @Cacheable

On results morning, thousands of students refresh "My results" again and again, and the answer does not change until the next publication. Computing it each time wastes the database. EduMate caches it:

The first call for student 7 runs the method and stores the result in the cache publishedResults under the key 7. Every later call with 7 returns the stored result without running the method. key = "#studentId" is a SpEL expression naming the parameter (by default, all parameters form the key).

A cache is only correct if it is emptied when the truth changes. Publishing new results does exactly that:

AnnotationEffect
@Cacheablereturn the cached value if present; otherwise run and store
@CacheEvictremove one key, or allEntries = true for everything in the cache (after the method, by default)
@CachePutalways run, and store the new value (refresh a key)
@Cachingseveral of the above on one method
@EnableCachingswitches the whole mechanism on (on EduMateApplication)

Where the cache lives: providers

The annotations are an abstraction; the storage is configuration. In development EduMate uses Spring's simple in-memory maps; the docker profile switches to Redis, shared by all backend copies and surviving restarts:

No Java code changes between the two. Values sent to Redis must be serialisable; by default Spring's Redis cache uses Java serialization, which is why the cached records are declared implements Serializable:

(A JSON serializer can be configured with a RedisCacheConfiguration bean; then the Serializable is unnecessary and the cached values are human-readable.) Other providers work the same way: Caffeine for a fast local cache with size limits, Hazelcast, or any JCache implementation.

Caching traps
  • Self-invocation: like @Transactional, @Cacheable works through a proxy; calling the method from the same class skips the cache.
  • Security: the key must include everything that makes the answer differ. Caching "my results" by studentId is safe because the id comes from the login token; a key that forgot the user would serve one student's results to another.
  • Staleness: every write path that changes the answer must evict, or a time-to-live must bound how old an answer may be. EduMate does both: eviction on publish and a 10-minute TTL in Redis.
  • Mutable values: with an in-memory cache, callers receive the same object; records (immutable) avoid accidental edits of the cached copy.

Scheduled jobs and the outbox pattern

The problem (design finding DR-08): computing results used to send e-mails and SMS itself. A slow or failing SMS provider then slowed down or broke the result computation, and a rollback after sending could not un-send a message.

The fix: the outbox pattern. Business code only writes a row into the notification_outbox table, in the same transaction as the business change. A separate scheduled job sends what is waiting:

  • @EnableScheduling (on the main class) activates @Scheduled methods on any bean.
  • fixedDelayString = "PT5S": 5 seconds after the previous run finished (an ISO-8601 duration). fixedRate would count from the previous start; cron = "0 0 7 * * MON-FRI" runs at 7:00 on weekdays (Spring cron has a seconds field first).
  • The message is queued only if the business transaction commits (it is part of it), and it is sent even if the provider is down for an hour: failed sends are retried up to 3 times.
  • The deduplication key (existsByDedupKey, plus a UNIQUE column) stops the same message being queued twice.
Several copies of the application Every running copy runs every @Scheduled method. With two backends, both could pick the same pending message. Solutions: lock the rows being processed (SELECT … FOR UPDATE SKIP LOCKED), use a scheduler lock library such as ShedLock, or run jobs on one designated instance. EduMate, run as one backend, keeps it simple and notes the limit.

Running work in the background: @Async and virtual threads

@EnableAsync plus @Async on a method makes callers return immediately while the method runs on another thread (returning void or a CompletableFuture). It is useful for work the user need not wait for, but it is not durable: if the application stops, the work is lost. For anything that must happen (a receipt e-mail), prefer the outbox.

Java 21's virtual threads make blocking cheap: set spring.threads.virtual.enabled=true and Tomcat, @Async and the scheduler run tasks on virtual threads, so thousands of requests waiting on the database or a slow provider no longer need thousands of expensive platform threads. The Level 4 performance chapter discusses when this helps.

Start-up tasks: ApplicationRunner

A bean implementing ApplicationRunner (or CommandLineRunner) is called once, after the context is ready and Tomcat has started. EduMate creates missing campuses from the configuration:

Adding a campus is a configuration change (edumate.tenants in the YAML), never a code change. @Order(1) makes it run before the demo seeder, which needs the campuses:

@ConditionalOnProperty means the seeder bean does not even exist unless edumate.demo.seed=true: in production it cannot run by accident. This is the same conditional mechanism Spring Boot's auto-configuration is built on (Level 4).

Runners versus events Runners are for "do this once at start-up". To react to the lifecycle more precisely, listen for events: @EventListener(ApplicationReadyEvent.class) runs when the application is fully ready to serve (after the runners). Do not put slow work in a constructor or @PostConstruct: it delays the whole start-up and runs before other beans are ready.

Self-check

What is the difference between fixedDelay and fixedRate?
fixedDelay waits the given time after the previous run finished; fixedRate starts runs at a fixed interval measured from the previous start, whatever their duration.
Why does EduMate write e-mails to an outbox table instead of sending them directly?
So a slow or failing provider cannot slow down or break the business operation, the message is queued atomically with the change it announces, and failed sends can be retried later.
What would go wrong if publishing results did not evict the publishedResults cache?
Students would keep receiving the cached, older list of results until the entries expired.
How is it guaranteed that demo data is never seeded in production?
The seeder is annotated @ConditionalOnProperty(… seed = "true"); with the property false the bean is never created, so its code cannot run.

An application that works on your laptop is half the job. In production someone must know whether it is alive, why it is slow, what went wrong at 3 a.m., and how to ship a new version safely. Spring Boot's production features cover most of this with configuration, not code.

Actuator: the application's dashboard

Health checks and orchestrators

Docker Compose, Kubernetes and load balancers ask "are you alive?" and "can you take traffic?". Spring Boot provides liveness and readiness groups (/actuator/health/liveness, /actuator/health/readiness), enabled automatically on Kubernetes. Readiness goes UP only after the ApplicationRunners have finished, so no traffic reaches a half-started instance. You can write your own indicator by implementing HealthIndicator (for example "the payment gateway is reachable").

Logging

Spring Boot logs through SLF4J (the API your code uses) with Logback underneath. EduMate's classes use it like this:

  • Levels: TRACE, DEBUG, INFO, WARN, ERROR. Set them per package in YAML (logging.level.com.edumate: DEBUG in the dev profile) or at run time through /actuator/loggers.
  • Placeholders ({}) instead of string concatenation: the message is only built if the level is enabled. Pass the exception as the last argument to get its stack trace (log.error("…", traceId, ex) in GlobalExceptionHandler).
  • Never log secrets (passwords, tokens, OTPs, full card numbers) or more personal data than needed.
  • Structured logging: logging.structured.format.console=ecs (or logstash, gelf) writes JSON lines that log platforms can search by field.
  • Correlation: EduMate's unexpected-error handler logs a short traceId and shows the same id to the user, so a support request can be matched to its log line.

Observability: metrics and traces

Logs tell you what happened to one request; metrics tell you how the whole system behaves (requests per second, 95th-percentile latency, pool usage, cache hit rate); traces follow one request across services. Spring Boot instruments itself with Micrometer:

  • Add micrometer-registry-prometheus and expose prometheus: Prometheus scrapes /actuator/prometheus, Grafana draws dashboards (http.server.requests per endpoint and status, hikaricp.connections.active, cache.gets…).
  • Add tracing with OpenTelemetry (Spring Boot 4 has a starter for it) and every log line carries a trace id; a tracing UI shows the time spent in each step of a request.
  • The Observation API (@Observed on a method, or Observation.createNotStarted(...)) produces a metric and a trace span from one piece of instrumentation, for your own important operations (computing results, handling a payment callback).

Packaging and running

The fat jar

./mvnw package produces one runnable jar. Run it anywhere with a JRE: java -jar edumate-backend-2.0.0.jar --spring.profiles.active=docker. Settings come from the environment (the twelve-factor way), so the same artifact goes to test and to production.

Containers

  • Two stages: a JDK image builds; a much smaller JRE image runs. Compilers and sources never reach production.
  • Dependencies first: copying pom.xml and downloading libraries before copying the code lets Docker reuse that layer when only code changes.
  • Not root: the process runs as an unprivileged user that may only write its upload folder.
  • Alternatives: ./mvnw spring-boot:build-image builds an optimised image with Cloud Native Buildpacks and no Dockerfile at all; Boot's layered jars split libraries and code into separate image layers.

Graceful shutdown

When a container is stopped, requests in progress should finish. Spring Boot enables graceful shutdown by default in recent versions: on the stop signal Tomcat stops accepting new connections and waits for active requests (spring.lifecycle.timeout-per-shutdown-phase, default 30 s), then beans are destroyed in order (pools closed, schedulers stopped).

Spring Boot's "magic" is ordinary Spring configuration, written by the Boot team, guarded by conditions, and loaded from a list inside each jar. Step 1: @EnableAutoConfiguration reads a list

@SpringBootApplication includes @EnableAutoConfiguration. At start-up it collects, from every jar on the classpath, the file

15. Inside the container: the bean lifecycle, proxies and AOP

In this chapter

  4. Aspect-oriented programming (AOP): write your own interceptor

Transactions, caching, security annotations, retries and repositories all work the same way: the container creates your object, then may wrap it in a proxy that adds behaviour around your methods. Knowing exactly when and how that happens is what lets you debug the hard cases and extend the framework yourself.

How the application context starts ("refresh")

  1. Collect bean definitions. Component scanning, @Configuration classes, @Bean methods, @Imports and the auto-configuration list are turned into BeanDefinitions: recipes, not objects yet. (This is done by a special post-processor, ConfigurationClassPostProcessor.)
  2. Run BeanFactoryPostProcessors, which may change the recipes before any bean exists (resolving ${…} placeholders, adding definitions).
  3. Register BeanPostProcessors, the hooks that will see every bean as it is created.
  4. Create every non-lazy singleton, each after its dependencies (next section).
  5. Publish ContextRefreshedEvent and start SmartLifecycle beans (the web server, schedulers).

Proxies: behaviour around your methods

A BeanPostProcessor may return a different object from the one it was given. Spring's auto-proxy creator does this for every bean that has something to add (a @Transactional method, a @Cacheable method, an aspect that matches…): it returns a proxy that holds your real object and a chain of interceptors.

Spring Data repositories are JDK proxies of your repository interfaces, backed by a generic implementation class. Ask Spring what a bean really is with AopUtils.isAopProxy(bean) or look at its class name in the debugger: ResultPublicationService$$SpringCGLIB$$0.

Everything that works through proxies shares the same rules:

  • Only calls from outside the bean go through the proxy (the self-invocation trap).
  • Only public, non-final methods of Spring-managed beans are intercepted; objects you create with new are never proxied.
  • Several features on one method become a chain of interceptors, and the order can matter (should the cache be checked before a transaction is opened?). Both default to the lowest precedence; when it matters, set it explicitly with @EnableCaching(order = …) and @EnableTransactionManagement(order = …).

Proxy-based features: @Transactional, @Cacheable/@CacheEvict, @Async, @PreAuthorize/@Secured, method validation (@Validated on a class), resilience annotations (@Retryable, @ConcurrencyLimit in Spring Framework 7), @Observed, and your own aspects.

As an application grows, the danger is not size but tangling: every module calling every other module directly, until nothing can change alone. Application events loosen the coupling inside one application, and Spring Modulith turns "we organise code by feature" into rules a test can check.

Direct calls couple modules

When a teacher saves attendance, EduMate queues guardian e-mails for students below the minimum. Today the attendance service calls the notifier directly:

That is simple and fine at this size. But notice what it means: the capture service must know that e-mails exist, when they should be sent, and must change whenever another reaction to "attendance saved" is added (update a dashboard cache, recalculate eligibility, send an analytics event…). The publisher knows all its subscribers.

Application events: announce, don't command

Spring's container is also an event bus. A bean publishes an event (any object, usually a record); every bean with a matching listener method receives it.

The attendance module no longer depends on notifications; notifications depend on attendance's event, a small public record. Adding a reaction means adding a listener, without touching the publisher.

After-commit reactions can be lost If the application crashes between the commit and the listener, an in-memory event is gone. That is why EduMate's notifications go through a database outbox written inside the transaction. Spring Modulith (below) can persist events automatically for the same reason (its "event publication registry").

A modular monolith

EduMate is one deployable application with one database, organised by feature: attendance, exam, fees, admissions, library, timetable… This is a modular monolith: the simplicity of one application (one transaction for "pay and credit the ledger", no network between modules) with the clarity of modules. The risk is that nothing enforces the modules: any class can import any other.

What is the difference between @EventListener and @TransactionalEventListener?
The first runs immediately inside the publisher's transaction; the second (by default) only after the publisher's transaction commits, so it never reacts to changes that were rolled back.
Why are events named in the past tense?
They state facts that have happened ("attendance saved"), not commands; the publisher does not decide what others do about it.
What does ApplicationModules.verify() check?
That there are no cycles between application modules and that no module reaches into another module's internal packages.

17. Performance: threads, the database, start-up and native images

In this chapter
  1. First rule: measure
  2. The request thread model and virtual threads
  3. The database is usually the bottleneck
  4. Start-up time and memory
  5. GraalVM native images

Most Spring applications are slow for a handful of reasons: too many database round trips, too few (or too many) connections, blocking on slow services, and heavy start-up. This chapter shows how to reason about each, and the newest tools: virtual threads, ahead-of-time processing and GraalVM native images.

First rule: measure

  • Metrics (Actuator + Micrometer): http.server.requests by endpoint (count, mean, max, percentiles), hikaricp.connections.pending (requests waiting for a connection), jvm.*.
  • SQL logging in development: count the queries of one request.
  • Profilers: Java Flight Recorder (built into the JDK: -XX:StartFlightRecording) or async-profiler show where time really goes.
  • Load tests (k6, Gatling, JMeter) against a production-like set-up, with realistic data volumes: EduMate's demo seeds a 60-student cohort; results morning means thousands.

The request thread model and virtual threads

Spring MVC on Tomcat is thread-per-request: each request occupies one thread until its answer is written. While that thread waits for the database or a payment gateway, it does nothing but still costs memory (a platform thread has a large stack) and Tomcat's pool has a limit (200 by default). Under load, requests queue although the CPU is idle.

Java 21's virtual threads are cheap threads managed by the JVM: millions can exist, and a virtual thread that blocks on I/O releases its carrier thread for others. One setting switches Spring Boot to them:

  • Helps when requests mostly wait (database, HTTP calls, file I/O) and you need high concurrency.
  • Does not help CPU-heavy work (EduMate's timetable solver) or a bottleneck elsewhere: if the connection pool has 10 connections, 10,000 virtual threads still get 10 queries at a time.
  • Watch for pinning: code that blocks while holding a monitor could pin the carrier thread in Java 21 (largely fixed for synchronized in Java 24). Libraries have mostly adapted; keep dependencies current.

With virtual threads, the classic Spring MVC style (simple, blocking, easy to debug) scales far enough for most applications; the next chapter compares it with reactive programming.

The database is usually the bottleneck

Round trips

A query costs a network round trip plus database work. Ten fast queries are slower than one query that fetches the same data. EduMate's rules of thumb, seen throughout this course:

  • One grouped query per screen instead of one per row (countByCourseForStudent): avoid N+1.
  • Projections into records instead of whole entities when only a few columns are needed.
  • Load related data for a whole set in one …In(ids) query (findByStudentResultIdIn), then join in memory with a map.
  • Atomic conditional updates instead of read-modify-write (publishIfApproved).
  • @Transactional(readOnly = true) for reads; open-in-view: false.
  • Cache what many users read and few change (@Cacheable on published results).

Batching writes, and an IDENTITY surprise

With hibernate.jdbc.batch_size, Hibernate groups many UPDATEs into one JDBC batch. But Hibernate cannot batch INSERTs for entities whose ids come from an IDENTITY column: it must send each insert alone to learn the generated id. EduMate's entities use IDENTITY, which is why the demo seeder inserts thousands of attendance rows with JdbcTemplate.batchUpdate instead of saving entities. For write-heavy entities, a SEQUENCE generator with an allocationSize (e.g. 50) lets Hibernate reserve ids in advance and batch the inserts.

Connection pool size

Counter-intuitively, a small pool is usually faster: a database with 4 cores does not run 100 queries at once any faster than 10; it just switches between them. HikariCP's default of 10 is a good start. Increase it only when metrics show requests waiting for connections and the database has spare capacity; and remember that every application instance has its own pool.

GraalVM native images

A native image compiles the application and the parts of the JDK and libraries it uses into one operating-system executable, ahead of time. Spring Boot supports this directly:

How it works: at build time Spring runs its AOT engine: it evaluates the conditions, creates bean definitions as generated Java code, and records which classes need reflection, proxies, resources or serialization ("runtime hints"). GraalVM then analyses everything reachable from main and leaves the rest out: the closed-world assumption.

The closed world has rules
  • Profiles and @Conditional decisions are taken at build time; a native image built for one set of conditions cannot switch beans at run time (properties can still change values).
  • Reflection, dynamic proxies and resources the analysis cannot see need hints: implement RuntimeHintsRegistrar and register it with @ImportRuntimeHints, or use @RegisterReflectionForBinding. Most Spring and popular libraries ship their hints already.
  • Builds take minutes and much memory; test on the JVM, build native in CI.
  • Peak throughput may be lower than a warmed-up JIT-compiled JVM; native shines where start-up and memory matter (serverless, scale-to-zero, many small instances, command-line tools).

For EduMate, a long-running server with a steady load, the JVM is the right default; a native build would be worth it only for, say, a serverless payment-callback handler.

Self-check

When do virtual threads improve throughput, and when do they not?
They help when requests spend most of their time blocked on I/O and concurrency is limited by threads. They do not help CPU-bound work or when another resource (the connection pool, the database) is the limit.
Why can Hibernate not batch inserts of IDENTITY-id entities?
The id is generated by the database during the insert, and Hibernate needs it immediately to manage the entity, so it must execute each insert on its own. Sequence-based ids can be reserved in advance.
What is the "closed-world assumption" of native images?
Everything the program may use must be known at build time; code reachable only through undeclared reflection or dynamic loading is left out, which is why runtime hints exist and conditions are fixed at build time.

18. Talking to other services, resilience, and reactive programming

Real systems call other systems: a payment gateway, an SMS provider, the university ERP. Calls across a network are slow, fail, and sometimes hang. This chapter covers Spring's HTTP clients, declarative HTTP interfaces, timeouts and retries, and when the reactive stack (WebFlux) is the better foundation.

Where EduMate would need a client

EduMate simulates its external systems: MockPaymentGateway builds the signed callback a bank would send and hands it straight to PaymentOrchestrator.handleCallback; LoggingNotificationGateway writes e-mails to the log. Both sit behind interfaces or clear seams, so a real integration replaces one class. Here is how that class would be written.

RestClient: the synchronous HTTP client

RestClient (Spring Framework 6.1+) is the modern replacement for RestTemplate: a fluent API, the same message converters as your controllers, and exceptions for error statuses. Inject Boot's RestClient.Builder rather than creating one yourself, so observability (metrics, tracing) and shared settings apply.

Declarative HTTP interfaces

Instead of writing the calls, declare them, the same way you declare Spring Data repositories:

Spring generates the implementation on top of RestClient. In Spring Framework 7 you register groups of such interfaces with @ImportHttpServices(group = "gateway", types = PaymentGatewayClient.class), give each group its base URL and timeouts in Spring Boot properties (the exact keys are listed under "HTTP Service Interface Clients" in the Boot reference for your version), and simply inject PaymentGatewayClient.

Resilience: timeouts, retries, limits

Every remote call needs a timeout Without one, a hanging provider holds your request thread (and, inside a transaction, a database connection) forever. Set connect and read timeouts on every client (Spring Boot has global HTTP-client timeout properties and per-group settings for HTTP interfaces), and never call a remote service while holding a database transaction open if you can avoid it. EduMate's outbox exists precisely so that e-mail sending happens outside business transactions.

Spring Framework 7 brings basic resilience into the core:

  • Retry only what is safe to repeat (idempotent operations) and only transient failures (timeouts, 5xx, not 4xx). Use increasing delays with jitter so many clients do not retry in lockstep.
  • Idempotency keys: when retrying a payment call, send the same key so the provider does not charge twice; on the receiving side, EduMate's replay-safe callback handling is the mirror image.
  • Circuit breakers and bulkheads: Resilience4j (with Spring Cloud Circuit Breaker) stops calling a failing service for a while and fails fast instead.

Spring MVC or Spring WebFlux?

Spring has two web stacks:

Spring MVC (EduMate)Spring WebFlux

EduMate, a CRUD and workflow application on a relational database with JPA, is a textbook MVC application; with virtual threads it does not give up scalability. Self-check

Why inject RestClient.Builder instead of calling RestClient.create()?
Boot's builder is pre-configured with the application's message converters and observability (metrics, tracing) and shared settings; a hand-made client misses them.
Which calls may you safely retry?
Idempotent operations (repeating them has the same effect), and only for transient failures like timeouts or 5xx errors; for non-idempotent ones, use an idempotency key understood by the other side.
Why is WebFlux a poor fit for an application built on JPA?
JPA and JDBC block the calling thread, which would stall WebFlux's small event-loop thread pool; the reactive stack needs non-blocking drivers such as R2DBC throughout.

Migrating an older application

  1. Get to the latest 3.x first (3.5), fix every deprecation warning there, and make sure the test suite is green. Deprecated APIs in one generation are usually removed in the next.
  2. If coming from Boot 2: first move to 3 (Java 17, javax.* → jakarta.*, SecurityFilterChain beans instead of WebSecurityConfigurerAdapter, requestMatchers instead of antMatchers).
  3. Use the properties migrator: add spring-boot-properties-migrator as a runtime dependency for one run; it reports and temporarily maps renamed properties at start-up. Remove it afterwards.

  5. Change the parent version, switch to the new starter names, and fix compilation: Jackson 3 packages, moved test annotations, removed deprecated APIs.

How to keep learning

  • Read the reference documentation of Spring Framework and Spring Boot. It is long, precise and excellent; read a section after each chapter of this course.
  • Read the source. In your IDE, jump into DataSourceAutoConfiguration, TransactionInterceptor, JpaRepository's implementation SimpleJpaRepository, or DispatcherServlet.doDispatch. The framework's code is readable and well commented; debugging into it is the fastest way to go from user to expert.
  • Follow the releases: the Spring blog, the "This Week in Spring" posts, and the release notes of each minor version.
  • Certify, if useful for you: the Broadcom/VMware Spring Certified Professional exam covers the container, AOP, data, transactions, MVC, security, Boot and testing: the first four levels of this course.
  • Contribute: documentation fixes and issues with small reproducible examples are welcome in the Spring projects, and are how many Spring experts started.
What "pioneer" means Not knowing every annotation, but being able to answer any "why does Spring do this?" by reasoning from a few ideas: beans and dependency injection, conditions and auto-configuration, proxies and interceptors, the persistence context, the filter chain, and transactions. Everything else in the framework is built from those.

A debugging routine that always works

  1. Read the whole message, then the last "Caused by:". Spring usually says exactly what is wrong.
  2. Turn up the logs for the suspected area: logging.level.org.springframework.web=DEBUG (request mapping), org.springframework.security=TRACE (the filter chain), org.hibernate.SQL=DEBUG (queries), org.springframework.transaction=TRACE (transaction boundaries).
  3. Ask the application about itself: --debug for the conditions report; Actuator's beans, mappings, configprops, env in development.
  4. Reproduce it in a test (MockMvc makes this quick), then fix it and keep the test.
  5. Set a breakpoint in the framework: DispatcherServlet.doDispatch, TransactionInterceptor.invoke, FilterChainProxy.doFilter. Stepping through Spring's code is how experts learn it.

Glossary

The words of the Spring world, in plain language.

TermMeaning
ActuatorSpring Boot's production endpoints: health, info, metrics, configuration, log levels.
AOP (aspect-oriented programming)Adding behaviour (timing, transactions, security) around methods chosen by a rule, without editing them. Spring does it with proxies.
AOT (ahead-of-time) processingDoing at build time what Spring normally does at start-up (evaluating conditions, creating bean definitions), for faster start-up and native images.
ApplicationContextThe Spring container: it creates, wires, holds and destroys the beans, and publishes events.
ApplicationRunnerA bean whose run method is called once after start-up.
Auto-configurationConfiguration classes shipped with Spring Boot, applied when their conditions match (a library is present, no bean of that type exists…).
BeanAn object created and managed by the Spring container.
Bean definitionThe recipe for a bean (its class, scope, dependencies), known before the bean exists.
BeanPostProcessorA hook that sees every bean after creation and may modify or wrap it (this is where proxies are made).
BOM (bill of materials)A list of library versions tested together; Spring Boot's parent POM provides one.
Component scanningSearching packages for annotated classes to turn into beans.
ConditionA test (@ConditionalOn…) deciding whether a bean or configuration applies.
Connection poolA set of open database connections lent to requests and returned (HikariCP).
ControllerA class whose methods handle HTTP requests.
CSRFCross-site request forgery: another site making the browser send a request with its cookies. Irrelevant for header-token APIs.
Dependency injection (DI)Giving an object its collaborators from outside (usually through its constructor) instead of letting it create them.
DispatcherServletSpring MVC's front controller: the one servlet that routes every request to a controller method.
Dirty checkingHibernate comparing managed entities with their loaded state and writing UPDATEs for changes, without explicit saves.
DTOData transfer object: a simple object (a record, in EduMate) shaped for a request or a response.
EntityA class mapped to a database table (@Entity).
Fat jarOne jar containing the application and all its libraries, runnable with java -jar.
Filter chainThe ordered servlet filters every request passes through; Spring Security is one of them, containing its own chain.
FlywayA tool that applies versioned SQL migration files to a database, once each, in order.
HibernateThe JPA implementation that generates SQL and manages entities.
IdempotentDoing it twice has the same effect as doing it once (a replay-safe payment callback).
Inversion of control (IoC)The framework, not your code, creates and connects the objects and calls your code.
JacksonThe JSON library Spring uses to convert objects to JSON and back (version 3 in Boot 4).
Jakarta EEThe standard Java enterprise APIs (Servlet, Persistence, Validation…), formerly Java EE (javax.* → jakarta.*).
JPAJakarta Persistence: the standard API for mapping objects to relational tables.
JPQLJPA's query language: SQL-like, written against entities and fields.
JWTJSON Web Token: signed claims (who, role, expiry) a client sends with each request.
Lazy loadingLoading related data only when first accessed, by an extra query.
Lost updateOne user's save silently overwriting another's; prevented by optimistic locking.
MicrometerThe metrics and observation library behind Spring Boot's metrics and tracing.
MockMvcA test tool that sends requests through Spring MVC and security without a network port.
Modular monolithOne deployable application divided into modules with explicit boundaries.
N+1 problemOne query for a list, then one more per element: a common performance bug.
Native imageAn executable compiled ahead of time by GraalVM: fast start, small memory, closed world.
Optimistic lockingDetecting concurrent changes at write time with a version column.
Outbox patternWriting outgoing messages to a table in the business transaction, and sending them from a separate job.
Persistence contextHibernate's per-transaction map of managed entities (identity, dirty checking, write-behind).
Pessimistic lockingLocking rows when reading them (SELECT … FOR UPDATE) so others wait.
ProfileA named set of settings and beans for an environment (dev, docker).
PropagationHow a transactional method behaves when called inside another transaction (join, new, …).
ProxyA generated object standing in front of a bean, adding behaviour around method calls.
Relaxed bindingMatching settings regardless of spelling style (jwt-secret, JWT_SECRET, jwtSecret).
RepositoryAn interface for data access whose implementation Spring Data generates.
Resource serverAn API that accepts access tokens issued by someone (in EduMate, itself).
ScopeHow many instances of a bean exist and for how long (singleton, prototype, request, session).
SecurityContextThe per-request holder of the authenticated user.
Self-invocationA method calling another method of the same object, bypassing the proxy (so its annotations do nothing).
SpELSpring Expression Language: #studentId, hasRole('ADMIN').
StarterA dependency that brings a tested set of libraries for one capability.
StatelessKeeping no per-user state on the server between requests; each request carries what is needed.
TransactionA group of database operations that succeed or fail together.
Twelve-factor appA set of practices for cloud applications, including configuration from the environment.
Virtual threadA lightweight Java thread (Java 21) that makes blocking I/O cheap at high concurrency.
