Databases with JPA: entities and the persistence context

Your objects live in memory; your data must live in a database that survives restarts and is shared by every server. This chapter explains the layers between the two, how a Java class becomes a table row, and the one concept that explains most JPA surprises: the persistence context.

Four layers, from the database up

With spring-boot-starter-data-jpa and a JDBC driver on the classpath, Spring Boot creates for you: a DataSource (a HikariCP connection pool, configured from spring.datasource.*), an EntityManagerFactory (Hibernate, scanning your @Entity classes), a transaction manager, and an implementation for every repository interface.

A connection pool is a taxi rank Opening a database connection is slow (network, login, set-up). A pool opens a few connections once and lends them out: a request takes one, uses it, and gives it back. HikariCP's default is 10 connections. More is not faster: a database works best with few busy connections, not hundreds of idle ones.

Entities are not records
Java records are immutable and have no no-argument constructor, so they cannot be JPA entities. Use records for
requests, responses and query results (EduMate does, everywhere), and ordinary classes for entities.



The persistence context: the key to understanding JPA


Inside a transaction, Hibernate keeps a persistence context: a map of every entity it has loaded or
saved, by type and id. It is short-lived (usually one request's transaction) and it changes how your code behaves:


    

  1. Identity: loading the same row twice in one transaction returns the same object, and
the second time without a query (the "first-level cache").
    2. 

  2. Dirty checking: Hibernate remembers what each entity looked like when it was loaded. At the end of
the transaction (or at a flush), it compares, and writes an UPDATE for every entity that changed.
You never call save for a loaded entity.
    3. 

  3. Write-behind: INSERTs and UPDATEs are collected and sent at flush time,
not the instant you call save or change a field.
    4. 



This is why EduMate's attendance correction works like this, with no "save" call for changed marks:




record.setPresent(...) only changes the Java object. Because the record was loaded in this transaction,
Hibernate notices the change and writes the UPDATE itself. New records are passed to
records.save(...), which makes them managed. The explicit sessions.flush() forces the
pending SQL out now, so a version conflict is detected inside the request and answered with 409.

Changes to a detached entity (after its transaction ended) are not saved. That is a
frequent surprise: modify objects inside the service method that runs in a transaction, not in the controller.



Relationships, and why EduMate mostly avoids them


JPA can map links between tables to object references:


@Entity
class BookLoan {
    @ManyToOne(fetch = FetchType.LAZY)            // many loans → one book
    @JoinColumn(name = "book_id")
    private Book book;
}
@Entity
class Book {
    @OneToMany(mappedBy = "book")                 // one book → many loans
    private List<BookLoan> loans;
}


Convenient (loan.getBook().getTitle()), but with costs: each reference is either loaded
eagerly (always, even when not needed) or lazily (on first access, by a hidden query).
Lazy loading in a loop causes the N+1 query problem (1 query for 60 students, then 60 more for their
marks), and accessing a lazy reference after the transaction has ended throws
LazyInitializationException.


EduMate deliberately stores ids instead (private Long bookId;,
private Long examSessionId;) and loads what it needs with explicit queries, often one grouped query for a
whole class (next chapter). Every database access is visible in the code. Both styles are legitimate; for a
report-heavy application, explicit queries keep performance predictable.


Why spring.jpa.open-in-view: false
By default Spring Boot keeps the persistence context open until the HTTP response has been written ("Open Session in
View"), so lazy references work even while Jackson writes JSON in the controller. It hides N+1 problems and holds a
database connection for the whole request. EduMate switches it off: all database work happens inside service methods,
and controllers only receive plain records. Boot logs a warning when you leave it on without deciding; that is a hint
worth following.

H2 in development, PostgreSQL in production


EduMate's dev profile uses an in-memory H2 database with MODE=PostgreSQL, so nothing needs to
be installed; the docker profile points the same code at PostgreSQL 17. Because H2 only imitates
PostgreSQL, a test (PostgresCompatibilityTest) starts a real PostgreSQL and runs the important queries on
it. Spring Boot picks the driver and Hibernate's SQL dialect from the JDBC URL automatically.

Self-check


You load an entity in a transactional service method, change a field, and never call save. Is the change stored?

Yes: the entity is managed, and dirty checking writes an UPDATE when the transaction is flushed at
commit.


Why does an entity need a no-argument constructor?

Hibernate creates the object first and then fills its fields from the row; it needs a constructor it can call
without knowing the values.


What is the danger of EnumType.ORDINAL?

It stores the position of the constant; reordering or inserting constants changes the meaning of existing rows
without any error.


What is the N+1 query problem?

One query loads N parents, then accessing a lazy relationship on each parent runs one more query per parent: N+1
queries where one or two would do.
