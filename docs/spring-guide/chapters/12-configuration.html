Configuration: settings, profiles and typed properties

The same jar runs on a laptop with an in-memory database and in production with PostgreSQL, Redis and real secrets. Nothing is recompiled; only settings change. This chapter shows where settings come from, how profiles switch whole groups of them, and how to read them safely in Java.

Where settings live

Spring Boot reads settings (called properties) from many places and merges them into one Environment. The most common place is src/main/resources/application.yml (or application.properties; same content, different syntax):



YAML uses indentation for nesting, so spring: → jpa: → open-in-view: false is
the property spring.jpa.open-in-view. The same line in .properties syntax would be
spring.jpa.open-in-view=false. Settings under server.*, spring.* and
management.* belong to Spring Boot; each one is documented in the "Common Application Properties"
appendix of the Spring Boot reference, and your editor completes them for you.

Placeholders and environment variables


${PORT:8080} is a placeholder: "the value of the property or environment variable
PORT, or 8080 if there is none". This is how secrets stay out of the code:




On a laptop the harmless development defaults are used. In Docker, docker-compose.yml sets
JWT_SECRET and PAYMENT_GATEWAY_SECRET from the .env file, and the placeholders pick
them up.


Relaxed binding: one setting, many spellings
Spring Boot matches names loosely. The YAML key edumate.security.jwt-secret can also be set as the
environment variable EDUMATE_SECURITY_JWTSECRET (upper case, dots and dashes become underscores or
disappear) or the command-line argument --edumate.security.jwt-secret=…, and it is read in Java as
jwtSecret. The canonical form to write in files is lower case with dashes ("kebab case").



Which value wins?


When the same property is set in several places, the more specific source wins. Simplified, from strongest to
weakest:


    

  1. Command-line arguments: java -jar app.jar --server.port=9090
    2. 

  2. Java system properties: -Dserver.port=9090
    3. 

  3. Operating-system environment variables: SERVER_PORT=9090
    4. 

  4. Profile-specific files: application-docker.yml when the docker profile is active
    5. 

  5. The plain file: application.yml
    6. 

  6. Defaults written in code
    7. 



Files outside the jar (for example ./config/application.yml next to it) beat the ones inside it, so
operations staff can override settings without rebuilding.

Choose a profile with --spring.profiles.active=docker or the environment variable
SPRING_PROFILES_ACTIVE=docker (the backend's Dockerfile sets it). Several can be active at
once, separated by commas.


Keep profiles about environments, not features
Profiles such as dev, test, docker, prod age well. For switching a
feature on or off, use a normal property and a condition, as EduMate does for demo data:
@ConditionalOnProperty(prefix = "edumate.demo", name = "seed", havingValue = "true") on
DemoDataSeeder. The same profile can then run with or without demo data.



Reading settings in Java: typed properties


EduMate keeps all of its own settings under one prefix, edumate:, and reads them into a
record:




At start-up Spring Boot creates an AppProperties bean and fills it from the YAML:
edumate.academic.attendance-threshold-percent: 75 becomes
properties.academic().attendanceThresholdPercent(). The YAML list of campuses becomes a
List<Tenant>, the map of reserved seat shares a Map<String, BigDecimal>. Values are
converted to the right type (int, boolean, BigDecimal, Duration from
text like 10m…), and a value that cannot be converted stops start-up with a clear error.


Two things make it work: @ConfigurationProperties(prefix = "edumate") on the record, and
@ConfigurationPropertiesScan on the main class, which finds it. Any bean can then simply ask for it:





The alternative: @Value


@Service
public class LibraryService {
    public LibraryService(@Value("${edumate.library.loan-days}") int loanDays) { … }
}


@Value injects one property. It is fine for a single value, but for anything larger typed properties
win: one place lists every setting with its type, typos in names are found at start-up instead of silently giving
null, the editor offers completion, and tests can build the record by hand (TestFixtures
does).



Validate your settings
Add @Validated to a properties class and Bean Validation annotations to its fields
(@Min(1) int tokenValidityHours, @NotBlank String jwtSecret). A wrong setting then stops the
application at start-up, with the property's name, instead of misbehaving later. EduMate does its most important check
(the JWT secret's length) in SecurityConfig.jwtSigningKey.



Configuration as a whole: the rules of thumb


    

  • No secrets in the repository. Only harmless development defaults; real values come from the
environment (.env, Docker or Kubernetes secrets, a vault).
    • 

  • Everything that differs between environments is a setting; everything else is code. This is the
"config" rule of the Twelve-Factor App method.
    • 

  • Business rules that the university may change are settings too: EduMate's attendance threshold,
loan days, fines, merit weights and campuses are in YAML, so changing them needs no new release.
    • 

  • One prefix per application (edumate.*) keeps your settings apart from the framework's.

Self-check


server.port is 8080 in application.yml, SERVER_PORT=9000 is set in the environment, and the app is started with --server.port=7000. Which port is used?

7000: command-line arguments beat environment variables, which beat the files.


What does ${JWT_SECRET:dev-only…} mean?

Use the property or environment variable JWT_SECRET if it exists, otherwise the text after the colon.


Why does EduMate use a record with @ConfigurationProperties rather than many @Value annotations?

Type safety and one overview of all settings, errors at start-up for unconvertible values, editor completion, and
easy construction in tests.


When would you use @ConditionalOnProperty instead of a profile?

For a feature switch that is independent of the environment, like EduMate's demo data: any profile can run with
or without it.
