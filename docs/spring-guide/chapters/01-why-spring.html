Why Spring exists: the problem before the framework

Before learning how to use Spring, it helps to feel the problem it solves. This chapter builds a tiny web server in plain Java, lists everything a real one still needs, and then shows where Spring and Spring Boot come in.

A web server in plain Java

The JDK contains a small HTTP server. Here is a complete program that answers GET /hello:

import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class PlainServer {
    public static void main(String[] args) throws Exception {
        HttpServer server = HttpServer.create(new InetSocketAddress(8080), 0);
        server.createContext("/hello", exchange -> {
            byte[] body = "{\"message\":\"Hello\"}".getBytes(StandardCharsets.UTF_8);
            exchange.getResponseHeaders().add("Content-Type", "application/json");
            exchange.sendResponseHeaders(200, body.length);
            exchange.getResponseBody().write(body);
            exchange.close();
        });
        server.start();
    }
}

It works. Now imagine turning it into EduMate, where a teacher saves the attendance of a class. You would have to write, by hand:

JobWhat "by hand" means
RoutingMap every method + path (PUT /api/attendance/sessions) to the right Java method, including path variables like /api/library/loans/{id}/return.
JSONTurn request text into Java objects and objects back into text, with dates, decimals and nested lists.
ValidationCheck that period is between 1 and 6, that section is not blank… and report every problem clearly.
SecurityRead the Authorization header, verify a signed token, check the role against the address, refuse politely with 401 or 403.
DatabaseOpen connections (and share them in a pool), write SQL for every query, copy each row into an object and back.
TransactionsMake "save the register, write the audit line, queue the e-mails" succeed or fail together, even when an exception is thrown half-way.
ConcurrencyStop two teachers from overwriting each other's save.
ConfigurationRead the database address, secrets and limits from files and environment variables, differently on a laptop and in production.
WiringCreate the controller, which needs the service, which needs four repositories, a clock and a notifier, each of which needs something else… in the right order, once.
Everything elseError pages, logging, health checks for Docker, caching, scheduled jobs, file uploads with size limits, tests that start the whole thing…

None of these jobs is specific to a university. Every server application needs them. Writing them yourself takes months, and each hand-made version has its own bugs, especially the security and transaction parts.

Like building a house You could make your own bricks, pipes and wiring. Or you could buy tested parts that fit together and spend your time on the rooms that make this house special. Spring is the tested parts plus the builder who assembles them; EduMate's code is the rooms.

Spring Framework: the container and the integrations

Spring Framework (first released in 2003) has two big ideas:

  1. A container that builds your objects for you. You write classes that say what they need (AttendanceCaptureService needs repositories, a clock and a notifier). The container creates each object once, hands every object what it asked for, and keeps them all ready. This is called Inversion of Control and Dependency Injection (see Beans and dependency injection).
  2. Integrations that plug into the container. Web (Spring MVC), data access, transactions, security, caching, scheduling, messaging, testing. Because every integration talks to the same container, they combine: a method can be a web endpoint, run in a transaction and be cached, just by adding annotations.

Spring Boot: Spring with the set-up already done

Classic Spring was powerful but needed a lot of configuration (at first in XML) before the first request worked. Spring Boot (2014) removed that step with four ideas:

IdeaWhat it meansIn EduMate
StartersOne dependency brings a whole, tested set of libraries for one jobspring-boot-starter-webmvc = Tomcat + Spring MVC + Jackson (JSON)
Auto-configurationBoot looks at what is on the classpath and in your settings, and creates sensible beans for you (a DataSource, a JSON mapper, a transaction manager…), stepping aside when you define your ownEduMate never creates a database connection pool or a Jackson ObjectMapper itself
Embedded serverThe web server lives inside your application: java -jar app.jar and it listens on port 8080Tomcat, started by EduMateApplication.main
Production featuresHealth checks, metrics, externalised configuration, profiles/actuator/health for Docker; application-docker.yml

Two quick signs: imports from javax.persistence or javax.validation (now jakarta.*), and security code that extends WebSecurityConfigurerAdapter (removed; now you declare a SecurityFilterChain bean, as EduMate does). Self-check

What is the difference between Spring Framework and Spring Boot?
The Framework provides the container (dependency injection) and the integrations (MVC, transactions, data access, security hooks…). Boot sits on top and does the set-up: starters choose compatible libraries, auto-configuration creates the usual beans, an embedded server makes the application a runnable jar, and Actuator adds production features.
Why is "every server needs it" a good reason to use a framework for transactions and security?
Because these are hard to get right and easy to get subtly wrong. A framework's implementation has been tested by millions of applications; a hand-made one is tested only by yours, usually after something has gone wrong.
You find a tutorial with import javax.persistence.Entity;. What does that tell you?
It was written for Spring Boot 2 or older. Since Boot 3 the package is jakarta.persistence.
