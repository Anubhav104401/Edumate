Performance: threads, the database, start-up and native images

Most Spring applications are slow for a handful of reasons: too many database round trips, too few (or too many) connections, blocking on slow services, and heavy start-up. This chapter shows how to reason about each, and the newest tools: virtual threads, ahead-of-time processing and GraalVM native images.

First rule: measure

  • Metrics (Actuator + Micrometer): http.server.requests by endpoint (count, mean, max, percentiles), hikaricp.connections.pending (requests waiting for a connection), jvm.*.
  • SQL logging in development: count the queries of one request.
  • Profilers: Java Flight Recorder (built into the JDK: -XX:StartFlightRecording) or async-profiler show where time really goes.
  • Load tests (k6, Gatling, JMeter) against a production-like set-up, with realistic data volumes: EduMate's demo seeds a 60-student cohort; results morning means thousands.

The request thread model and virtual threads

Spring MVC on Tomcat is thread-per-request: each request occupies one thread until its answer is written. While that thread waits for the database or a payment gateway, it does nothing but still costs memory (a platform thread has a large stack) and Tomcat's pool has a limit (200 by default). Under load, requests queue although the CPU is idle.

Java 21's virtual threads are cheap threads managed by the JVM: millions can exist, and a virtual thread that blocks on I/O releases its carrier thread for others. One setting switches Spring Boot to them:

spring:
  threads:
    virtual:
      enabled: true      # Tomcat request handling, @Async, the scheduler… run on virtual threads
  • Helps when requests mostly wait (database, HTTP calls, file I/O) and you need high concurrency.
  • Does not help CPU-heavy work (EduMate's timetable solver) or a bottleneck elsewhere: if the connection pool has 10 connections, 10,000 virtual threads still get 10 queries at a time.
  • Watch for pinning: code that blocks while holding a monitor could pin the carrier thread in Java 21 (largely fixed for synchronized in Java 24). Libraries have mostly adapted; keep dependencies current.

With virtual threads, the classic Spring MVC style (simple, blocking, easy to debug) scales far enough for most applications; the next chapter compares it with reactive programming.

The database is usually the bottleneck

Round trips

A query costs a network round trip plus database work. Ten fast queries are slower than one query that fetches the same data. EduMate's rules of thumb, seen throughout this course:

  • One grouped query per screen instead of one per row (countByCourseForStudent): avoid N+1.
  • Projections into records instead of whole entities when only a few columns are needed.
  • Load related data for a whole set in one …In(ids) query (findByStudentResultIdIn), then join in memory with a map.
  • Atomic conditional updates instead of read-modify-write (publishIfApproved).
  • @Transactional(readOnly = true) for reads; open-in-view: false.
  • Cache what many users read and few change (@Cacheable on published results).

Batching writes, and an IDENTITY surprise



With hibernate.jdbc.batch_size, Hibernate groups many UPDATEs into one JDBC batch. But Hibernate
cannot batch INSERTs for entities whose ids come from an IDENTITY column: it must
send each insert alone to learn the generated id. EduMate's entities use IDENTITY, which is why the demo
seeder inserts thousands of attendance rows with JdbcTemplate.batchUpdate instead of saving entities. For
write-heavy entities, a SEQUENCE generator with an allocationSize (e.g. 50) lets Hibernate reserve ids
in advance and batch the inserts.



Connection pool size


Counter-intuitively, a small pool is usually faster: a database with 4 cores does not run 100 queries at once
any faster than 10; it just switches between them. HikariCP's default of 10 is a good start. Increase it only when
metrics show requests waiting for connections and the database has spare capacity; and remember that every
application instance has its own pool.

GraalVM native images


A native image compiles the application and the parts of the JDK and libraries it uses into one operating-system
executable, ahead of time. Spring Boot supports this directly:


# with GraalVM installed (the Spring Boot parent defines a "native" profile)
./mvnw -Pnative native:compile          # → target/edumate-backend (an executable, no JVM needed)
./mvnw -Pnative spring-boot:build-image # → a container image with the native executable


How it works: at build time Spring runs its AOT engine: it evaluates the conditions, creates bean
definitions as generated Java code, and records which classes need reflection, proxies, resources or serialization
("runtime hints"). GraalVM then analyses everything reachable from main and leaves the rest out: the
closed-world assumption.


The closed world has rules

    

  • Profiles and @Conditional decisions are taken at build time; a native image built for one set of
conditions cannot switch beans at run time (properties can still change values).
    • 

  • Reflection, dynamic proxies and resources the analysis cannot see need hints: implement
RuntimeHintsRegistrar and register it with @ImportRuntimeHints, or use
@RegisterReflectionForBinding. Most Spring and popular libraries ship their hints already.
    • 

  • Builds take minutes and much memory; test on the JVM, build native in CI.
    • 

  • Peak throughput may be lower than a warmed-up JIT-compiled JVM; native shines where start-up and memory matter
(serverless, scale-to-zero, many small instances, command-line tools).
    • 



For EduMate, a long-running server with a steady load, the JVM is the right default; a native build would be worth
it only for, say, a serverless payment-callback handler.

Self-check


When do virtual threads improve throughput, and when do they not?

They help when requests spend most of their time blocked on I/O and concurrency is limited by threads. They do not
help CPU-bound work or when another resource (the connection pool, the database) is the limit.


Why can Hibernate not batch inserts of IDENTITY-id entities?

The id is generated by the database during the insert, and Hibernate needs it immediately to manage the entity, so
it must execute each insert on its own. Sequence-based ids can be reserved in advance.


What is the "closed-world assumption" of native images?

Everything the program may use must be known at build time; code reachable only through undeclared reflection or
dynamic loading is left out, which is why runtime hints exist and conditions are fixed at build time.
