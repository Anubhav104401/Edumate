Beans and dependency injection: the heart of Spring

Everything else in Spring is built on one idea: you do not create your important objects; the container does, and it hands each object the others it needs. Understand this chapter well and the rest of the framework stops feeling like magic.

The problem: wiring objects by hand

EduMate's AttendanceController needs an AttendanceCaptureService. That service needs two repositories, a student repository, a course-access checker, an audit logger, a shortfall notifier and a clock. The notifier needs a summary service, which needs more repositories and the settings… Without a framework, some main method would have to build the whole tree, in the right order:

// Imagine this for all 120 classes of EduMate…
AppProperties properties = loadPropertiesSomehow();
Clock clock = Clock.system(ZoneId.of("Asia/Kolkata"));
DataSource dataSource = new HikariDataSource(/* url, user, password, pool size… */);
AttendanceSessionRepository sessions = new JdbcAttendanceSessionRepository(dataSource);
AttendanceRecordRepository records = new JdbcAttendanceRecordRepository(dataSource);
StudentRepository students = new JdbcStudentRepository(dataSource);
AuditLogger audit = new AuditLogger(new JdbcAuditRepository(dataSource), clock);
AttendanceSummaryService summary = new AttendanceSummaryService(records, /* 4 more… */);
ShortfallNotifier notifier = new ShortfallNotifier(summary, students, /* notifications */, clock);
AttendanceCaptureService capture = new AttendanceCaptureService(sessions, records, students,
        new CourseAccess(/* … */), audit, notifier, clock);
AttendanceController controller = new AttendanceController(capture, summary, notifier, /* … */);

This is fragile (change one constructor and fix ten places), repetitive, and it gets harder when some objects must be shared (one clock, one connection pool) and others must be wrapped with extra behaviour (transactions, security, caching).

Inversion of Control and Dependency Injection

Like a film set An actor does not hire the camera crew or build the set. They say what they need for a scene ("a chair, a phone"), and the production team provides it before the camera rolls. In Spring, your class is the actor: its constructor lists what it needs, and the container is the production team.
  • Inversion of Control (IoC): the framework, not your code, controls when objects are created and how they are connected. You describe; it builds.
  • Dependency Injection (DI): the specific technique: an object receives the objects it depends on ("dependencies") from outside, usually through its constructor, instead of creating them itself.
  • A bean is simply an object that the Spring container creates and manages. EduMate has a few hundred: its own services, controllers and repositories, plus the ones Spring Boot creates (the data source, the JSON mapper, the security filters…).
  • The container is the ApplicationContext. SpringApplication.run creates it.

Constructor injection, in a real class



Read it as a sentence: "I am a service. To exist, I need these seven things." That is all. When Spring
creates this bean it looks at the constructor, finds a bean for each parameter type (the two repositories, the
student repository, CourseAccess, AuditLogger, ShortfallNotifier,
Clock), creates those first if necessary, and calls the constructor.


    

  • No @Autowired is needed: when a class has exactly one constructor, Spring uses it.
    • 

  • Fields are final: once built, the service can never lose or swap a collaborator. That
also makes it safe to share between threads (see scopes below).
    • 

  • The class does not know Spring exists. Nothing in the constructor mentions the container. A test
can call new AttendanceCaptureService(...) with test doubles.
    • 




Always prefer constructor injection
The older styles are field injection (@Autowired private Foo foo;) and setter injection.
Field injection hides what a class needs, cannot use final, and forces tests to use reflection or Spring.
Use constructor injection in application code. In test classes, field injection is fine and common: EduMate's
IntegrationTestBase uses @Autowired protected MockMvc mvc;.

@Bean: beans made from classes you do not own


You cannot put @Component on java.time.Clock or on Spring Security's
BCryptPasswordEncoder: they are not your classes. Instead, a @Configuration class has a
method that makes the object, marked @Bean:




The method's return value becomes a bean named after the method (clock). Every class that asks for a
Clock in its constructor, and there are many, receives this same object. Why not just call
LocalDate.now() everywhere? Because a test can then replace this one bean with a fixed clock
(Clock.fixed(...)) and get the same "today" on every run: "attendance for a future date" and "the loan is
3 days late" become testable.


@Bean methods can ask for other beans as parameters:




jwtSigningKey needs the settings (AppProperties); jwtEncoder and
jwtDecoder both need the key. Spring works out the order. Notice the check in
jwtSigningKey: a secret shorter than 32 bytes stops the application at start-up with a clear message,
which is far better than a security weakness discovered in production.



Under the hood: why @Configuration classes are special
Spring creates a subclass of every @Configuration class at start-up (with a library called CGLIB). The
subclass intercepts @Bean methods, so if one @Bean method called another
(return new NimbusJwtEncoder(new ImmutableSecret<>(jwtSigningKey()))), it would still receive the
one shared key instead of a new one. Passing beans as parameters, as EduMate does, avoids relying on that trick
altogether; such classes can even be marked @Configuration(proxyBeanMethods = false) to skip the subclass.
Spring Boot's own auto-configurations do exactly that.

Singletons are shared by all requests at the same time
Tomcat serves many requests in parallel, each on its own thread, and they all use the same
AttendanceCaptureService object. So a singleton must be stateless: no field may hold data
about one request (the current user, a running total…). Keep that data in local variables and parameters. EduMate's
services only have final fields holding other beans. RoleMatrix fills its list once, in the
constructor, and afterwards only reads it; rules() even hands out a copy.



A few more things you will meet


    

  • Bean names default to the class name with a small first letter (attendanceCaptureService)
or the @Bean method name (clock).
    • 

  • ObjectProvider<T>: inject it instead of T to get the bean lazily,
or only if it exists (getIfAvailable()).
    • 

  • Optional dependencies: a constructor parameter of type Optional<T> receives an
empty Optional when no such bean exists.
    • 

  • Circular dependencies (A needs B, B needs A) make start-up fail. Spring Boot refuses them by
default since version 2.6, because they usually signal a design problem. Break the cycle: extract the shared part into
a third bean, or let one side publish an event.
    • 

  • Never fetch beans by hand with context.getBean(...) in application code (the
"service locator" style). It hides dependencies just like field injection does.
    •

Self-check


What is the difference between IoC and DI?

Inversion of Control is the general principle that the framework controls object creation and the flow; Dependency
Injection is the concrete technique of handing an object its collaborators from outside (in Spring, usually through the
constructor).


When do you use @Bean instead of @Component?

When the class is not yours (a JDK or library class such as Clock, PasswordEncoder,
JwtDecoder), or when creating the object needs code (reading a setting, checking a secret's length,
choosing an implementation).


Why must a singleton service not keep "the current user" in a field?

The same instance serves many requests in parallel threads. A field would be overwritten by another request while
the first is still running, mixing up users. Request data belongs in parameters and local variables.


Two beans implement the same interface and start-up fails. Name three fixes.

Create only one (profiles or conditions), mark one @Primary, or name the wanted one with
@Qualifier at the injection point. (Or inject a List of all of them.)
