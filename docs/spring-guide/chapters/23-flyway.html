Evolving the schema with Flyway migrations

Code changes every week; the database must change with it, on every developer's laptop, in the tests, and in production, in exactly the same way and without losing data. Migrations make database changes versioned, repeatable and automatic.

Why not let Hibernate create the tables?

Hibernate can generate tables from your entities (spring.jpa.hibernate.ddl-auto: create or update). It is handy for a first prototype and dangerous afterwards:

  • update only adds; it never renames, drops, moves data or fixes a wrong type, and it guesses at column types and lengths.
  • It cannot express many database rules you want (CHECK constraints, partial indexes, precise UNIQUE combinations, ON DELETE CASCADE).
  • Nobody reviews the SQL it runs on the production database.

EduMate sets ddl-auto: none: Hibernate never touches the schema. Flyway owns it.

How Flyway works

  1. You write SQL files in src/main/resources/db/migration/, named V<version>__<description>.sql (two underscores): V1__create_schema.sql, V2__add_book_language.sql…
  2. At start-up, before Hibernate and your beans use the database, Spring Boot runs Flyway (thanks to spring-boot-starter-flyway).
  3. Flyway reads its own table, flyway_schema_history, to see which versions this database already has, and runs only the missing files, in version order, each in a transaction where the database allows it.
  4. It records each file's version, description, checksum, time and success in the history table.

The same jar therefore upgrades an empty test database from nothing to the latest version, and a year-old production database from version 7 to version 12, with no manual step.

Portable SQL
EduMate's migration runs unchanged on H2 (development) and PostgreSQL (production): standard types, GENERATED BY
DEFAULT AS IDENTITY for ids, TIMESTAMP WITH TIME ZONE for instants, NUMERIC(12,2) for
money. When you need database-specific SQL, Flyway can keep separate folders per vendor
(spring.flyway.locations=classpath:db/migration/{vendor}).



The rules of migrations


Never edit a migration that has run somewhere
Flyway stores each file's checksum. Change V1__create_schema.sql after it has run on any shared database,
and the next start-up fails with a checksum mismatch, deliberately: that database was built from the old text. Write a
new file instead: V2__add_room_capacity.sql with ALTER TABLE ….


    

  • One change, one file, small and reviewed like code.
    • 

  • Change entities and migrations together, in the same commit. Start-up (and every integration test)
runs the migrations first, so a mismatch shows up immediately.
    • 

  • Expand, then contract for changes on a live system: add the new column (V5), deploy code that writes
both, copy the data (V6), deploy code that reads only the new one, drop the old column (V7). Every step is safe to roll
out while the previous version is still running.
    • 

  • Data migrations are migrations too: UPDATE statements that fix or move data belong in
versioned files, not in someone's SQL console.
    • 

  • Repeatable migrations, named R__description.sql, run again whenever their content
changes; use them for views and stored procedures.
    • 

  • Existing databases: spring.flyway.baseline-on-migrate=true lets Flyway adopt a database
that was created before Flyway was introduced.
    • 



Liquibase is the other popular tool; it does the same job with changelogs in XML, YAML or SQL and can generate
rollbacks. Spring Boot supports both equally.

Self-check


How does Flyway know which migrations a database still needs?

It reads flyway_schema_history, which lists every version already applied, and runs the newer files in
order.


Why must you not edit an applied migration?

Databases that already ran it would not run it again, so they would differ from new databases. Flyway detects the
edit through the checksum and refuses to start.


What does ddl-auto: none protect against?

Hibernate silently altering (or failing to correctly alter) the production schema; the schema changes only through
reviewed migration files.
