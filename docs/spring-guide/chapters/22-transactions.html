Transactions and concurrency: all or nothing, one at a time

Saving attendance writes a session, sixty records, an audit line and a few outbox messages. Either all of that must happen or none of it. And when two teachers save the same register at once, neither may silently destroy the other's work. This chapter covers @Transactional, rollback rules, propagation, and the two kinds of locking, with the real bugs EduMate fixed.

What a transaction guarantees

A database transaction groups statements into one unit with the ACID guarantees:

GuaranteeIn EduMate
Atomicall statements succeed, or none take effecta payment is never marked SUCCESS without its ledger credit and receipt
Consistentconstraints (UNIQUE, foreign keys, CHECK) hold after every transactionno second ledger credit for the same bank reference
Isolatedconcurrent transactions do not see each other's half-done worka student never sees a result set half-published
Durableonce committed, it survives a crasha receipt number, once shown, exists

@Transactional: one annotation, and the method becomes a transaction



When another bean calls publish(...), Spring:


    

  1. takes a connection from the pool and starts a transaction;
    2. 

  2. runs your method; every repository call inside it uses that same connection and transaction;
    3. 

  3. if the method returns normally: flushes pending changes and commits;
    4. 

  4. if it throws an unchecked exception: rolls back, as if nothing had happened, and re-throws.
    5. 



So when publish throws ApiException.conflict("NOT_APPROVED", …), any change made earlier in
the method is undone, and GlobalExceptionHandler sends the 409.


Under the hood: a proxy stands in front of your bean
Spring does not change your class. At start-up it wraps the bean in a proxy: an object of a generated
subclass that intercepts calls to @Transactional methods, starts the transaction, calls your real method,
then commits or rolls back. Other beans receive the proxy, not your object. This explains the famous trap below, and
Level 4 has a whole chapter on proxies.



Read-only transactions


Many EduMate services are annotated at class level with @Transactional(readOnly = true)
(AttendanceSummaryService, ReportService, DashboardService…). A class-level
annotation applies to every public method. readOnly tells Hibernate it may skip dirty checking and lets the
driver and database optimise; a method that must write overrides it with its own @Transactional.



Rollback rules, and when you do not want to roll back


By default Spring rolls back for unchecked exceptions (RuntimeException,
Error) and commits for checked exceptions. You can change that per method. EduMate has a
case where a refusal must still save something: a wrong password must increase the failed-attempts counter, even though
the method then throws.




noRollbackFor = ApiException.class means: if an ApiException is thrown, commit anyway. The
counter update (dirty checking on user) and the audit line are saved, then the 401 is sent. Without it the
counter would be rolled back on every failure, and the lockout after five wrong passwords would never happen.
ConsentRegistry.verify uses the same technique for the guardian's wrong-code counter.


Also worth noticing in that method: when the username does not exist, it still runs a bcrypt check against a dummy
hash, so that "no such user" takes as long as "wrong password" and an attacker cannot discover valid usernames by
timing the answers.



Propagation: transactions inside transactions


When a @Transactional method calls another @Transactional method (on another bean), what
happens depends on propagation:




PropagationBehaviourUse



REQUIRED (default)join the caller's transaction if there is one, else start onealmost always: EduMate's AuditLogger.record joins the caller's transaction, so the audit line commits or rolls back with the change it describes


REQUIRES_NEWsuspend the caller's transaction and run in a new, independent onesomething that must be saved even if the caller fails, e.g. a security log line that must survive a rollback


MANDATORYmust be called inside a transaction, or failguard methods that are only meaningful as part of a bigger unit


SUPPORTS, NOT_SUPPORTED, NEVER, NESTEDrarer variantsread the reference when you need them




Joined transactions roll back together
If an inner REQUIRED method throws and the outer method catches the exception and carries on, the shared
transaction has already been marked rollback-only, and the commit at the end fails with
UnexpectedRollbackException. Catching an exception does not undo the inner method's vote.



The self-invocation trap


@Service
public class ReportJob {
    public void runAll() {
        for (Long id : ids) {
            runOne(id);          // ← a plain call on "this", NOT through the proxy
        }
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void runOne(Long id) { … }   // the annotation is silently ignored for the call above
}


The proxy only sees calls that come from outside the bean. A method calling another method of the same
object goes straight to the real object, and no transaction (or cache, or security check) is applied. Fixes: move
runOne to another bean (the cleanest), or inject the bean's own proxy, or use
TransactionTemplate in code. The same rule applies to @Cacheable, @Async and
@PreAuthorize. Also: annotated methods must be public and not final.



Two users, one record: optimistic locking


The bug (EduMate's design review finding DR-01): two teachers open the same attendance register.
Teacher A saves. Teacher B, still looking at the old version, saves a minute later, and A's work is silently
overwritten. This is a lost update.


The fix: a version number on the row.




With @Version, every UPDATE Hibernate writes looks like this:


update attendance_session set taken_by=?, updated_at=?, version=4 where id=41 and version=3


If someone else has already moved the row to version 4, the WHERE matches nothing, Hibernate sees
"0 rows updated", and throws an optimistic-locking exception, which EduMate turns into 409
STALE_UPDATE. Nobody waits and nothing is locked: the conflict is detected at the moment it happens. EduMate
adds a second, earlier check: the browser sends the version it loaded, and the service compares it before writing
anything:




The frontend then tells the teacher: "Someone else saved this register while you were editing. Your changes were not
saved, so nothing was overwritten. Reload…". AttendanceConcurrencyIntegrationTest proves the whole chain.



One record, strictly one at a time: pessimistic locking


The bug (DEF-014): payment gateways sometimes deliver the same "payment succeeded" callback twice,
sometimes at the same instant. The old handler credited the student twice.


Here, detecting the conflict afterwards is not enough; the second delivery must wait for the first and then
see its result. So PaymentOrchestrator.handleCallback loads the payment with
findByGatewayOrderIdForUpdate (@Lock(PESSIMISTIC_WRITE), i.e. SELECT … FOR
UPDATE): the database holds the row lock until the first transaction commits, the second then reads a payment
already marked SUCCESS and answers DUPLICATE_IGNORED. A UNIQUE constraint on the bank reference is the last
line of defence.




Optimistic (@Version)Pessimistic (@Lock)



Ideaassume conflicts are rare; detect them at write timeassume conflicts happen; prevent them by locking at read time


Costnone until a conflict; the loser must retryothers wait; risk of deadlocks if rows are locked in different orders


Good forhuman editing (forms open for minutes)short, machine-driven critical sections (payments, counters)

The third tool, seen in the repositories chapter, is the atomic conditional update
(UPDATE … WHERE status = 'APPROVED'): check and change in one statement, no lock held in between.



Isolation levels, briefly


Databases let transactions see each other's committed changes in different ways (READ_COMMITTED,
REPEATABLE_READ, SERIALIZABLE). PostgreSQL's default, READ_COMMITTED, is what EduMate
uses: a statement sees data committed before it started. Rather than raising the isolation level globally (slower, and
more transactions fail), EduMate protects the few places that need it with the locks and conditional updates above.
@Transactional(isolation = …) exists when you need it.



Doing something only if the transaction commits


Files are not in the database, so a rollback cannot undo writing one. EduMate's DocumentService therefore
registers callbacks with the transaction:




A new upload is written to disk first; if the transaction then rolls back (say the database insert fails), the file
is deleted again. When a document is removed, its file is only deleted after the database change has
committed. The database and the disk can never disagree. @TransactionalEventListener (Level 4) is the
higher-level version of the same idea.

Self-check


A @Transactional method throws a checked IOException. Is the transaction rolled back?

No, by default only unchecked exceptions roll back. Use rollbackFor = IOException.class (or wrap it
in an unchecked exception, as EduMate does with UncheckedIOException).


Why does calling a @Transactional method from another method of the same class not start a transaction?

Transactions are applied by a proxy around the bean; an internal call on this never goes through the
proxy.


When would you choose a pessimistic lock over @Version?

When the second party must wait and then act on the first one's result (duplicate payment callbacks), in short
critical sections. For people editing forms, optimistic locking is better: nobody waits, conflicts are reported.


What does noRollbackFor achieve in LoginAttemptService?

The failed-attempt counter and audit line are committed even though the method throws the 401 error, so the
lockout works.
