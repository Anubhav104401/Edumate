Caching, background jobs and start-up tasks

Three kinds of work do not fit "one request, one answer": answers worth remembering (caching), work that should happen on a timer or later (scheduling, the outbox), and work that must happen once when the application starts (runners). Spring handles each with an annotation and an abstraction you can plug a real technology into.

Caching with @Cacheable

On results morning, thousands of students refresh "My results" again and again, and the answer does not change until the next publication. Computing it each time wastes the database. EduMate caches it:



The first call for student 7 runs the method and stores the result in the cache publishedResults under the
key 7. Every later call with 7 returns the stored result without running the method.
key = "#studentId" is a SpEL expression naming the parameter (by default, all parameters form the key).


A cache is only correct if it is emptied when the truth changes. Publishing new results does exactly that:






AnnotationEffect



@Cacheablereturn the cached value if present; otherwise run and store


@CacheEvictremove one key, or allEntries = true for everything in the cache (after the method, by default)


@CachePutalways run, and store the new value (refresh a key)


@Cachingseveral of the above on one method


@EnableCachingswitches the whole mechanism on (on EduMateApplication)





Where the cache lives: providers


The annotations are an abstraction; the storage is configuration. In development EduMate uses Spring's simple
in-memory maps; the docker profile switches to Redis, shared by all backend copies and surviving restarts:






No Java code changes between the two. Values sent to Redis must be serialisable; by default Spring's Redis cache uses
Java serialization, which is why the cached records are declared implements Serializable:




(A JSON serializer can be configured with a RedisCacheConfiguration bean; then the Serializable
is unnecessary and the cached values are human-readable.) Other providers work the same way: Caffeine for a fast local
cache with size limits, Hazelcast, or any JCache implementation.


Caching traps

    

  • Self-invocation: like @Transactional, @Cacheable works through a proxy; calling
the method from the same class skips the cache.
    • 

  • Security: the key must include everything that makes the answer differ. Caching "my results" by
studentId is safe because the id comes from the login token; a key that forgot the user would serve one
student's results to another.
    • 

  • Staleness: every write path that changes the answer must evict, or a time-to-live must bound how old an
answer may be. EduMate does both: eviction on publish and a 10-minute TTL in Redis.
    • 

  • Mutable values: with an in-memory cache, callers receive the same object; records (immutable)
avoid accidental edits of the cached copy.
    • 




Scheduled jobs and the outbox pattern


The problem (design finding DR-08): computing results used to send e-mails and SMS itself. A slow or
failing SMS provider then slowed down or broke the result computation, and a rollback after sending could not un-send
a message.


The fix: the outbox pattern. Business code only writes a row into the
notification_outbox table, in the same transaction as the business change. A separate scheduled job sends
what is waiting:






    

  • @EnableScheduling (on the main class) activates @Scheduled methods on any bean.
    • 

  • fixedDelayString = "PT5S": 5 seconds after the previous run finished (an ISO-8601 duration).
fixedRate would count from the previous start; cron = "0 0 7 * * MON-FRI" runs at 7:00 on
weekdays (Spring cron has a seconds field first).
    • 

  • The message is queued only if the business transaction commits (it is part of it), and it is sent even if the
provider is down for an hour: failed sends are retried up to 3 times.
    • 

  • The deduplication key (existsByDedupKey, plus a UNIQUE column) stops the same message being queued twice.
    • 



Several copies of the application
Every running copy runs every @Scheduled method. With two backends, both could pick the same pending message.
Solutions: lock the rows being processed (SELECT … FOR UPDATE SKIP LOCKED), use a scheduler lock library
such as ShedLock, or run jobs on one designated instance. EduMate, run as one backend, keeps it simple and notes the
limit.



Running work in the background: @Async and virtual threads


@EnableAsync plus @Async on a method makes callers return immediately while the method runs on
another thread (returning void or a CompletableFuture). It is useful for work the user need not
wait for, but it is not durable: if the application stops, the work is lost. For anything that must happen (a
receipt e-mail), prefer the outbox.


Java 21's virtual threads make blocking cheap: set spring.threads.virtual.enabled=true
and Tomcat, @Async and the scheduler run tasks on virtual threads, so thousands of requests waiting on the
database or a slow provider no longer need thousands of expensive platform threads. The Level 4 performance chapter
discusses when this helps.



Start-up tasks: ApplicationRunner


A bean implementing ApplicationRunner (or CommandLineRunner) is called once, after the
context is ready and Tomcat has started. EduMate creates missing campuses from the configuration:




Adding a campus is a configuration change (edumate.tenants in the YAML), never a code change.
@Order(1) makes it run before the demo seeder, which needs the campuses:




@ConditionalOnProperty means the seeder bean does not even exist unless
edumate.demo.seed=true: in production it cannot run by accident. This is the same conditional mechanism
Spring Boot's auto-configuration is built on (Level 4).


Runners versus events
Runners are for "do this once at start-up". To react to the lifecycle more precisely, listen for events:
@EventListener(ApplicationReadyEvent.class) runs when the application is fully ready to serve (after the
runners). Do not put slow work in a constructor or @PostConstruct: it delays the whole start-up and runs
before other beans are ready.

Self-check


What is the difference between fixedDelay and fixedRate?

fixedDelay waits the given time after the previous run finished; fixedRate starts runs at a
fixed interval measured from the previous start, whatever their duration.


Why does EduMate write e-mails to an outbox table instead of sending them directly?

So a slow or failing provider cannot slow down or break the business operation, the message is queued atomically
with the change it announces, and failed sends can be retried later.


What would go wrong if publishing results did not evict the publishedResults cache?

Students would keep receiving the cached, older list of results until the entries expired.


How is it guaranteed that demo data is never seeded in production?

The seeder is annotated @ConditionalOnProperty(… seed = "true"); with the property false the bean is
never created, so its code cannot run.
