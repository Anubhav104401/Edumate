Spring Data repositories: queries without boilerplate

A repository is an interface. You declare what you want, Spring Data writes the implementation at start-up. This chapter covers the free methods, queries derived from method names, hand-written JPQL, projections, bulk updates, locking and paging, all from EduMate's repositories.

The smallest repository



Extending JpaRepository<Entity, IdType> gives you, without writing anything:




MethodDoes

findById(id)an Optional: empty if there is no such row


findAll(), findAll(Sort), findAll(Pageable)everything, sorted, or one page


existsById, count()quick checks


delete(entity), deleteById(id)remove


flush(), saveAndFlushsend pending SQL now (used by EduMate to detect a lost race inside the request)




Every call runs in a transaction (a read-only one for the finders) unless you are already inside one.

Projections: select only what you need, straight into a record


Loading whole entities to compute a few numbers is wasteful. A constructor expression builds result
records directly in the query:




The database groups and counts; only one small row per course travels to Java, and the result is a list of
AttendanceCount records (key, held, attended). One query for a
student's whole semester, whatever the number of classes. This is how EduMate avoids the N+1 problem: think in
sets (one query for the cohort), not in loops (one query per student).


Other projection styles
Spring Data also accepts an interface projection (declare interface CourseName { String getCode();
String getName(); } and return List<CourseName>) or a record type as the return type of a
derived query. Constructor expressions are the most explicit and work everywhere.



Changing many rows at once: @Modifying


An update or delete query needs @Modifying. EduMate uses one for the most
safety-critical write in the system, publishing results:




The whole decision "is it still approved? then publish it" happens in one SQL statement. The
database executes it atomically: if two superintendents press Publish at the same moment, only one
UPDATE finds the row still APPROVED; the method returns 1 for that one and
0 for the other, which the service turns into a clear refusal. The earlier design (read the status in Java,
then write it) let both succeed.


    

  • flushAutomatically = true: write any pending changes before the bulk statement, so it sees them.
    • 

  • clearAutomatically = true: empty the persistence context after it, because bulk statements
bypass dirty checking and loaded entities would otherwise show stale values.
    • 

  • Bulk statements skip entity callbacks and @Version checks; that is why this query increments
version itself.
    • 




Locking a row: @Lock


When a payment callback arrives, EduMate must be sure no other thread handles the same payment at the same time:




PESSIMISTIC_WRITE adds FOR UPDATE to the SQL: the database locks the row until the
transaction ends, and a second callback for the same order waits, then sees the payment already marked SUCCESS. The
transactions chapter compares this with optimistic locking.



Paging and sorting


List<Payment> findAllByOrderByCreatedAtDesc(Pageable pageable);     // PaymentRepository

// FeeAccountService.recent: "the 200 newest payments" (page 0, 200 per page)
payments.findAllByOrderByCreatedAtDesc(PageRequest.of(0, 200));


A Pageable parameter adds LIMIT/OFFSET (page number and size, optionally a
sort). Return Page<T> instead of List<T> to also get the total count (one extra
count query), useful for "page 3 of 12" in a table. The outbox dispatcher uses the same technique to take at
most 50 pending messages per run.



When to go below JPA


    

  • Native queries: @Query(value = "…", nativeQuery = true) for database-specific SQL
(window functions, JSON operators). You lose portability between H2 and PostgreSQL, so test on the real database.
    • 

  • JdbcTemplate / JdbcClient: plain SQL with Spring's help, no entities. EduMate's
demo seeder inserts thousands of attendance rows with one batched jdbc.batchUpdate(...), far faster than
saving entities one by one.
    • 

  • Specifications / Querydsl: build queries dynamically from many optional filters.

Self-check


Where does the implementation of StudentRepository come from?

Spring Data creates it at start-up (a proxy backed by a generic repository implementation), deriving each query
from the method name or its @Query.


Why is publishIfApproved safe when two people publish at the same moment?

The check and the change are one atomic UPDATE … WHERE status = 'APPROVED'; only one statement can
match the row, and the returned count tells each caller whether it won.


What does clearAutomatically = true protect you from?

From reading stale entities: a bulk update changes rows directly in the database, not the objects already loaded in
the persistence context, so the context is cleared after it.


Why are named parameters immune to SQL injection?

The values are sent to the database separately from the query text (as bound parameters), so they are always
treated as data, never as SQL.
