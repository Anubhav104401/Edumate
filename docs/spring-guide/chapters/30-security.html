Spring Security: tokens, roles and deny-by-default

Security answers two questions on every request: who are you? (authentication) and may you do this? (authorisation). Spring Security answers both in a chain of filters before your controller runs. This chapter builds EduMate's security from its parts: password hashing, login, signed tokens, a role matrix that refuses everything it does not know, and checks on individual records.

The big picture

① Login   POST /api/auth/login {"username","password"}
            → LoginAttemptService: bcrypt check, lockout after 5 failures
            → JwtTokenService: a signed token {sub, role, campus, uid, sid, exp}
            ← {"token": "eyJ…", "expiresAt": …, "user": {…}}

② Every later request    Authorization: Bearer eyJ…
   Security filter chain (before Spring MVC):
     BearerTokenAuthenticationFilter   read the header, verify the signature and expiry with the JwtDecoder
        → Authentication { name: "student", authorities: [ROLE_STUDENT] } in the SecurityContext
     AuthorizationFilter               RoleMatrix: may ROLE_STUDENT call GET /api/attendance/me?  yes → continue
     (no / bad token → 401 by the entry point;  wrong role → 403 by the access-denied handler)
   → DispatcherServlet → controller → service: "may THIS teacher open THIS course?" (object-level check)

Because the token carries everything the server needs and is verified by its signature, the server stores no session: any copy of the backend can serve any request. That is what stateless means.

Under the hood: filters and the SecurityContext
Tomcat passes each request through a list of servlet filters. Spring Security registers one of them
(DelegatingFilterProxy → FilterChainProxy), which runs the chain you configured: about a
dozen small filters, each with one job. A successful authentication is stored in the
SecurityContextHolder, a thread-local slot that later code (EduMate's CurrentUserArgumentResolver,
method security) reads. Start the backend with logging.level.org.springframework.security=TRACE to see each
filter handle a request.



From token claim to role




Spring Security represents permissions as authorities (strings). A role is simply an
authority starting with ROLE_. The converter reads the token's role claim
("FACULTY") and produces the authority ROLE_FACULTY; rules written as
hasRole("FACULTY") or hasAnyRole(...) add the prefix when comparing.



Issuing tokens




A JWT has three parts, each Base64url-encoded and joined by dots: a header ({"alg":"HS256"}),
the claims (sub = username, exp = expiry, plus EduMate's uid,
role, campus, sid) and a signature: an HMAC-SHA256 of the first two
parts with the server's secret key. Anyone can read the claims (never put secrets in them), but changing a
single character invalidates the signature, and the JwtDecoder refuses the token with 401.


Symmetric versus asymmetric keys
EduMate signs and verifies with one shared secret (HS256), which is right when the same application does both. When a
separate identity provider issues tokens (Keycloak, Azure AD, the university's single sign-on), use asymmetric keys
(RS256/ES256): configure only spring.security.oauth2.resourceserver.jwt.issuer-uri, and Spring Boot
fetches the provider's public keys and builds the decoder for you.



Passwords: bcrypt and lockout


The PasswordEncoder bean is new BCryptPasswordEncoder(12). Bcrypt adds a random
salt to every password and is deliberately slow (cost 12 ≈ a quarter of a second): harmless for one login,
crippling for an attacker trying millions of guesses from a stolen database. Never store passwords any other way, and
never compare hashes with equals; use passwordEncoder.matches(raw, hash).


LoginAttemptService (see the transactions chapter) counts failures and locks the account for 15 minutes
after the fifth, answering 423 Locked. Unknown usernames take as long as wrong passwords, and both get
the same message, so the login form does not reveal which usernames exist.

Deny by default. An address that nobody listed is refused for everyone, even administrators. In the
original design two report endpoints were forgotten and fell back to "any logged-in user may call it"; a student could
download every student's marks (defect DEF-031). With denyAll() a forgotten endpoint fails closed, and
RoleMatrixCoverageTest fails the build if any controller mapping is missing from the list.


Rules are checked in order and the first match wins, so specific patterns must come before general ones.
* matches one path segment, ** any number.



Authorisation by record: object-level checks


The matrix knows roles and addresses, not data. "A FACULTY member may call GET /api/attendance/courses/{id}/summary"
is true, but which courses? Without a second check, a teacher could type another course's id into the address
(an insecure direct object reference, OWASP's number one risk, "Broken Access Control"). EduMate's services
check the record itself:




The same idea appears everywhere a record belongs to someone: students only see their own fees (the student id comes
from the token, never from the request), applicants only touch their own draft application, campus staff only their
campus. For another person's record, EduMate often answers 404 rather than 403, so as not to confirm
that the record exists.



Method security


@EnableMethodSecurity (on SecurityConfig) switches on annotations such as:


@PreAuthorize("hasRole('ADMIN')")
public void resetDemoData() { … }

@PreAuthorize("hasRole('FACULTY') and #courseId == …")          // expressions can use parameters
public AttendanceSheet loadSheet(Long courseId, …) { … }


They are applied by a proxy (like transactions) and throw AccessDeniedException, which EduMate's
GlobalExceptionHandler turns into an audited 403. EduMate prefers the central matrix plus explicit service
checks, which are easier to review in one place and to unit-test, but method security is a standard alternative and
useful for services called from several entry points.



Other defences worth knowing


    

  • CORS: browsers block JavaScript from calling another origin unless the server allows it. EduMate
avoids the question entirely: the frontend and /api are served from the same origin (Vite's proxy in
development, nginx in production). If you need it, configure http.cors(...) with a
CorsConfigurationSource, never "allow everything".
    • 

  • Security headers: Spring Security adds X-Content-Type-Options,
X-Frame-Options: DENY, cache-control headers and more by default. EduMate relaxes frame options only for
the H2 console in development.
    • 

  • Secrets: the signing key comes from an environment variable and must be at least 32 bytes, or the
application refuses to start.
    • 

  • Audit: logins, lockouts and refusals are written to the audit log.

Testing security




EduMate's integration tests log in for real (bearer("admin") sends the login request) and check the
statuses: 401 without a token, 401 for a tampered token, 403 for the wrong role and for unknown endpoints, 423 after five
wrong passwords, and no stack trace in any error body. For tests that do not need a real token,
spring-security-test offers @WithMockUser(roles = "ADMIN") and MockMvc helpers such as
.with(jwt().authorities(...)).

Self-check


What is the difference between a 401 and a 403?

401: the server does not know who you are (no token, or an invalid one). 403: it knows who you are, and you may not
do this.


Why is it safe for EduMate to disable CSRF protection?

CSRF abuses credentials the browser sends automatically (cookies). EduMate's credential is a bearer token in a
header that JavaScript adds explicitly; another site cannot make the browser send it.


The RoleMatrix allows FACULTY to call a course summary. Why is that not enough?

It only checks the role, not the record. The service must also check that this teacher teaches this course
(object-level authorisation), or any teacher could read any course by changing the id.


What does anyRequest().denyAll() protect against?

Forgotten rules: a new or overlooked endpoint is refused for everyone instead of silently being open.
