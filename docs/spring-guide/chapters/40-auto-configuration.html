How auto-configuration really works, and how to write your own starter

Spring Boot's "magic" is ordinary Spring configuration, written by the Boot team, guarded by conditions, and loaded from a list inside each jar. Once you can read a condition report you can explain every bean in your application, override any default with confidence, and package your own reusable configuration as a starter.

Step 1: @EnableAutoConfiguration reads a list

@SpringBootApplication includes @EnableAutoConfiguration. At start-up it collects, from every jar on the classpath, the file

META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

Each line of such a file names one auto-configuration class. Spring Boot's own modules list a few hundred of them (data source, JPA, Flyway, Jackson, MVC, security, cache, Redis, Actuator…). They are ordinary @Configuration classes, marked @AutoConfiguration, full of @Bean methods, like EduMate's SecurityConfig. The difference is the conditions on them.

Step 2: conditions decide what applies

A typical auto-configuration looks like this (simplified from the data-source one):

@AutoConfiguration(before = SqlInitializationAutoConfiguration.class)
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })   // JDBC is on the classpath
@EnableConfigurationProperties(DataSourceProperties.class)               // binds spring.datasource.*
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(DataSource.class)                          // only if YOU did not define one
    HikariDataSource dataSource(DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }
}
ConditionThe bean or class applies only if…
@ConditionalOnClass / @ConditionalOnMissingClassa class is (not) on the classpath: "configure Redis only if the Redis client library is present"
@ConditionalOnMissingBeanno bean of that type exists yet: the back-off rule that lets you override defaults
@ConditionalOnBeansome other bean exists
@ConditionalOnPropertya setting has a value (EduMate's DemoDataSeeder uses this)
@ConditionalOnWebApplicationthe application is a (servlet or reactive) web application
@ConditionalOnResource, @ConditionalOnExpression, @ConditionalOnJava, @ConditionalOnThreading…more specialised tests (a file exists, a SpEL expression, the Java version, virtual threads enabled)

The golden rule: your beans win. User configuration is processed first; auto-configurations run afterwards and mostly say "only if missing".

Reading the condition evaluation report

Start with --debug (or expose /actuator/conditions) and Spring Boot prints, for every auto-configuration, why it did or did not apply:

============================
CONDITIONS EVALUATION REPORT
============================
Positive matches:
-----------------
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found required classes 'javax.sql.DataSource', … (OnClassCondition)
   FlywayAutoConfiguration matched:
      - @ConditionalOnClass found required class 'org.flywaydb.core.Flyway' (OnClassCondition)
      - @ConditionalOnProperty (spring.flyway.enabled) matched (OnPropertyCondition)

Negative matches:
-----------------
   UserDetailsServiceAutoConfiguration:
      Did not match:
         - @ConditionalOnMissingBean (types: …AuthenticationManager, …UserDetailsService,
           …JwtDecoder …) found beans of type 'org.springframework.security.oauth2.jwt.JwtDecoder'
           jwtDecoder (OnBeanCondition)

When something is configured that you did not expect (or is missing), this report answers "why?" in seconds.

Switching auto-configuration off

  • Most of them have a property: spring.flyway.enabled=false, spring.cache.type=none.
  • Exclude a whole class: @SpringBootApplication(exclude = RedisRepositoriesAutoConfiguration.class) or spring.autoconfigure.exclude=….
  • Usually the best way: define your own bean of the type, and the default backs off.

Write your own starter

Suppose several university applications want EduMate's audit log. Packaged as a starter, another application would only add one dependency and get an AuditLogger bean, configurable and replaceable. The recipe:

  1. An autoconfigure module (edumate-audit-spring-boot-autoconfigure) with the configuration, depending on Spring Boot's spring-boot-autoconfigure.
  2. Properties for the knobs: 
    @ConfigurationProperties("edumate.audit")
public record AuditProperties(boolean enabled, @DefaultValue("30") int retentionDays) { }
  3. The auto-configuration, conditional and backing off: 
    @AutoConfiguration(after = DataSourceAutoConfiguration.class)
@ConditionalOnClass(JdbcTemplate.class)
@ConditionalOnProperty(prefix = "edumate.audit", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                         // an application can still provide its own
    public AuditLogger auditLogger(JdbcTemplate jdbc, AuditProperties properties, ObjectProvider<Clock> clock) {
        return new JdbcAuditLogger(jdbc, clock.getIfAvailable(Clock::systemUTC), properties.retentionDays());
    }
}
  4. Register it in src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports: 
    com.edumate.audit.autoconfigure.AuditAutoConfiguration
  5. A starter module (edumate-audit-spring-boot-starter) that contains no code and depends on the autoconfigure module and whatever it needs (JDBC). Naming: your own starters are xxx-spring-boot-starter; the spring-boot-starter-xxx form is reserved for Spring's own.
  6. Metadata for editor completion: add spring-boot-configuration-processor as an optional annotation processor, and it generates META-INF/spring-configuration-metadata.json from the properties class.
  7. Test it without starting an application, with ApplicationContextRunner: 
    class AuditAutoConfigurationTest {
    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withConfiguration(AutoConfigurations.of(AuditAutoConfiguration.class))
            .withBean(JdbcTemplate.class, () -> mock(JdbcTemplate.class));

    @Test
    void createsTheLoggerByDefault() {
        runner.run(context -> assertThat(context).hasSingleBean(AuditLogger.class));
    }

    @Test
    void backsOffWhenTheApplicationHasItsOwn() {
        runner.withBean("custom", AuditLogger.class, () -> mock(AuditLogger.class))
              .run(context -> assertThat(context).getBean(AuditLogger.class).isSameAs(context.getBean("custom")));
    }

    @Test
    void canBeSwitchedOff() {
        runner.withPropertyValues("edumate.audit.enabled=false")
              .run(context -> assertThat(context).doesNotHaveBean(AuditLogger.class));
    }
}
Details that separate good starters from bad ones
  • Auto-configuration classes must not be found by component scanning; keep them in their own package, reached only through the imports file.
  • Use @AutoConfiguration(before/after = …) for ordering against other auto-configurations, never @Order.
  • Prefer @ConditionalOnClass on the class level with class literals: the conditions are evaluated from the bytecode before the class is loaded, so a missing optional library never causes ClassNotFoundException.
  • Keep beans overridable (@ConditionalOnMissingBean) and settings discoverable (metadata).
  • For GraalVM native images, conditions are evaluated at build time (next chapters), so they must not depend on things that change at run time other than properties.

Beyond annotations: registering beans in code

Spring Framework 7 adds BeanRegistrar, an interface for registering beans programmatically (loops, conditions in plain Java) in a way that also works with ahead-of-time compilation. For most applications @Bean methods remain the clearest choice; registrars are for framework and library authors.

Try it
  1. Run EduMate with --debug and find three auto-configurations that matched and three that did not; for each, say which condition decided it.
  2. Comment out the jwtDecoder bean in SecurityConfig and start: read the failure: nothing provides a JwtDecoder any more, because Boot's resource-server configuration only creates one when spring.security.oauth2.resourceserver.jwt.* settings are present. Restore it.
  3. Build the audit starter above as a small separate Maven project and use it from a fresh Initializr application.

Self-check

How does Spring Boot find auto-configuration classes?
From the META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports files in the jars on the classpath, loaded by @EnableAutoConfiguration.
What makes it possible to override almost any default?
@ConditionalOnMissingBean: auto-configured beans are only created if the application has not defined its own bean of that type, and user configuration is processed first.
Why does EduMate never log a generated security password?
UserDetailsServiceAutoConfiguration backs off because EduMate defines a JwtDecoder bean (one of the types in its @ConditionalOnMissingBean list).
How do you test an auto-configuration quickly?
With ApplicationContextRunner: build tiny contexts with chosen configurations, beans and properties, and assert which beans exist.
