Inside the container: the bean lifecycle, proxies and AOP

Transactions, caching, security annotations, retries and repositories all work the same way: the container creates your object, then may wrap it in a proxy that adds behaviour around your methods. Knowing exactly when and how that happens is what lets you debug the hard cases and extend the framework yourself.

How the application context starts ("refresh")

  1. Collect bean definitions. Component scanning, @Configuration classes, @Bean methods, @Imports and the auto-configuration list are turned into BeanDefinitions: recipes, not objects yet. (This is done by a special post-processor, ConfigurationClassPostProcessor.)
  2. Run BeanFactoryPostProcessors, which may change the recipes before any bean exists (resolving ${…} placeholders, adding definitions).
  3. Register BeanPostProcessors, the hooks that will see every bean as it is created.
  4. Create every non-lazy singleton, each after its dependencies (next section).
  5. Publish ContextRefreshedEvent and start SmartLifecycle beans (the web server, schedulers).
  6. Spring Boot then runs the ApplicationRunners and publishes ApplicationReadyEvent.

The life of one bean

BeanDefinition "localFileObjectStore"
   │
   ├─ 1. instantiate          new LocalFileObjectStore(appProperties)      ← constructor injection happens here
   ├─ 2. populate             @Autowired fields / setters (none in EduMate's main code)
   ├─ 3. Aware callbacks      setBeanName(…), setApplicationContext(…)  (if the class implements *Aware)
   ├─ 4. BeanPostProcessors   postProcessBeforeInitialization(bean)
   ├─ 5. initialise           @PostConstruct method → InitializingBean.afterPropertiesSet() → init method
   ├─ 6. BeanPostProcessors   postProcessAfterInitialization(bean)   ← PROXIES ARE CREATED HERE
   │                           (the object other beans receive may now be a proxy, not your instance)
   ├─ … in use …
   └─ 7. destroy (shutdown)   @PreDestroy → DisposableBean.destroy() → AutoCloseable.close()

Proxies: behaviour around your methods


A BeanPostProcessor may return a different object from the one it was given. Spring's
auto-proxy creator does this for every bean that has something to add (a @Transactional method, a
@Cacheable method, an aspect that matches…): it returns a proxy that holds your real object
and a chain of interceptors.


// What the proxy for ResultPublicationService does, in spirit:
class ResultPublicationService$$SpringCGLIB$$0 extends ResultPublicationService {
    ResultPublicationService target;                      // your real object
    List<MethodInterceptor> chain;                         // e.g. cache eviction, transaction

    @Override
    public ResultSetView publish(Long id, CurrentUser me) {
        // e.g. CacheInterceptor → TransactionInterceptor → target.publish(id, me)
        //   TransactionInterceptor: begin; call; commit (or roll back on RuntimeException)
        //   CacheInterceptor:        after success, evict "publishedResults"
        return invokeChain(chain, () -> target.publish(id, me));
    }
}

Everything that works through proxies shares the same rules:


    

  • Only calls from outside the bean go through the proxy (the self-invocation trap).
    • 

  • Only public, non-final methods of Spring-managed beans are intercepted; objects you create
with new are never proxied.
    • 

  • Several features on one method become a chain of interceptors, and the order can matter (should the cache be
checked before a transaction is opened?). Both default to the lowest precedence; when it matters, set it explicitly with
@EnableCaching(order = …) and @EnableTransactionManagement(order = …).
    • 



Proxy-based features: @Transactional, @Cacheable/@CacheEvict, @Async,
@PreAuthorize/@Secured, method validation (@Validated on a class), resilience
annotations (@Retryable, @ConcurrencyLimit in Spring Framework 7), @Observed, and your
own aspects.



Aspect-oriented programming (AOP): write your own interceptor


Cross-cutting concerns are things many classes need but none is about: timing, logging, auditing,
retries. AOP lets you write them once and apply them by rule.




TermMeaning



Join pointa place where extra behaviour can run; in Spring AOP always a method execution


Pointcutan expression selecting join points: "every public method of a @Service class"


Advicethe code to run: @Before, @AfterReturning, @AfterThrowing, @After, @Around


Aspecta class that bundles pointcuts and advice


Weavingattaching aspects to code; Spring AOP does it at run time with proxies (full AspectJ can also weave at compile or load time, even into newed objects)




An aspect that warns about slow service methods in EduMate (add the AspectJ starter,
spring-boot-starter-aspectj; it was called spring-boot-starter-aop before Boot 4):


@Aspect
@Component
public class SlowServiceAspect {

    private static final Logger log = LoggerFactory.getLogger(SlowServiceAspect.class);

    // every public method of every class annotated @Service in EduMate's packages
    @Around("within(com.edumate..*) && @within(org.springframework.stereotype.Service)")
    public Object time(ProceedingJoinPoint call) throws Throwable {
        long start = System.nanoTime();
        try {
            return call.proceed();                              // run the real method (and the rest of the chain)
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            if (ms > 500) {
                log.warn("Slow service call {} took {} ms", call.getSignature().toShortString(), ms);
            }
        }
    }
}


Use AOP sparingly
Behaviour that is invisible at the call site is hard to follow. Good uses are truly cross-cutting and boring (timing,
metrics, tracing). Business rules, such as "only the course's teacher may take its attendance", belong in plain code
where readers expect them, which is why EduMate writes courseAccess.requireTaughtBy(...) explicitly.



Writing a BeanPostProcessor


The lowest-level hook: see (and replace) every bean. For example, verifying at start-up that no singleton service
has a mutable, non-final field (the thread-safety rule of the beans chapter):


@Component
class StatelessServiceGuard implements BeanPostProcessor {
    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        Class<?> type = AopUtils.getTargetClass(bean);
        if (type.getPackageName().startsWith("com.edumate") && type.isAnnotationPresent(Service.class)) {
            for (Field field : type.getDeclaredFields()) {
                if (!Modifier.isFinal(field.getModifiers()) && !Modifier.isStatic(field.getModifiers())) {
                    throw new IllegalStateException(name + " has a mutable field '" + field.getName()
                            + "'; singleton services must be stateless");
                }
            }
        }
        return bean;
    }
}


Spring itself is built from such processors: @Autowired fields, @PostConstruct,
@Scheduled, @Async and proxy creation are each implemented by one.



Circular dependencies, lazy beans and scopes revisited


    

  • With constructor injection a cycle (A needs B needs A) cannot be built, and Spring Boot stops with a diagram of the
cycle. That is a feature: redesign (extract the shared logic into a third bean, or communicate through events).
@Lazy on one constructor parameter injects a proxy that resolves later; use it only as a last resort.
    • 

  • spring.main.lazy-initialization=true creates beans on first use: faster start-up in development, but
configuration errors appear later, at the first request instead of at start-up.
    • 

  • A request- or session-scoped bean injected into a singleton is injected as a scoped proxy that finds the
right instance for the current request each time.

Self-check


At which step of a bean's life are proxies created?

In postProcessAfterInitialization, after the bean is constructed, injected and initialised; other beans
then receive the proxy.


Why can Spring not add a transaction to a final method?

Spring Boot's default proxies are generated subclasses; a final method cannot be overridden, so the proxy
cannot intercept it.


What is the difference between a pointcut and advice?

The pointcut selects where (which method executions); the advice is what runs there (before, after, or around).


Name four Spring features that are implemented with proxies.

Transactions, caching, method security, @Async (also method validation, retries, Spring Data
repositories, observations).
