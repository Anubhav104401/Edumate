Events and modular monoliths

As an application grows, the danger is not size but tangling: every module calling every other module directly, until nothing can change alone. Application events loosen the coupling inside one application, and Spring Modulith turns "we organise code by feature" into rules a test can check.

Direct calls couple modules

When a teacher saves attendance, EduMate queues guardian e-mails for students below the minimum. Today the attendance service calls the notifier directly:



That is simple and fine at this size. But notice what it means: the capture service must know that e-mails exist, when
they should be sent, and must change whenever another reaction to "attendance saved" is added (update a dashboard cache,
recalculate eligibility, send an analytics event…). The publisher knows all its subscribers.



Application events: announce, don't command


Spring's container is also an event bus. A bean publishes an event (any object, usually a record); every
bean with a matching listener method receives it.


// 1. The event: a fact that happened, in the past tense
public record AttendanceSaved(Long courseId, String section, LocalDate date, int period) { }

// 2. The publisher only announces it
@Service

// 3. Any number of listeners, in any module, react
@Component
class ShortfallMailer {
    @EventListener

The attendance module no longer depends on notifications; notifications depend on attendance's event, a small
public record. Adding a reaction means adding a listener, without touching the publisher.



Timing matters: transactional listeners

@EventListenerimmediately, synchronously, inside the publisher's transactionthe reaction must succeed or fail with the change (it can roll it back)


@TransactionalEventListener (phase AFTER_COMMIT, the default)only after the publisher's transaction has committedreacting to facts that are definitely true: never e-mail about a save that was rolled back

After-commit reactions can be lost
If the application crashes between the commit and the listener, an in-memory event is gone. That is why EduMate's
notifications go through a database outbox written inside the transaction. Spring Modulith (below) can persist
events automatically for the same reason (its "event publication registry").



A modular monolith


EduMate is one deployable application with one database, organised by feature: attendance,
exam, fees, admissions, library, timetable… This is a
modular monolith: the simplicity of one application (one transaction for "pay and credit the ledger",
no network between modules) with the clarity of modules. The risk is that nothing enforces the modules: any class can
import any other.


Here are EduMate's actual dependencies between top-level packages (who imports whom):


attendance    → academic, common, config, notifications, security
exam          → academic, attendance, common, fees, notifications, security
fees          → academic, common, config, notifications, security
admissions    → academic, common, config, consent, documents, notifications, security
documents     → admissions, common, config, security            ← admissions ⇄ documents: a cycle
consent       → admissions, common, config, notifications, security   ← admissions ⇄ consent: a cycle
library       → academic, common, config, security
timetable     → academic, common, security
notifications → (nothing)
dashboard     → almost everything (it summarises every module: expected)


Mostly clean layering, with two cycles: admissions uses documents and consent, and they use
admissions back (to check that an application belongs to the caller). Cycles mean the modules cannot be understood,
tested or extracted separately.



Spring Modulith: modules you can verify


Spring Modulith treats each direct sub-package of the main package as an application module.
Classes in the module's top package are its public API; sub-packages are internal. One test checks the rules:


class ModularityTest {
    ApplicationModules modules = ApplicationModules.of(EduMateApplication.class);

    @Test
    void verifiesModularStructure() {
        modules.verify();          // fails on cycles and on access to another module's internal packages
    }

    @Test
    void writesDocumentation() {
        new Documenter(modules).writeModulesAsPlantUml().writeIndividualModulesAsPlantUml();
    }
}


On EduMate this test would fail today and name the two cycles. Fixing them is a design exercise: for example, let
documents ask a small interface owned by documents ("may this user touch this application?"),
implemented inside admissions, so the dependency points one way only (dependency inversion).


Other Modulith features:


    

  • @ApplicationModuleListener: a listener that is asynchronous, transactional and runs after commit: the
recommended way for modules to react to each other.
    • 

  • An event publication registry that stores events in the database until every listener has processed
them, and retries incomplete ones after a restart (a built-in outbox).
    • 

  • @ApplicationModuleTest: start only one module (and what it needs) in an integration test.
    • 

  • Generated documentation: module diagrams and a "module canvas" per module.
    • 



Monolith first
Many teams start with microservices and discover that the boundaries were wrong, now with network calls and
distributed transactions to undo. A well-modularised monolith keeps the options open: a module with a clean API and
event-based communication can later be extracted into its own service if scale or team structure truly demands it.

Self-check


What is the difference between @EventListener and @TransactionalEventListener?

The first runs immediately inside the publisher's transaction; the second (by default) only after the publisher's
transaction commits, so it never reacts to changes that were rolled back.


Why are events named in the past tense?

They state facts that have happened ("attendance saved"), not commands; the publisher does not decide what others do
about it.


What does ApplicationModules.verify() check?

That there are no cycles between application modules and that no module reaches into another module's internal
packages.
