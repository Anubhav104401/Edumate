Testing a Spring Boot application

Tests are how you know the rules hold today and will still hold after the next change. Spring Boot makes it easy to test at every level: plain Java for logic, the whole application for behaviour, a real database for compatibility, and even the framework's own configuration. EduMate has 64 backend tests; this chapter shows each kind.

The test pyramid

                ▲  few, slower, most realistic
               ╱ ╲     PostgreSQL compatibility (a real database server)
              ╱   ╲    integration tests: whole app + MockMvc + H2 (security, concurrency, workflows)
             ╱     ╲   slice tests: one layer (@WebMvcTest, @DataJpaTest)      ← not needed by EduMate yet
            ╱_______╲  unit tests: plain Java, no Spring (maths, rules, state machines)
                ▼  many, milliseconds each

spring-boot-starter-test brings JUnit 5 (@Test, @ParameterizedTest), AssertJ (assertThat(...)), Mockito (test doubles), JsonPath and Spring's test support. ./mvnw test runs them all.

Design for unit tests
Constructor injection, a Clock bean instead of LocalDate.now(), settings in a record, and pure
functions for calculations (AttendanceMath, SgpaCalculator, FineCalculator,
TimetableSolver) are what make these tests possible. If a class is hard to unit-test, that is usually a
design message.

The context cache: why the second test class starts instantly
Starting the application takes seconds. Spring's test framework caches application contexts and reuses one for every
test class with the same configuration. All EduMate integration tests extend the same base class with the same
annotations, so the application starts once per test run. Each different combination of
@TestPropertySource, @MockitoBean, profiles… creates (and caches) another context; keep them few.
Because the context and its database are shared, each test uses its own users and records so tests do not disturb one
another.

@DynamicPropertySource supplies settings whose values are only known at run time (the server's random
port). The most common way to do this in the industry is Testcontainers, which starts PostgreSQL (or
Redis, Kafka…) in Docker; Spring Boot even connects it automatically with @ServiceConnection. EduMate uses
embedded-postgres instead, so the test also runs on machines without Docker.

@WebMvcTest(AttendanceController.class)
class AttendanceControllerSliceTest {
    @Autowired MockMvc mvc;
    @MockitoBean AttendanceCaptureService capture;         // the real service is not started
    @MockitoBean AttendanceSummaryService summary;
    @MockitoBean ShortfallNotifier notifier;
    @MockitoBean CourseAccess courseAccess;

    @Test
    void rejectsAPeriodOutsideOneToSix() throws Exception {
        mvc.perform(put("/api/attendance/sessions").with(jwt().authorities(new SimpleGrantedAuthority("ROLE_FACULTY")))
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("{\"courseId\":1,\"section\":\"A\",\"date\":\"2026-09-28\",\"period\":9,\"marks\":[]}"))
           .andExpect(status().isBadRequest());
    }
}


Do not mock what you do not own, and do not mock everything
A test full of mocks tests the mocks. EduMate's approach, real application and in-memory database, catches the bugs
that matter (wrong queries, missing security rules, transaction mistakes) that mocked tests miss. Mock only the edges:
external services, clocks, randomness.

Self-check


What does @SpringBootTest start, and what does @AutoConfigureMockMvc add?

The whole application context (all beans, database migrations, security). MockMvc adds a way to send HTTP
requests through the real filters and controllers without a network port.


Why do EduMate's integration tests share one base class?

So they share one cached application context: the application starts once per test run, not once per class.


What is @DynamicPropertySource for?

Supplying settings whose values are known only at run time (like the URL of a database started by the test)
before the application context starts.


Why is RoleMatrixCoverageTest valuable even though every endpoint "works"?

It enforces a rule about the code itself (every endpoint has a security rule), so a forgotten rule fails the build
instead of becoming a data leak.
