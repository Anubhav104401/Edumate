Validation and error handling: saying "no" clearly

A good API refuses bad input early, explains exactly what was wrong, never leaks internals, and answers every kind of failure in the same shape. Spring gives you declarative validation and one central place to turn exceptions into responses.

Bean Validation: rules written on the data

Validation versus business rules


Bean Validation checks the shape of one request: types, required fields, lengths, ranges.
Business rules need the database or the current state ("this student is not in this section", "this
fee is already paid", "you gave the first approval, a different person must give the second"). Those belong in the
service, which throws an exception with a clear code:


// PaymentOrchestrator.initiate
if (due.signum() <= 0) {
    throw ApiException.conflict("ALREADY_PAID", "This fee has already been paid in full.");
}


The browser's checks are a courtesy, the server's are the law
EduMate's frontend checks the application form too, to give instant feedback. But anyone can send a request with
curl and skip the browser. The server must check everything again, which is exactly what the annotations
on ApplicationForm do.

Why these choices?


    

  • Unchecked (extends RuntimeException): no throws clauses everywhere, and, as
the Level 2 transactions chapter shows, an unchecked exception makes Spring roll back the transaction, so a
refused request leaves no half-written data.
    • 

  • A code as well as a message: the message is for people and may be reworded; the code
(ALREADY_PAID, STALE_UPDATE) is for programs: the frontend and the tests rely on it.
    • 

  • Factory methods (notFound, conflict…) keep the calls short and the statuses
consistent.
    •

fieldErrors under the matching form field.



How Spring picks the handler
When a controller method throws, Spring MVC looks for an @ExceptionHandler first in the controller's own
class, then in @ControllerAdvice classes, choosing the handler for the closest exception type
(a handler for ApiException wins over one for Exception). That is why a catch-all
Exception handler is safe: it only receives what nothing more specific handled. Note that errors raised
inside the security filters (a bad token) happen before Spring MVC, so they are answered by Spring Security's
entry point and access-denied handler instead; EduMate's RestAuthHandlers writes the same JSON shape
there.



Never leak internals


    

  • server.error.include-stacktrace: never and include-message: never in
application.yml stop Spring Boot's fallback error page from showing Java details.
    • 

  • The database handler logs the real constraint message but tells the client only "conflicts with data that already
exists": table and column names help attackers.
    • 

  • The catch-all handler gives a reference (traceId) that support can find in the log, and nothing else.
    • 




The standard alternative: Problem Details (RFC 9457)
Spring supports a standard error format, application/problem+json, through the ProblemDetail
class and ErrorResponseException; switch it on for Spring MVC's own errors with
spring.mvc.problemdetails.enabled=true. Its fields are type, title,
status, detail, instance, plus your own. EduMate predates that choice and has its
own ApiError, which carries the same information; for a new public API, prefer the standard.

Self-check


What happens if you forget @Valid on a @RequestBody parameter?

The annotations on the record are simply not checked; invalid data reaches your method. @Valid is
what triggers validation.


Why should "the fee is already paid" not be a Bean Validation annotation?

It depends on the database state, not on the shape of the request. Business rules belong in the service, which
throws an exception with a clear code.


Why does ApiException extend RuntimeException?

So it needs no throws declarations, and so Spring's transaction management rolls back the transaction
when it is thrown (by default, only unchecked exceptions cause a rollback).


Two handlers exist, one for ApiException and one for Exception. Which one handles an ApiException?

The ApiException handler: Spring chooses the handler for the most specific matching type.
